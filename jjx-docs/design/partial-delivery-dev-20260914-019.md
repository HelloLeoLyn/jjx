## 1. 现状（一次全发全扣）

| 环节 | 现状 | 证据 |
|---|---|---|
| 发货 | 订单发货（7→8）时生成 **1 张** 发货单 `DL`，数量取订单**全部**明细 | `OrderStatusServiceImpl.shipOrder` |
| 库存 | 同时建 1 张销售出库单并确认 → 一次全扣 | `@Event order.delivering` → `InventoryEventBridge.onSalesDelivery` |
| 订单数量 | `sales_order.shipped_quantity` **已有写入**：销售出库**确认**时按 Σ出库行数量累加（073 定稿） | `InventoryOutboundServiceImpl:569-592` |
| 累计的缺口 | 该回写**不校验上限**（代码只累加，注释写"不超订单量"但无校验）；且发货/出库仍按**全部明细全额**生成，所以现状累计值恒等于全量 | 同上 |
| 签收 | 签收是**发货单级**（`delivery_status=4`），一张单签一次 | `SalesDeliveryServiceImpl.receive` |
| 状态 | 订单 7 生产中 → 8 已发货，一步到位，没有"部分发货"态 | `SalesOrderStatusEnum` |

## 2. 目标

同一张订单可以发**多次**（先发一半、后补一半），每次生成自己的发货单与出库单；订单侧能看出"已发多少 / 还差多少 / 是否发完"。

## 3. 方案（推荐做法）

### 3.1 数据与模型（不新增表）
- **一订单多发货单**：`sales_delivery` 已经按 `order_id` 关联，天然支持多张；只需放开"每单只能一张"的隐含假设。
- **累计已发量**：`sales_order.shipped_quantity` 改为**每次发货累加**（末次可超发校验）。
- **单据状态**：`sales_delivery.delivery_status` 沿用（1待发货/2已发货/3运输中/4已签收/5已拒收）。多张单各自独立签收。
- **订单状态**：新增派生口径（不新增枚举值，按数量判定）：
  - `shipped_quantity = 0` → 仍是「生产中(7)」
  - `0 < shipped_quantity < total_quantity` → 「**部分发货**」（建议用 `prod_status` 或未发跟踪字段表达，避免动 7/8 主状态机）
  - `shipped_quantity >= total_quantity` → 「已发货(8)」
  - 全部发货单签收完成 → 可进「已完成」(由现有规则决定)

### 3.2 后端改动点（估）
1. `OrderStatusServiceImpl.shipOrder`：入参支持"本次发货明细"（行级数量，缺省=全部未发量）；生成 DL 时只带本次数量。
2. 发货校验：本次数量 ≤ 未发数量（`总数量 − shipped_quantity`）；**是否允许超发=待拍板**。
3. `shipped_quantity` **累加机制已存在**（出库确认时回写）→ 本方案只需：给发货入参加"本次数量"、并**补一个上限校验**（现状无校验）；再根据累计值决定订单停留 7 / 转 8。
4. 库存：出库单按**本次数量**建（沿用 `order.delivering` → 建单确认链路）。
5. 签收：仍是发货单级，不跨单合并。

### 3.3 前端改动点（估）
1. 订单发货弹窗：明细按行显示「订单数量 / 已发 / 本次可发」，本次数量可改（默认=未发量）。
2. 订单列表/详情：显示"已发 X / 共 Y"与部分发货标记。
3. 发货管理列表：已有（按单展示），无需大改。
4. 「未发跟踪」：可选的新查询（订单已发/未发一览），**待拍板是否要做**。

## 4. 待拍板（业务，不自定）

| # | 问题 | 备选 | 影响 |
|---|---|---|---|
| 1 | 是否允许**超发**（本次数量 > 未发量） | 禁止（推荐，正好补上现状缺失的校验）/ 允许并留痕 | 校验位置与提示文案；**注意现状代码无此校验** |
| 2 | 部分发货时订单主状态怎么表达 | A 保持 7，另用派生标识（推荐）；B 新增"部分发货"状态值 | 主状态机是否要动（动它 = 影响所有依赖 7/8 的判断与报表） |
| 3 | 未发完是否允许**取消剩余** | 允许（补一个"关闭未发"动作）/ 不允许 | 需要一个收口动作，避免订单永远挂在 7 |
| 4 | 「未发跟踪」清单是否要做 | 做（推荐，业务常问"这单还差多少"）/ 不做 | 新增 1 个只读查询页 |
| 5 | 部分发货的**签收/对账**是否按单 | 按单（推荐，与 D2 回签件一致）/ 按订单合并 | 影响对账与回签件归档粒度 |

## 5. 实施建议（拍板后分两步）

**第一步（核心，风险低）**：一单多发货单 + 本次数量 + `shipped_quantity` 累加 + 订单状态派生标识；出库按本次数量。验收：一张订单分两次发完，数量与库存前后对得上。
**第二步（可选）**：未发跟踪清单、取消剩余、超发策略（若选"允许"）。

## 6. 明确不做（本次方案范围）

- 不改现有单次全发的既有链路（拍板前保持现状）
- 不新增枚举值 / 不改 7、8 主状态语义（除非选 4-A 之外的方案）
- 不做"合并发货"（多订单一张单）——本方案只解决"一张单分多次"
