## 3. 根因（四条）

1. **双真相**：同一份数据有**两个可编辑入口**，用户永远在猜"以哪个为准"。← 最伤，且是"不确定"而非"难"
2. **三套交互**：同一个业务动作在三个模块三种做法，换个页面就要重学一遍。
3. **流程不显式**：真实顺序被摊平成一排平级按钮，没有"我在哪、下一步干嘛"；**需要靠文案解释的流程就是反直觉的流程**。
4. **「保存」≠「提交」**：弹窗保存只回写行数据、**未落库**；真正提交要按整单按钮。用户按完"保存"以为完事。

## 4. 目标形态

### 4.1 一处可编辑（去双真相）

**列表只看、弹窗只填**（推荐）：
- 列表：判定 / 合格 / 不良 / 原因 → **全部只读展示**（+ 批量操作按钮保留）
- 弹窗：**唯一的编辑场所**（检测项目 + 行判定 + 数量 + 原因 一次填完）

理由：弹窗能放大、能容纳更多列、能逐项；列表承担"概览 + 批量"，职责清晰。

### 4.2 统一录入弹窗骨架（三处共用一套结构）

```
┌─ 弹窗标题：{材料/批} 检验录入 ────────────────────────┐
│ [行信息条] 编码 · 名称 · 收货数量 · 当前状态            │
│ ──────────────────────────────────────────────  │
│ ① 检验项目 表（项目/标准/方法/设备/实测值/CR/MA/MI/结论）│
│ ② 行判定区  合格数量 | 不良数量 | 判定 | 不合格原因       │
│              （判定=不合格时才展开"原因/补充"）          │
│ ──────────────────────────────────────────────  │
│ [整批合格(本行)]  [保存本行]  [取消]  [保存并下一行 ▸]   │
└──────────────────────────────────────┘
```
- **三处骨架一致**（来料 / 入库管理 / 成品检验），差异只在字段（来料有处置语境、成品有判定上界闸门）
- 检验项目**不再"展开行"或"子弹窗"**两种形态并存 —— 统一成弹窗内的①区

### 4.3 流程显式化

页面顶部加**阶段条**，并让按钮**按阶段显隐/分组**：

```
① 录入  →  ② 提交  →  ③ 主管复核  →  ④ 确认入库
（检验员）  （检验员）   （品质主管）     （仓库）
```
- 每阶段只显示该阶段该做的按钮（现在 5 个平级 → 分到阶段里）
- 当前卡在哪一阶段，用颜色 + 文字说清（如「本单：3 行待录入 / 2 行待复核」）

### 4.4 「保存」与「提交」语义分离

- 弹窗内按钮 → **「保存本行」**（明确：只是暂存本行草稿）
- 页面级按钮 → **「提交检验」**（确认后交给复核）
- 列表/页面显著位置显示 **「有 N 行未提交」**

### 4.5 校验与反馈

- 行级**红标**（缺什么直接标在哪一行哪一列）
- 提交时给**缺失清单**（「3 行不合格未填原因」），**点一下跳到那一行**，而不是逐条 `return`

### 4.6 键盘流作为主路径

现有 `Tab 移动 / Enter 保存 / 保存并下一行` 是好设计 —— 应该**显式提示 + 默认引导**（工人用键盘比鼠标快得多）。列表内联编辑反而是逆向。

### 4.7 列瘦身

- 「接收数量」等**纯派生列**降为小字或移除
- 关键列固定，次要列收进「详情」
