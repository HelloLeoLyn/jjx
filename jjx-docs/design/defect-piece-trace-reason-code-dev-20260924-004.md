## 0. 一句话结论

不良现在只对齐到**「批 + 数量」**，原因也只是一段手打文字：能说"这批坏了 2 件、原因是外观颜色"，答不了"是**哪 2 件**、**哪项不合格**、**实测多少**"。
本方案做四件事：①**不良件级发号**（一物一号，正常品一律不动）②**原因取自检验单本身**（一级 = 检验项目，二级 = 不合格分级 CR/MA/MI，不另起全局原因字典）③**一件可多项不合格**（缺陷记录 = 件 × 项目 × 分级，处置仍按件）④**逐件实测值落库**（把检验单已有的"逐件实测"按件拆开）。
四件事都落在**同一张判定/处置弹窗**里，所以并成一批做。

## 3. 口径定义（本方案新增术语；与 045 §1 冲突时以 045 为准）

| 术语 | 定义 | 落点 |
|---|---|---|
| **不良件 Defect Piece** | 判定为不良、需要单独处置与追溯的**单件**（一物一号） | `quality_ncr_piece` |
| **件号 Piece No** | `<不良单号>-D<序号>`，序号 3 位补零、超 3 位**自然进位**；**不限数量**（用户 2026-09-24 决定，影响面对策见 §11） | `quality_ncr_piece.piece_no` |
| **原因（本方案定义）** | 一级 = **检验项目**（`check_item`，FQC 由模板给、不可编辑）；二级 = **不合格分级**（CR 致命 / MA 严重 / MI 轻微）；文本降级为「补充说明」 | `quality_lot_item` + `piece_defect` + `action` |
| **缺陷记录 Defect Record** | **件 × 项目 × 分级** 的一条事实记录；一件可有多条（一件同时外观+尺寸不合格 → 2 条）→ 记录层是**多对多**，处置层仍是**一件一个决定** | `quality_ncr_piece_defect` |
| **主缺陷 Main Defect** | 该件缺陷中最严重的一条（CR > MA > MI，同级取第一个）；列表/派工只展示主缺陷，点开看全部 | `quality_ncr_piece.main_check_item / main_defect_level` |
| **不良数量 N 的口径** | **由项目明细推导**：N 默认 = Σ(所选检验项目的 CR+MA+MI)；N > Σ → 拒绝（不允许"无因不良"）；N < Σ → 提示确认（需说明）；无法归因时选「其他 + 文本」兜底，**不留白** | 判定弹窗 + 校验规则（§5） |
| **件级实测值** | 检验单 `sample_values`（竖线分隔）按件拆出的单件实测值；件号因此带内容（"这件实测 3.2 / 超差"） | `quality_ncr_piece.actual_value` + `sample_index` |
| **件级处置** | 一次处置必须落在具体件上；**处置件数 = 该次处置数量** | `quality_ncr_action.piece_count` + `piece.action_id` |
| **件数守恒** | 不良件数 = 待处置 + 返工中 + 已回收 + 已报废 + 已让步放行 + 已退货 + 已作废 | 门禁第 ⑩ 查（§7） |
| **良品不发号** | 正常品不产生件号；将来要全链路序列号，只需把发号点上移到"报工/入库" | 本方案不动正常链路 |
| **不建全局原因字典** | 原因取自检验单（项目 + 分级）；仅保留一个兜底「其他 + 文本」（v1 §4.3 独立字典作废） | —— |

| 表 | 增量 | 用途 |
|---|---|---|
| `quality_ncr_action` | `main_check_item varchar(100)`、`main_defect_level varchar(4)`、`piece_count int` | 本次处置的主缺陷项目/分级 + 件数（与件表对账） |
| `quality_ncr` | `main_check_item varchar(100)`、`main_defect_level varchar(4)` | 首因（台账列表直接按 项目 × 分级 筛选统计） |

### 4.3 原因口径（v2 起修正：**不建全局字典**）

- **一级：检验项目** —— 取 `quality_lot_item.check_item`（FQC 项目由质量模板给出、页面不可编辑；已有 216 行真实数据可直接统计）。
- **二级：不合格分级** —— `CR`（致命）/ `MA`（严重）/ `MI`（轻微），与 `quality_lot_item.cr/ma/mi_quantity` 同口径，业内同构（金蝶/用友缺陷等级、SAP 缺陷代码分组）。
- **多缺陷**：一件可挂多条缺陷记录（如外观 MA + 尺寸 MI）；**处置仍按件**（一件一个决定），统计按缺陷记录数（Pareto 不被"只记首因"埋掉）。
- **兜底**：检验项目里没有的情况，允许「其他 + 文本说明」（沿用 `defect_reason`，降级为补充说明）。
- **不做**：不新建 `quality_defect_reason` 全局字典（v1 §4.3 作废）；不做"检验项目下的缺陷代码子字典"（将来确有细化需求再评估）。

## 5. 流程与状态机

```
① 检验录入：按检验项录 standard / 实测值 / CR·MA·MI      ← 已有（quality_lot_item）
② 判定：检验数量 / 合格 / 不良数量 N + 【选不合格检验项目（多选）】+ 补充说明（可空）
        联动校验（v3）：
          · N 默认 = Σ(所选项目的 CR+MA+MI)（自动预填，工人不必手打）
          · N > Σ  → 硬拦，提示"还有 K 件未归因，请补选检验项目"（不允许无因不良）
          · N < Σ  → 提示确认（需说明，留痕）
          · 确实归不到项目的（新型缺陷）→ 选「其他 + 文本」，不留白
        同事务落库：
          · 件号 NCR…-D001…D00N（N 件，不限数量）
          · 每件：main_check_item / main_defect_level（CR>MA>MI，同级取第一个）
                  actual_value（sample_values 按竖线拆）、sample_index
          · 缺陷记录：件 × 项目 × 分级 逐条写入（is_main 标一条）
          · 幂等：uk(ncr_id, seq_no) / uk(piece_id, check_item, defect_level)
③ 处置：选件（默认全选，可部分 / 按状态 / 按区间）→ 校验件数 = 处置数量
        ├─ 返工 REWORK     件 → REWORKING → 复检合格回收 → RECOVERED（入良品库存）
        ├─ 让步 CONCESSION 件 → CONCEDED（客户确认后转良品库存）
        ├─ 报废 SCRAP      件 → SCRAPPED（口径A：无库存扣减）
        └─ 退货 RETURN     件 → RETURNED（成品侧入口后续开，来料侧已用）
④ 撤销（受控）：报废撤销 → 件 SCRAPPED → PENDING，处置单 DONE → VOID（与 045 §2 撤销流一致）
⑤ 随批作废（022）：复检换代 → 未处置/未完处置件随单 → VOID（禁止再处置）
⑥ 补产 / 补料（002 已实施）：不动件级（补产是"新做的件"，不属不良件）
```

**逐件实测值解析规则（v2 新增）**：
- 解析源：被判为不良的那个检验项目的 `sample_values`（竖线分隔的样本值串）拆分；
- 段数 = 不良件数 → 一一对应（`sample_index` = 段序）；段数 < 件数 → 缺的件 `actual_value` 留空 + 页面提示"实测值不完整"；段数 > 件数 → 只取前 N 段 + 提示；
- 不做格式强校验、不阻断判定（沿用"先录数、后纠错"的既有风格）；复检换代时件随单作废，不跨版本搬运。

## 7. 门禁（第 ⑩ 查）

- 新增查：**件数守恒**（按 NCR 聚合）——`不良件数 = 待处置 + 返工中 + 已回收 + 已报废 + 已让步 + 已退货 + 已作废`；**处置对账**——`quality_ncr_action.piece_count = COUNT(piece WHERE action_id = …)`；**缺陷归因守恒（v3）**——`COUNT(DISTINCT piece) ≥ 不良数量 N`（不允许无因不良）、每件恰有一条 `is_main=1`。
- 归属：追加到既有 `scripts/check-inbound-lot-integrity.sh`（023 已定"扩既有脚本，不新起第三个"），随 `check:lot:strict` 进 `npm run validate`。
- **两步上线**：先提示模式（跑 5 个工作日，只报不拦）→ 存量无异常后转 `--strict`。
- 实现要点：全部聚合 SQL，不逐件循环（面向 §11 的大数量）。

## 9. 验收（一期）

1. 判定 2 件不良 + 选「外观 / MA」→ 生成 `NCR…-D001 / D002`，状态 `PENDING`，各带 `main_check_item=外观`、`main_defect_level=MA`；重复判定不重复发号。
2. **一件两项**：某件同时「外观 MA + 尺寸 MI」→ 该件 2 条缺陷记录、`is_main=1` 落在外观 MA；**处置仍按件**（一次处置只落一个件）。
3. **联动校验**：N 自动=Σ 项目不合格数；把 N 改大超过 Σ → 提交被拦并提示补选项目；把 N 改小 → 需确认说明方可提交。
4. 逐件实测：该检验项实测串有 2 段 → D001/D002 各带对应实测值；段数不足时有提示且不阻断。
5. 处置 D001 返工、D002 报废 → 件状态 `REWORKING` / `SCRAPPED`；`piece_count` 与件数一致；件数守恒 0 差。
6. 原因必选 + 统计：台账能按「检验项目 × 分级」汇总（同一原因可统计、可做 Pareto）。
7. 撤销报废 → D002 回 `PENDING`，处置单 `VOID`（与 045 撤销流一致）。
8. 大批量：判定 500 件 → 提示"N 个件号待生成"、列表分页、处置全选一次通过、门禁聚合口径正确。
9. 回归：库存五项 / 检验批九项 / 数量守恒八查仍全 0；工单缺口与补产链（002）不受影响。

## 12. 建议（供采纳，非本期强制）

1. **发号开关化**：`sys_config` 加 `quality.defect-piece.enabled`，出问题一键回退到数量口径。
2. **检验项目（含分级口径）的维护归口明确到质量模板**：原因取自检验项目，模板里项目清单的准确性直接决定统计质量；建议模板维护设专人（品质主管），并给"项目命名规范"一句约束（不用同义词、不带日期）。
3. **件号做成后续所有质量动作的 join key**（处置 / 退货 / 召回 / 客诉 / 报废单），一次做对。
4. **三期报废单直接用业内命名**（报废单 / 不合格品处理单），替掉"台账 + 处置记录两处拼"。
5. **`defect_reason` 保留为补充说明**，不废弃、不清洗历史数据。
6. 以后同类业务（质量 / 库存 / 生产交界）默认先对齐**金蝶 / 用友 / SAP 的形态**再落设计，本方案即按此写。
