## 0. 一句话结论

不良现在只对齐到**「批 + 数量」**：能说"这批坏了 2 件"，答不了"是**哪 2 件**、它们现在在哪"；原因也只是自由文本，统计不出"哪个原因最多"。
本方案只给**不良件**发号（正常品一律不动，零成本），并把「为什么不良」从随手写的文字改成**受控原因码（两级字典）**；两件事都落在**同一个处置弹窗**里，所以并成一批做。

## 3. 口径定义（本方案新增术语；与 045 §1 术语表不冲突，冲突以 045 为准）

| 术语 | 定义 | 落点 |
|---|---|---|
| **不良件 Defect Piece** | 判定为不良、需要单独处置与追溯的**单件**（一物一号） | `quality_ncr_piece` |
| **件号 Piece No** | `<不良单号>-D<序号>`，序号 3 位补零、超 3 位**自然进位**；**不限数量**（用户 2026-09-24 决定，影响面对策见 §11） | `quality_ncr_piece.piece_no` |
| **件级处置** | 一次处置必须落在具体件上；**处置件数 = 该次处置数量** | `quality_ncr_action.piece_count` + `piece.action_id` |
| **件数守恒** | 不良件数 = 待处置 + 返工中 + 已回收 + 已报废 + 已让步放行 + 已退货 + 已作废 | 门禁第 ⑩ 查（§7） |
| **原因码 Reason Code** | 两级受控字典值（大类 / 细项），处置时**必填**；`defect_reason` 保留为"补充说明" | `sys_dict: quality_defect_reason` + `action.reason_code` |
| **良品不发号** | 正常品不产生件号；将来要全链路序列号，只需把发号点从"判定不良"上移到"报工/入库" | 本方案不动正常链路 |

## 4. 数据模型

### 4.1 新表 `quality_ncr_piece`（不良件）

| 字段 | 类型 | 说明 |
|---|---|---|
| `piece_id` | bigint PK | 自增 |
| `piece_no` | varchar(64) UNIQUE | 件号（`<ncr_no>-D<序号，3 位补零>`，唯一） |
| `ncr_id` | bigint | 所属不良单 |
| `lot_id` | bigint | 来源检验批（追溯用） |
| `seq_no` | int | 序号（发号幂等键之一） |
| `status` | varchar(20) | 件状态：`PENDING/REWORKING/RECOVERED/SCRAPPED/CONCEDED/RETURNED/VOID` |
| `dispose_type` | varchar(20) | 最近处置类型（REWORK/CONCESSION/SCRAP/RETURN，冗余展示） |
| `action_id` | bigint | 关联处置单行（件级处置落点；可空=未处置） |
| `reason_code` | varchar(32) | 该件原因码（首因；字典值） |
| `order_id` / `work_order_no` / `lot_no` | —— | 冗余追溯字段（免 join 即可看件在哪张工单/批） |
| `remark` / `create_time` / `update_time` | —— | 备注与时间 |

索引：`uk_piece_no(piece_no)`、`idx_ncr_status(ncr_id, status)`、`idx_action(action_id)`、`uk_ncr_seq(ncr_id, seq_no)`（发号幂等）。
**铁律遵守**：件表只做身份与追溯，**不参与任何库存数量计算**（库存仍只由 `inventory_transaction` 驱动）。

### 4.2 字段增量
- `quality_ncr_action`：+ `reason_code varchar(32)`（原因码）、+ `piece_count int`（本次处置件数，用于与件表对账）
- `quality_ncr`：+ `defect_reason_code varchar(32)`（首因码，台账列表可直接按原因筛选统计）
- 不新增库存表、不改库存字段。

### 4.3 原因码字典
- 复用系统字典：`sys_dict`（`dict_type = quality_defect_reason`），两级用 `parent_value` 表达；不写死代码（对齐金蝶/用友"字典可维护"）。
- 建议字典初值（20 条上下，跑一个月再按实际分布收敛）：
  - 外观：颜色偏差 / 划伤 / 脏污 / 变形
  - 尺寸：超差 / 偏心 / 毛刺
  - 材料：来料缺陷 / 材质不符
  - 工艺：参数跑偏 / 漏工序 / 装配错位
  - 其他：其他（必带文本说明）

## 5. 流程与状态机

```
成品检验判定（不良 N 件）
   └─ 同事务按件发号：NCR…-D001 … D00N  状态 PENDING（幂等：uk(ncr_id, seq_no)）
处置（选件：默认全选，可部分/按状态/按区间）
   ├─ 返工 REWORK     件 → REWORKING → 复检合格回收 → RECOVERED（入良品库存）
   ├─ 让步 CONCESSION 件 → CONCEDED（客户确认后，转良品库存）
   ├─ 报废 SCRAP      件 → SCRAPPED（口径A：无库存扣减）
   └─ 退货 RETURN     件 → RETURNED（成品侧入口后续开，来料侧已用）
撤销（受控动作）
   └─ 报废撤销：件 SCRAPPED → PENDING，处置单 DONE → VOID（与 045 §2 撤销流一致）
随批作废（022）
   └─ 复检换代：未处置/未完处置件随单 → VOID（禁止再处置）
补产 / 补料（002 已实施）
   └─ 不动件级：补产是"新做的件"，不属不良件
```

- 发号时机：判定写入 `defect_quantity` 的同一事务内批量生成（不另设手动动作，免多一步操作）。
- 件号与批的关系：件依附 `ncr → lot`；复检换代时件随单作废，不跨版本搬运（与 022 口径一致）。

## 7. 门禁（第 ⑩ 查）

- 新增查：**件数守恒**（按 NCR 聚合）——`不良件数 = 待处置 + 返工中 + 已回收 + 已报废 + 已让步 + 已退货 + 已作废`；另加**处置对账**——`quality_ncr_action.piece_count = COUNT(piece WHERE action_id = …)`。
- 归属：追加到既有 `scripts/check-inbound-lot-integrity.sh`（023 已定"扩既有脚本，不新起第三个"），随 `check:lot:strict` 进 `npm run validate`。
- **两步上线**：先提示模式（跑 5 个工作日，只报不拦）→ 存量无异常后转 `--strict`。
- 实现要点：全部用聚合 SQL，不逐件循环（面向 §11 的大数量）。

## 9. 验收（一期）

1. 判定 2 件不良 → 生成 `NCR…-D001 / D002`，状态 `PENDING`；重复判定不重复发号。
2. 处置 D001 返工、D002 报废 → 件状态分别为 `REWORKING` / `SCRAPPED`；`piece_count` 与件数一致；件数守恒 0 差。
3. 原因码必填：不选提交被拒；台账可按原因分组统计（同一原因可汇总）。
4. 撤销报废 → D002 回到 `PENDING`，处置单 `VOID`（与 045 撤销流一致）。
5. 大批量：判定 500 件 → 弹窗提示"N 个件号待生成"、列表分页、处置全选一次通过、门禁聚合口径正确。
6. 回归：库存五项 / 检验批九项 / 数量守恒八查仍全 0；工单缺口与补产链（002）不受影响。

## 12. 建议（供采纳，非本期强制）

1. **发号开关化**：`sys_config` 加 `quality.defect-piece.enabled`，出问题可一键回退到数量口径。
2. **原因码字典先给 20 条**，跑一个月按真实分布收敛（避免一上来就设计成大而全）。
3. **件号做成后续所有质量动作的 join key**（处置 / 退货 / 召回 / 客诉），一次做对，别再各写各的。
4. **三期报废单直接用业内命名**（报废单 / 不合格品处理单），彻底替掉"台账 + 处置记录两处拼"的信息割裂。
5. **`defect_reason` 保留为补充说明**，不废弃、不清洗历史数据（旧单仍可读）。
6. 以后同类业务（质量 / 库存 / 生产交界）默认先对齐**金蝶 / 用友 / SAP 的形态**再落设计，本方案即按此写。
