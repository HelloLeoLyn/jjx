## 1. 现状与问题（已核实）

- 单据与批号都是**工单级**：入库单号 `FINISH-<工单号>`、成品批号 `BATCH-<工单号>` ⇒ 一个工单 = 一个批次 = 一张入库单。
- 检验批（`quality_lot`）是**质检侧**概念，可分批、可复检换代，与库存批次**粒度不一致**。
- 于是"合格累计"（会变）被反复写进"同一张单"（`syncFinishInbound` 覆盖 + 差额 ADJUST）：
  - 单据原地覆盖 ⇒ **看不到改过几次、每次多少**
  - 入库单详情页**无数量变更历史**
  - 流水 `ADJUST` 的 `lot_id` 为空（判定路径传 null），原因只靠备注文字
  - 该分支**绕过仓库确认**（019/020 已认定为风险点，并已造成当日汇总表少 50 的漏刷）
- 代码里**预留了"按检验单出单"的能力**：`createFromProduction(工单, 检验单ID, 数量)` → `FINISH-<工单号>-FQC-<检验单ID>`，带"已有分批单则完工不重复入"防重；但**无任何调用方**（带 inspectionId 的调用全传 null）⇒ 能力做了一半、没接线。

## 3. 目标设计：一个检验批一张入库单

### 3.1 单据与命名
- 入库单：`FINISH-<工单号>-FQC-<批号>`（批号用 `quality_lot.lot_no`，如 QL2609220006）
- 成品批次：`BATCH-<工单号>-<批号>`（库存明细唯一键已含 `batch_no`，**无需改表**）
- 一个工单 ⇒ N 张入库单、N 个库存批次；工单维度用 `source_id/source_no` 汇总

### 3.2 判定即出单（取消"同步入库"按钮）
- 判定（含复检）后：按**本批有效合格量**生成/维护**该批自己的**入库单（数量=本批合格），不再往工单级单里塞
- 前端：**删掉成品检验页的「同步入库」按钮**；列表「已入库」列改为读 `quality_lot.stored_quantity`（022 提供）；操作栏改成"去入库作业查看/确认本批入库单"
- 仓库确认：沿用 020 口径 —— **一律要仓库点「确认入库」才过账**（补入走 addStock，冲减走 020 新增的冲减分支）

### 3.3 复检规则（二选一，建议 A）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）红冲+重出** | 复检生效时：把**原批入库单生成一张红冲单**（负数量，走确认入库/或库存调整单），再按新合格量出一张新单 | 单据链一目了然（一红一蓝）；与 007"替换判定"语义一致 | 单据变多；需支持负数量单 |
| **B 差额调整单** | 原单不动，另出一张"差额调整单"（正/负） | 单据少一点 | 看到的是"调整单"，要顺着查才知道原委；实质仍是被 019/020 批判的覆盖式思路的变体 |

> 无论 A/B：**都要带 `lot_id`（022）+ 原因（复检/返工/报废）+ 操作人**，且每次都在单据列表可见。

### 3.4 工单完工/取消的建单逻辑
现有 3 处自动建单（`ProductionOrderServiceImpl` 重试/完工/取消部分入库）改为：
- 遍历该工单**有效检验批**，逐批出单（幂等键 = 工单号 + 批号）
- 已存在分批单 ⇒ 不再生成工单级兜底单（复用现成 `partialCount` 判重逻辑）
- "取消工单部分完工入库"同样按批出单

### 3.5 批关闭（接 017）
该批「入库完成（stored ≥ pass）且不良处置完成（disposed ≥ fail）」⇒ 自动 `CLOSED`；处置侧也要触发复算（017 的 A+C）。

## 4. 存量数据：**不迁移**（推荐）

- 老单据保留 `FINISH-<工单号>` / `BATCH-<工单号>`，新流程按批 ⇒ **天然兼容**（同一工单可能同时存在老单与新批单）
- 报表/台账按"工单 + 批次"两列展示即可；不要求历史拆批（拆批 = 大改 + 高风险）

## 5. 改造清单（预估）

**后端（约 4 处 + 复检规则）**
1. `QualityFinishServiceImpl`：判定/复检后 ⇒ 按**本批**出单（不再调工单级同步）
2. `ProductionOrderServiceImpl`（3 处）：按有效批遍历出单 + 判重
3. `InventoryInboundServiceImpl`：`syncFinishInbound` 工单级分支**停用**（或降级为"兜底/历史修复"）；`confirm()` 支持按单过账（含 020 的冲减）；`addStock` 走 019 的唯一入口
4. **复检红冲/差额**：按 §3.3 定案实现（新增负数量单或调整单）

**前端（约 3 处）**
1. 成品检验页：删「同步入库」、改「已入库」列数据源、操作栏加"查看/确认本批入库单"
2. 入库作业列表：按工单分组（一工单多单）+ 显示批次/检验批号；建议加**批量确认**
3. 工单/生产订单页：完工入库单链接（可能多个）

**SQL/迁移（0~1）**：仅批号命名规则变化（可用常量/代码层），如需加列走 022 已有迁移

## 6. 实施顺序与分工建议

```
020（口径B：都要仓库确认 + 冲减）      ← Hermes 进行中
  └→ 019（库存唯一入口 + 汇总刷新）    ← Hermes 进行中
       └→ 022（入库单挂 lot_id + stored_quantity 回写）  ← 待审核，建议先核销落地
            └→ 018（返工有效累计口径定案）+ 007（复检=更正口径统一）
                 └→ 【本案 021】一验批一单：单据粒度 + 前端 + 回归
                      └→ 017（批自动关闭）
```
- **合流点**：本案与 019/020/022 都动 `InventoryInboundServiceImpl` ⇒ **必须排在它们之后**，否则三头改同一函数
- **分工建议**：019/020/022 由 Hermes 收口；本案（021）由我（dahuang）承接，开始前先读 019/020/022 的最终实现再动手

## 7. 验收/回归清单

- 判定后：生成**本批**入库单（待确认），库存**不变**；仓库确认后库存/批次/流水/`stored_quantity` 才变
- 分批检验：两批各出单、各确认，库存按两个批次分行
- 复检更正：红冲/差额单可查，入库总量与合格累计一致；连续复检 3 次账不乱
- 返工闭环（v2 复检批）：工单完工数量**不被改小**（018 口径）
- 工单完工/取消：按批出单、不重复入
- 发货出库按批 FIFO、追溯/标签显示批次、报表按工单汇总
- `npm run validate`（含 `check:stock:strict` 对账门禁）长期 0

## 8. 风险与开放问题

1. **复检红冲规则**（§3.3）未定案 —— 这是唯一真正的新逻辑，建议先拍板
2. **多单带来的操作量**：仓库要逐张确认 ⇒ 建议同批做"批量确认入库"
3. **报表口径**：一工单多单后，所有"完工入库数量"报表改为按工单汇总
4. **与 018 的口径冲突**：返工复检批的"有效合格累计"若仍按现算法，出单数量会偏小 —— 必须等 018 定案
5. **历史单据**：不建议拆批；若将来要拆，单独立项评估

## 9. 附：为什么当初不是"一个批次一个单"

FQC 闭环方案 v3（dev-20260909-005）取向是**"零新表、最小改动"**：用"差额覆盖现有单"满足"完工数量 = 合格累计"的口径，而没有把**批次粒度**下沉到检验批（那会牵动库存台账/批次/报表/追溯一整片）。代码里 `FINISH-<工单号>-FQC-<检验单ID>` 这条按单出单的路做了但没接线，就是当时取舍留下的半成品。
