# 权限 fail-closed 规格（生产前置第 17 项）

状态：⏳待做（规格已定稿，代码未动）
任务：dev-20260914-014（任务 1770）
被取代 / 取代：无
什么情况看这篇：要修"权限清单为空=全放行"这个安全口子时；上线前必须落地
最后复核：2026-09-14

## 1. 现在为什么会全放行

| # | 位置 | 现在做什么 | 后果 |
|---|---|---|---|
| 1 | `jjx-web/src/permission.ts:51` | 拿不到权限清单时 `userStore.setPermissions(['*'])` | 判定层认为"什么都能干" → 需要权限的组件全部渲染 |
| 2 | `jjx-web/src/store/modules/user.ts:120` | 再兜底 `setPermissions(['dashboard:view'])` | 兜底逻辑两处、口径不一致 |
| 3 | `jjx-web/src/directives/index.ts:45` | `hasPermi()` 判定 | 判定输入是上面那份被兜底过的清单 |

**症状**：登录后权限清单为空（例如角色是登录后才授的、或 session 里的登录快照过期）→ 前端把页面/按钮全渲染出来 → 各组件各自向后端发请求 → 后端实时判权返回 **403**（前端看起来"满屏报无权限"）。
**真根因**：权限清单的**权威**在后端（后端已是 fail-closed），前端却对"清单为空"做了 fail-open 兜底。

## 2. 目标（验收口径）

1. 权限清单为空/缺失时，**前端按"无权限"处理**（不渲染、不发请求），不再全放行。
2. 登录后权限**实时重算**，不依赖登录那一刻冻结的快照；角色变更后无需"猜"（要么自动刷新，要么明确提示重新登录）。
3. 只有后端明确返回"全权"（约定为清单含 `*`）才视为全放行——**判断权在后端，前端不做兜底**。
4. 副作用：不再出现"满屏 403 噪音"。

## 3. 改动要求（给落地的人）

1. `permission.ts`：删掉 `setPermissions(['*'])` 兜底，改为 fail-closed 分支（拿不到清单 → 空清单 + 记一条日志/提示）。
2. `store/modules/user.ts`：去掉 `['dashboard:view']` 兜底；若确实需要"默认首页可见"，用**显式白名单常量 + 注释**说明理由（不要藏在兜底里）。
3. 权限获取时机：登录成功、页面刷新、路由守卫进入前，都从后端重新获取（复用现有登录用户信息接口）；确认 `userStore` 里不存在"只在登录时写一次、之后不再更新"的路径。
4. 角色变更后的处理：优先"重新登录刷新"（写进角色管理页的提示语），不引复杂的实时推送。
5. `hasPermi()` 的判定保持纯函数（输入空数组 → false），不要在里面再兜底。

## 4. 回归清单（改完必须过）

| # | 场景 | 期望 |
|---|---|---|
| 1 | admin 账号登录 | 菜单/按钮全有（后端返回 `*`） |
| 2 | 业务角色账号登录 | 只看到自己模块的菜单/按钮；不发其他模块请求 |
| 3 | 新账号（无任何角色）登录 | **看不到需要权限的菜单/按钮，无 403 报错** |
| 4 | 已登录状态下刷新页面 | 权限与登录时一致（不因刷新失效也不因刷新放大） |
| 5 | 角色权限被改后 | 重登后生效；未重登时表现可预期（不是全放行） |
| 6 | 手机端 `/m/**` | 同样遵守 fail-closed |

## 5. 明确不做

- 不改后端判权逻辑（后端已经是实时判权、fail-closed）。
- 不改角色/权限数据（数据修复属另一个任务）。
- 不做"权限实时推送"。
