## 2. 目标设计

### 2.1 单据、批次与绑定
- 入库单：`FINISH-<工单号>-FQC-<批号>`（用 `quality_lot.lot_no`，如 `FINISH-WO-PL2609220001-01-FQC-QL2609220006`；保留现有 `-FQC-<inspectionId>` 兼容读法）
- 库存批次：`BATCH-<工单号>-<批号>`
- 入库单**明细挂 `lot_id`**（022）：`inventory_inbound_item.lot_id = quality_lot.lot_id`，作为"单据↔检验批"的机器可读绑定（单号字符串只是人读）
- 一个工单 ⇒ N 张入库单、N 个库存批次；工单维度靠 `source_id/source_no` 汇总
- **不改表**：`inventory_stock_item` 唯一键已含 `batch_no`（`uk_item_warehouse_location_batch = inventory_item_id+warehouse_id+location_id+batch_no`）

### 2.2 判定/复检即出单（删掉「同步入库」按钮）
- 判定（含复检）后：按**本批应入量**（= 本批有效合格量）生成/维护**本批自己的**入库单；不再往工单级单里塞数量
- 幂等键：`工单号 + 批号`（重复判定只更新本批单据，不新建）
- 前端（成品检验页 `LotWorkbench.vue`）：① **删「同步入库」按钮**；② 「已入库」列改读 `quality_lot.stored_quantity`（022 提供）；③ 操作栏加「查看本批入库单」（跳入库作业并预筛工单+批号）
- 仓库确认：沿用 **020 口径**——**一切以「确认入库」为准**：应入 > 已入走 `addStock`，应入 < 已入走冲减（`reducePostedStock`），都要仓库点确认

### 2.3 工单完工/取消的建单逻辑
- 遍历该工单**有效检验批**（`summarizeEffectiveFqc` 同口径：跳过被复检取代的批），逐批出单
- 已存在分批单 ⇒ 不再生成工单级兜底单（复用现有 `partialCount` 判重）
- 「取消工单部分完工入库」同样按批出单

### 2.4 批关闭（接 017）
该批「入库完成（stored ≥ pass）且不良处置完成（disposed ≥ fail）」⇒ `CLOSED`；关闭判定改为**在过的两侧都触发**（入库回写 + 处置登记），并保留手工「重算收口」入口。

## 3. 关键规则定案

### 3.1 应入量的唯一口径（接 018）
- 单批应入 = 该批 `pass_quantity`
- 工单完工数 = Σ 有效批 `pass_quantity`（`summarizeEffectiveFqc`，仍是工单完工的唯一真源）
- **018 必须先定案**：复检批生效后原批失效不计账，若复检批只填"返工件数"，工单完工数会被改小。018 的 A 案（判定页把「批量 = 原批已合格 + 本次返工件数」作为基数并预填/校验）与本案天然契合：**一验批一单**后，复检批那张单的应入量就是它判定的合格量，口径必须写清

### 3.2 数量变更的可追溯（用户的第一诉求）
- 每张单据不再被覆盖：数量只在**本批单据**上体现；单据被取消/红冲时留痕
- 每次判定/复检都留一条链：`quality_lot` 版本（v1→v2）、对应单据、库存流水（带 `lot_id` + 单据号 + 原因）
- 入库单详情页显示：本批检验批号、版本、应入、已入、确认状态；列表按工单分组可展开多单

### 3.3 复检规则（**待拍板**，建议 A）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 红冲 + 重出（推荐）** | 复检生效时：原批入库单未过账 ⇒ 直接取消；已过账 ⇒ 生成一张**红冲单**（负数量，走仓库确认，落 020 的冲减能力），再为新批出单 | 单据链一目了然（一红一蓝）；与 007「替换判定」语义一致；与 020「减也要确认」一致 | 单据数量增加；需支持负数单展示与确认 |
| B 差额调整单 | 原单不动，另出"差额调整单"（正/负） | 单据少 | 看到的是"调整单"，要顺查才知道原委；实质仍是覆盖思路的变体 |

无论 A/B：红冲/调整单必须带 `lot_id` + 原因（复检/返工/报废）+ 操作人，且流水 `lot_id` 不再为空。

### 3.4 库存写入口（接 019）
所有库存动作（`addStock`、020 的 `reducePostedStock`、红冲）统一走 019 的**唯一入口**（改批次明细 + 重算汇总 `refreshSummary*` + 写流水），杜绝今天"漏刷汇总 50"那一类事故；对账门禁 `npm run check:stock:strict` 长期为 0。

## 8. 风险与开放问题
1. **复检规则未定案**（§3.3）——唯一真正的新逻辑，建议先拍板 A
2. **多单操作量**：仓库逐张确认 ⇒ 建议同批做批量确认（§5.3）
3. **报表口径**：一工单多单后，所有"完工入库数量"报表改成按工单汇总（SQL 层面注意 `SUM` 而不是取单张）
4. **与 018 的口径耦合**：018 不定案，出单数量可能偏小（返工复检场景）
5. **唯一键的 NULL 语义**（本次新发现）：`uk_item_warehouse_location_batch` 含 `location_id`，而完工入库的 `location_id` 常为 NULL —— MySQL 唯一键对 NULL 不去重，**多批次/多单据的重复防护依赖代码查询（按 item+batch+status 查），不能依赖唯一键**；改造时保持"先查后写"的幂等实现。
6. **构建可信度**（本次新发现，必须先解决）：`target/classes` 里有 23 个由 VSCode Java 插件（redhat.java）用错误 classpath 编译出的"带编译错误的 class"，maven 因类文件比源码新而跳过重编译 ⇒ **`mvn compile` 通过可能是假通过**，且 `mvn package` 可能把这些坏类打进 jar。已删除并 javac 全量重编译通过；**建议关闭该工作区 Java 插件自动构建**（`java.autobuild.enabled=false`）后再开工本案。
7. **历史单据的追溯**：老单看不到"改过几次"——不补历史，只在单据页加一行说明（"2026-09-22 前为工单级覆盖口径"）。

## 9. 为什么当初不是"一验批一单"（沿革，引用 021 稿）
