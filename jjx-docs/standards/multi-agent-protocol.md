## 1）总原则

1）任务卡明确目标、范围和验收，sys_task 记录任务与进度；交付方式遵循用户当次要求。用户要“贴卡，我转发”时，聊天直接给完整可复制卡，不自行启动 agent 或另建任务书文件。需要文件交付时按任务书指南登记，不强制聊天卡与文件卡双份维护。
2）单一写者（Single Writer）：同一文件同一时刻只允许一个任务、一个 agent 在写。
3）证据与结论对应：编译通过只证明编译；单元测试、真实库事务、页面运行各自说明验证范围。任务要求的行为证据缺失，不能宣称完成；不要求与任务无关的查库或全量检查。
4）先能力后壳：先把"能跑通"做出来，再换界面；不允许"换了壳但功能没接上"。
5）谁先提交谁算沿用 CONVENTIONS §11 的冲突仲裁口径；它不授权抢写他人已领取的文件，也不授权把他人在制改动带进自己的提交。

## 2）角色

1）Owner（用户）：定方向与口径、终审、插卡、拍板例外。
2）Dispatcher（派工方，当前 Hermes）：拆卡、派卡、维护依赖与波次、卡面质检、验收复核。
3）Executor（执行者）：认领 → 实现 → 自查 → 提交 → 回写。
4）Verifier（验收者）：只读复核（白名单 / 真实输出 / 痕迹 / 反例）。
分离约束：Verifier 不等于 Executor，同一张卡不许自产自验。

## 3）卡的状态机

0 待开始 → 1 进行中 → 2 待审核 → 10 完成（仅 Owner 拖）
                      ↘ 3 驳回 → 1（原卡退回，不新建卡）
4 废弃（被拆细 / 被取代，备注写清替代卡）

- 认领用 CAS（见第 5 节）；2 只代表"执行者认为完工"，不等于验收通过。

## 4）任务书模板（Definition of Ready）

模板唯一真源：[任务书指南](../guides/agent-task-brief.md)。默认短卡六段，复杂内容按需补充；要求信息齐全，不要求凑九段、固定字数或逐字匹配标题。下面是派工检查项，可并入短卡相应段落，不是第二份模板。

| 检查项 | 必须说清楚的内容 |
|---|---|
| 目标与范围 | 用户可观察的结果；允许写入的精确路径；其余只读 |
| 前置与归属 | 所需前置及满足判据，无则写无；执行者与验收人；文件不与在制任务重叠 |
| 既定规则与缺口 | 引用规则真源及章节；区分已有决定、已核实实现、未实现部分；不能把遗漏实现当作新需求重新问用户 |
| 约束与护栏 | 必须保留的行为、禁做事项；涉及测试/构建时写实际内存与超时限制 |
| 行为验收与证据 | 先行为和反例，再最小可执行命令及预期结果；涉及归属/事务时写查库判据 |
| 交付与阻塞 | 产物、提交和回写要求；具体停止条件、影响、可继续项及解除条件 |

替换组件的卡还须列全入口与保存路径，引用已有能力清单，逐项说明保留、承接或经用户批准删除的能力。按“入口 × 新增/编辑 × 整单/产品行”核对适用场景；不适用写明，不凭相似页面推定已覆盖。前置没有覆盖必要场景时先补派工边界，不能把不完整的前置称为“全绿”。

用户要聊天任务卡，就在当前回复完整给出；“出卡”不等于授权直接派进程。用户已明确授权的登记与交付继续完成，不反复确认；未授权的写入不能以“只登记”“顺便留痕”为理由执行。

## 5）认领（防撞的唯一机制）

    UPDATE sys_task
       SET status=1, assignee_name='<操作员>', update_by='<操作员>', start_time=NOW()
     WHERE task_code='dev-YYYYMMDD-NNN' AND status=0;

1）影响行数 = 1 → 认领成功；= 0 → 已被别人认领，停手，报告"卡已被 <assignee> 于 <start_time> 认领"。
2）认领前必须存档 git status --short 基线，确认白名单文件无他人在制改动；有 → 按 §11 停相关部分。
3）租约：status=1 且 60 分钟无 update_time 变化 → 向 Dispatcher 报告，由其裁定是否释放；不自行抢卡。
4）一个 agent 同时"进行中"的卡不超过 2 张。

## 6）完成模板（Definition of Done）

任务收尾统一遵循 CONVENTIONS §5 的六行报告，不另设“给用户六段版”。模板只在真源维护；日常答疑、讨论、进度询问不套任务收尾格式。跨 agent 交接需要的背景和证据写进任务记录或授权的文档，不能挤进六行报告。

提交前只暂存本任务文件，核对暂存区与白名单；完成后按仓库规则提交、推送并回写待审核及完成时间，用户明确不提交/不推送时遵从。已提交、已推送、待审核、验收通过、已完成分别报告，不能互相替代。

remark 写前读取原值并预检 CHAR_LENGTH，追加本次执行者、改动、提交、命令、结果和遗留；超过 500 字使用 description，写后回查。前次阻塞和失败记录不得覆盖；读取时原值已为空，只能报告“本次读取为空”，不能在没有审计证据时断言谁覆盖过。

完成检查：白名单内交付、必需行为证据与命令通过、反例核对、未验证项如实标注、提交/推送状态真实、任务回写可追溯。仅执行者自查通过不能替代独立验收；status=2 只表示待审核。

## 7）验收模板（Verifier 四查）

    卡：dev-YYYYMMDD-NNN（执行者：<x>）
    1）白名单：diff 是否只落在卡面白名单 → <是 / 否 + 文件清单>
    2）真实输出：复核执行者贴的命令与结果是否一致 → <一致 / 不一致>
    3）痕迹：需要时只读查库（jjx_ro）核对预期行 → <查到 / 未查到 / 本卡不涉及>
    4）反例：卡面反例是否真的没出现 → <没出现 / 出现>
    结论：通过 / 退回（退回理由 + 需补什么）

- 退回 → 原卡 status=3 + 理由，执行者改完再置 2；不新建卡。
- 验收者只读，不改执行者的文件。用户明确要求验收时，可在授权的任务记录内追加结论；普通提问或讨论中的只读核查不授权回写。
- 看不到原始输出或退出码就写“未核实”。流水线 `命令 | tail` 后的 `$?` 可能只代表 tail；需要日志截取时先保存被测命令退出码，或使用 pipefail 并检查对应退出码。无输出本身不能证明成功。
- 替身/模拟库测试不能宣称真实业务库已经落定；编译通过不能宣称回滚已验证。运行态验证未完成时，写清未验证项，不以“代码级通过”掩盖任务的行为验收缺口。
- 验收不隐含启动、停止或重启服务授权；服务操作仍按 CONVENTIONS §9 的逐次明确授权规则。

## 8）与人交互规则

### 8.1 先判断授权，再决定动作

按 CONVENTIONS §9 判断用户这句话在做什么，不按孤立动词机械匹配。“你要怎么做”“为什么这么改”是在问方案，不等于要求执行；“你来优化这份规则”是对该范围的执行授权。

| 当前请求 | 允许的动作 | 不能自动追加的动作 |
|---|---|---|
| 讨论、建议、要求解释或纠正表述 | 回答；必要时做相关只读核查，并说明核查范围 | 写文件（含临时草稿）、改库、建卡、提交、派进程或改运行状态 |
| 查、核查任务状态或事实 | 做对应只读查询，报告证据与未知项 | 修改状态、追加验收结论或登记新任务 |
| 登记任务、出卡、修改、派发、验收等执行要求 | 在本次明确范围内完成；权限已给且范围清楚时不重复问 | 把一种授权扩展成另一种，如“出卡”变为“启动 agent” |
| 暂停、先不动、算了或缩小范围 | 停止/缩小所指任务的后续工作，简要说明已做与未做 | 自行删除产物、回滚记录、扩大清理，或未经明确授权终止进程 |

理解仍有歧义时按 CONVENTIONS §9 先澄清动什么、哪里、交付什么。已授权的执行过程中，用户问进度或补充解释时先回答并保留原目标；用户明确暂停时停止推进。发送、发布、推送等外部动作遵循已有明确授权与仓库规则，授权充分不重复问；服务生命周期必须当次明确授权。

### 8.2 把当前问题讲清楚

1）直接回答当前这一问，简单问题不机械复述。默认先讲具体场景、问题及后果，再说明是否有需要用户决定的事；这些是信息要求，不强制拆四段或固定行数。
2）固定名称，不只说“保存”“那个弹窗”“第二条”。例如明确说“报价单保存”“整单附件保存”“产品行附件保存”“报价列表附件弹窗”；同一动作不轮换成“钉附件”等自造比喻。技术词确有必要时解释一次，不要求普通用语逐个找代码出处。
3）同一轮多问题讨论保持名称和编号对应。引用先说“报价列表附件弹窗问题”，不能让用户猜编号指哪一轮。新发现的问题明确另列，不悄悄把两项改成三项；已处理的问题给出结果，未处理项保留状态。
4）严格区分事实、推断、建议：已核实才下确定结论；缺证据就说哪项未核实。不得先把推断写成裁决，再拿未核实的前提让用户选方案。
5）需要确认前先查已有决定。既定规则下的实现缺口不要求用户重新定功能；是否已获修复授权另外判断。“按既定规则需要补实现”不等于“现在可以自行开工”。
6）仅当存在真实的、未被既定规则解决的取舍，才说明场景、差异、后果及推荐，问一个具体问题。用户询问原理时不夹带选择题，不用“回两个字我就做”催促，不在每次回答末尾附加“要不要继续”。
7）用户说“没懂”时，换成一个具体操作场景，只解释当前问题，写全谁、在哪个入口、点击哪个保存、期望和实际结果。不能重复原文、增加问题或暗示用户理解有误。
8）日常答疑以短段落为主，细节按用户需要展开；比较时用表格，证据在结论后简列。枚举统一 1）/ A) / a)，结论不编号。无需用户决定时直接写“无需重新定规则”；已有执行授权就继续，未授权就停在解释。

### 8.3 回答示例与反例

以下是当时讨论的表达示例，不代表当前实现状态；实际结论须重新对照相关代码、任务记录与验证证据。

| 场景 | 合格回答或动作 | 反例 |
|---|---|---|
| 用户问“071 什么问题” | “编辑报价单时上传产品图，再点报价单保存；新流程的编辑接口尚未接收并关联附件，替换组件后可能提示保存成功但附件未关联。已有规则要求一起保存，这是实现缺口。”结论须与已核实证据一致 | 把报价单保存、附件信息保存混说；顺带要求选择另一个弹窗的方案 |
| 用户问“另一个问题呢” | 用固定名称回答该问题，说明已核实和未核实部分 | 改编号、增加问题，让用户自己对照上一轮 |
| 用户说“没懂保存指哪个” | 直接回答“这里指报价单编辑弹窗底部的报价单保存”，再解释该按钮的一个场景 | 重讲全部设计并催用户选择 a/b |
| 用户只问优化建议 | 给建议与依据，留在讨论；只读核查如有必要可做 | 建任务、写 /tmp 草稿、改卡或直接派 agent |
| 用户要“贴任务卡，我转发” | 按指南在聊天给完整可复制卡；登记/文件产物依用户授权与仓库规则处理 | 自行启动 Codex/OpenClaw，或仅返回文档路径 |
| 编译通过、事务行为未验 | 分别报告“编译通过；事务回滚未验证”，任务是否可收尾按本卡验收判断 | 把未完成行为验收的前置称为“全绿、可接下一卡” |

### 8.4 执行前与回复前自查

执行前核对：本次请求允许什么动作，是否有更早的明确约束，写入对象是否在白名单，是否误把建议当授权。回复前核对：回答的是当前问题吗，名称完整吗，事实与推断分开了吗，是否漏项，是否又问了已定的事。自查由 agent 完成，不把检查表逐轮贴给用户，也不要求用户不断重复提醒口令。

发现自己越界时立即停止新增动作，简要说明实际改了什么和影响；不在解释期间继续写“改进记录”，也不自行删除或回滚产物。后续处理遵循用户明确指令，不反复催用户收拾 agent 擅自增加的事项。

## 9）波次与依赖（WIP 限流）

1）同一波内，各卡的"文件所有权"必须互不重叠；派工时按文件分组。
2）前置卡必须 status=2 且本次所依赖的行为验收通过 → 才开下一波。核对实际提交和已验证范围，不能只看状态；例如新增保存已实现不等于编辑保存也已实现。
3）接入类卡（换界面）必须排在其"能力卡"之后：先做能落定 / 能跑通的卡，再做接入卡。
4）每波结束做一次"整波验收"（端到端痕迹），再开下一波。

## 10）冲突与升级

1）发现同文件他人在制 / 已改：取证（baseline 时间戳、git log）→ 报告 Owner / Dispatcher → 停相关部分；不覆盖、不还原。
2）卡被误领 / 重领：CAS 拿不到即让，报告；不并行改同一文件。
3）口径冲突：先列"这会改变既有规则 X"，取得确认再改（§9.1）。
