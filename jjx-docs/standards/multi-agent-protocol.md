## 1）总原则

1) 卡是唯一交接介质：派工 / 验收 / 回写都落到 sys_task + 绝对路径文件；聊天只放摘要。
2) 单一写者（Single Writer）：同一文件同一时刻只允许一个任务、一个 agent 在写。
3) 证据优先（Evidence-based）：没有真实命令输出 / 只读库痕迹 = 未完成；"静态通过"不能当运行态验收。
4) 先能力后壳：先把"能跑通"做出来，再换界面；不允许"换了壳但功能没接上"。
5) 谁先提交谁算：冲突仲裁口径；后来者 rebase 或让。

## 2）角色

1) Owner（用户）：定方向与口径、终审、插卡、拍板例外。
2) Dispatcher（派工方，当前 Hermes）：拆卡、派卡、维护依赖与波次、卡面质检、验收复核。
3) Executor（执行者）：认领 → 实现 → 自查 → 提交 → 回写。
4) Verifier（验收者）：只读复核（白名单 / 真实输出 / 痕迹 / 反例）。
分离约束：Verifier 不等于 Executor，同一张卡不许自产自验。

## 3）卡的状态机

0 待开始 → 1 进行中 → 2 待审核 → 10 完成（仅 Owner 拖）
                      ↘ 3 驳回 → 1（原卡退回，不新建卡）
4 废弃（被拆细 / 被取代，备注写清替代卡）

- 认领用 CAS（见第 5 节）；2 只代表"执行者认为完工"，不等于验收通过。

## 4）任务书模板（Definition of Ready）

沿用 agent-task-brief.md 短卡，派卡必填 9 段。合同条款线后的内容逐条写清楚：

1) 目标：触发条件 + 当前行为 + 期望行为，一句话。
2) 文件所有权（写白名单）：绝对路径；只动这些；其余只读。
3) 前置 / 波次：前置卡码 + 满足判据；无则写"无（立即可开）"。
4) 约束：必须保留的行为；本次禁做；明确例外。
5) 验收（先行为、后命令）：
   a) 用户可观察结果；
   b) 硬证据：真实命令 + 期望输出；涉及归属 / 落库的，附"只读查库痕迹"判据；
   c) 反例：看似通过但实际错误的结果。
6) 护栏：内存 / 耗时 / 并发等强制护栏；如内核笼子命令。
7) 交付：代码 / 文档精确路径；提交与回写要求。
8) 验收人：与执行者不同的人。
9) 阻塞：具体停止条件；证据、影响、可继续、解除条件。

DoR 检查（缺一不派）：
1) 目标可验收（有用户可观察结果）；2) 文件白名单非空且不与在制卡重叠；3) 前置明确；
4) 硬证据可执行；5) 至少一条反例；6) 验收人已指定；7) 护栏已写。

## 5）认领（防撞的唯一机制）

    UPDATE sys_task
       SET status=1, assignee_name='<操作员>', update_by='<操作员>', start_time=NOW()
     WHERE task_code='dev-YYYYMMDD-NNN' AND status=0;

1) 影响行数 = 1 → 认领成功；= 0 → 已被别人认领，停手，报告"卡已被 <assignee> 于 <start_time> 认领"。
2) 认领前必须存档 git status --short 基线，确认白名单文件无他人在制改动；有 → 按 §11 停相关部分。
3) 租约：status=1 且 60 分钟无 update_time 变化 → 向 Dispatcher 报告，由其裁定是否释放；不自行抢卡。
4) 一个 agent 同时"进行中"的卡不超过 2 张。

## 6）完成模板（Definition of Done）

a) 跨 agent 交接（聊天 + remark），仓库六行：

    任务码：dev-YYYYMMDD-NNN
    提交：<hash>（已 push）
    改：<N 个源文件，一句话>
    验：<命令 → 结果>（没跑写未跑）
    DB：<迁移 / 表 / 权限；无则无>
    遗留：<一句话；无则无>

b) 给 Owner 的报告（自解释，六段）：

    1）任务：<任务码> · <一句话标题>
    2）做了什么：<白话 1-2 句；改了 N 个文件>
    3）改了：<文件 / 模块>
    4）验证：<跑了什么 → 结果>
    5）状态：<待审核 / 已完成 / 卡住（卡哪）>｜提交：<hash>（已 push）｜DB：<有 / 无>
    6）遗留 + 下一步：<白话；无则"无">

DoD 检查（缺一不算完成）：
1) 白名单内改动且只有这些文件；2) 硬证据已跑且贴真实输出；3) 痕迹类任务已附只读查库结果；
4) remark 已写（改动 / 命令 / 结果 / 遗留）；5) status=2 + completed_time；6) 未验证项如实标注；7) 反例已验证不出现。

## 7）验收模板（Verifier 四查）

    卡：dev-YYYYMMDD-NNN（执行者：<x>）
    1）白名单：diff 是否只落在卡面白名单 → <是 / 否 + 文件清单>
    2）真实输出：复核执行者贴的命令与结果是否一致 → <一致 / 不一致>
    3）痕迹：只读查库（jjx_ro）核对预期行 → <查到 / 未查到>
    4）反例：卡面反例是否真的没出现 → <没出现 / 出现>
    结论：通过 / 退回（退回理由 + 需补什么）

- 退回 → 原卡 status=3 + 理由，执行者改完再置 2；不新建卡。
- 验收者只读，不改执行者的文件。

## 8）与人交互规则

1) 一次只问一个：需确认时先贴"待确认清单"（已回 / 待回），只问第一个待回项。
2) 报告自解释：每个结论写四段 —— 担心什么 / 预期 / 实测（带 文件:行 或 SQL 结果）/ 达标（中文词）。
3) 讨论 vs 执行：按 CONVENTIONS §9 判；"讨论 / 建议 / 要不要"只给判断不落盘；只有"做 / 改 / 写"才动手，且只做点名范围。
4) 编号：1）/ A) / a)；状态写中文词（待开始 / 进行中 / 待审核 / 完成 / 驳回 / 废弃）；不用方框、圆圈类符号。
5) 先给"用户可观察结果"，再讲实现；不把技术细节堆在结论前。
6) 外部动作（发送 / 发布 / 部署 / 改运行态）先问；只读诊断可直接做。
7) 变更服务生命周期（启停 / 重启）必须当次明确授权。

### 8.1 反跑偏与反术语幻想（2026-10-16 增）

背景：与 AI 对话时常见两种毛病 —— 跑偏（答非所问、顺带扩展、把讨论当执行）与术语幻想（编造看似专业的词、把内部代号当既有概念、用未定义的缩写）。

用户可复制的口令（随口一说即生效）：
1) 「停，只回答我问的那一句。」—— 禁止扩展与追问第二个问题。
2) 「用仓库里已有的说法回答；新词必须给出 文件路径:行号，给不出就别用。」—— 反术语幻想。
3) 「先给结论，再给证据（命令 + 输出）。」
4) 「这是讨论，不要落盘。」/「这是执行，只做 X，别顺手做 Y。」
5) 「你说的『XXX』在哪份文档 / 代码里？引用出来。」
6) 「不要用内部代号，用大白话再说一遍。」

Agent 侧硬规则：
1) 术语白名单：只允许用 a) 用户当次用过的词；b) 仓库文档 / 代码里已存在的词。用新词必须附 文件:行 出处。
2) 找不到出处的词一律不用，改用大白话描述，并明确说"我找不到出处"。
3) 回答前先用一句话复述问题，再作答；答完即停，不追加"顺便……"。
4) 不确定就直说"不确定 / 查不到"，不许编。
5) 结论句不编号；枚举才编号；不堆砌形容词。

## 9）波次与依赖（WIP 限流）

1) 同一波内，各卡的"文件所有权"必须互不重叠；派工时按文件分组。
2) 前置卡必须 status=2 且验收通过 → 才开下一波。
3) 接入类卡（换界面）必须排在其"能力卡"之后：先做能落定 / 能跑通的卡，再做接入卡。
4) 每波结束做一次"整波验收"（端到端痕迹），再开下一波。

## 10）冲突与升级

1) 发现同文件他人在制 / 已改：取证（baseline 时间戳、git log）→ 报告 Owner / Dispatcher → 停相关部分；不覆盖、不还原。
2) 卡被误领 / 重领：CAS 拿不到即让，报告；不并行改同一文件。
3) 口径冲突：先列"这会改变既有规则 X"，取得确认再改（§9.1）。
