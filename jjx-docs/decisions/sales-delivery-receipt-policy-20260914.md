## 一、背景

销售发货链路（现状实现）：

```
订单(生产中7) --发货--> 生成发货单 DL(delivery_status=2 已发货) + 自动建销售出库单扣库存
                --签收--> delivery_status=4 已签收，记录签收人/电话/备注 + 登记人
                --打印--> 行操作随时可点，系统版/纸版(QR-026) 双版式
```

问题观感：打印与签收在 UI 上并列，看不出先后；"签收之后再打印有什么用"——因为**随货凭证的正确时序没有被表达出来**，且凭证闭环的两个环节（回签件、打印留痕）缺失。

## 二、现状证据（代码/事实）

| 项 | 证据 |
|---|---|
| 发货写单 + 出库事件 | `OrderStatusServiceImpl.shipOrder`：生成 `DL` 单、`delivery_status=2`，`@Event order.delivering` → `InventoryEventBridge.onSalesDelivery` 建销售出库单并确认 |
| 签收 | `SalesDeliveryServiceImpl.receive`：写 `receiver_name/receiver_phone/receive_remark`、`receive_time`（登记时间）、`receive_by/receive_name`（登记人），`delivery_status=4`；已签收不可重复 |
| 打印 | `views/sales/delivery/print.vue`：`PrintCompanyHeader` + A4Canvas，系统版与 QR-026 双版式，底部"收货人 ____ / 日期 ____"签字栏 + 单号二维码 |
| 打印留痕缺失 | 送货单 `print.vue` **未调用** `print-log`（收款单 `salesReceiptApi.printLog`、发票 `salesInvoiceApi.printLog` 均有） |
| 回签件缺失 | 无上传入口，`sys_attachment` 无 `biz_type=sales_delivery` 的归档路径 |
| 状态机死状态 | `DeliveryStatusEnum`：1待发货/2已发货/3运输中/4已签收/5已拒收；代码仅使用 2 与 4，3/5 无任何写入路径，拒收无回流逻辑 |
| 签收无联动 | 签收后不改订单状态、不发事件、不起账期/对账 |
| 无分批发货 | 一张订单一次全发，`total_quantity` 取全部明细，不支持部分发货 |

## 三、决策（口径）

**D1 签收主体与登记**
- 签收由**客户**在纸质送货单上完成；系统侧由**销售内勤（或发货经办人）代登记**。
- 必须区分两个日期：**客户签收日期（纸面）** 与 **系统登记时间**。现状只有后者，须补前者。
- 升级方向（可选、后续）：客户扫送货单二维码自助签收（复用 `/m/` 扫码底座），不开客户账号。

**D2 回签件归档**
- 客户签字的回签件**必须进系统**，作为对账/开票/收款依据。
- **分级强制**：月结客户、自送/专线物流 → 强制上传；快递小额 → 可用运单号 + 物流签收轨迹替代。
- 落法：挂发货单附件（复用 `AttachmentUploader`，`bizType=sales_delivery`），并标记为"结算依据"。

**D3 打印定位**
- 打印定位为「**随货凭证 + 补打留档**」：发货成功后应有引导去打印，随货交客户签字。
- **必须补打印留痕**（谁/何时/第几次/哪张单），与 1237 的 `biz_type+biz_id` 口径对齐。

**D4 发货状态机**
- `3 运输中`、`5 已拒收` 两个死状态：**要么删除，要么补全**（含拒收回流：拒收后订单回到何状态、能否重新发货、责任归属）。
- 业务取舍待定，登记任务跟进（见 §五 T3）。

**D5 分批发货**
- 现实存在"先发一半、后补一半"，现系统一次全发全扣，与实物流不符。
- **单独立项**评估（改动涉及发货单/出库/订单状态/签收口径），见 §五 T5。

**D6 签收事件**
- 签收应触发事件 `sales.delivery.received`（通知销售 + 起账期/进对账清单），使其不再是"死动作"。

**D7 入口去重**
- 核查「订单跟踪页(menu 17)」与「发货管理(menu 218)」的数据源与入口是否重复，避免两个半吊子入口。
