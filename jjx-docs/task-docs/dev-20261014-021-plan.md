## 3）方案（第一版）

### 1）一个入口，复用已有脚本

| 子命令 | 负责什么 |
|---|---|
| `inspect` | 只读检查环境、工作区、在制任务及文件冲突 |
| `start` | 登记任务、记录白名单、保存基线、置「进行中」 |
| `check` | 按改动范围运行必要验证 |
| `commit` | 核对文件归属及验证结果，只提交本任务文件 |
| `record` | 回写提交、验证、遗留及任务状态 |
| `push` | 单独检查目标并推送 |

- 内部调用现有 `agent-preflight.sh` / `task-register.sh` / 各门禁脚本，**不重写第二套**登记、门禁、数据库逻辑。
- **不提供**「一把梭 finish」；`commit` / `record` / `push` 分开执行，某一步被拦不拖累其他步骤。

### 2）任务只配置一次，后续不重复描述

- `.tmp/tasks/<任务码>/plan.tsv`（忽略目录，不入库）记录：A) 任务码/目标/允许修改的文件；B) 开工 HEAD、已有改动及文件指纹；C) 验证类型（前端/后端/库存写入/迁移/文档）；D) 已完成步骤、检查结果、日志位置。
- 该清单是**执行记录**；`sys_task` 仍是任务状态真源。不存口令，不允许填写任意 shell 命令。

### 3）验证按影响范围选择，并记住结果

| 改动 | 执行的检查 |
|---|---|
| 前端代码 | 相关测试 + `vue-tsc` |
| 前端状态逻辑 | 再加 `check:status-enums` |
| 后端代码 | 编译 + 相关测试（固定 Mockito/JVM 代理参数） |
| 库存写入路径 | 再加 `check:stock:strict`（五项全 0） |
| 文档 / 迁移 | `check:docs` / 迁移门禁 |

- 验证结果关联**被验证文件的内容指纹**：A) 文件没变 → 不重复跑相同检查；B) 文件变化 → 相关结果自动失效；C) 判不了影响范围 → 明示需补验证，**不静默跳过**。
- 数据库对账、远端状态属**易变信息** → 每次重查，不吃文件缓存。

### 4）机器保存日志，让 agent 看结论

- 默认输出 ≤12 行摘要：任务 / 范围 / 冲突 / 后端项数 / 前端项数 / 库存五项 / 提交条件 / 未验证 / 日志路径。
- 失败只输出失败步骤 + 关键错误 + 日志路径（`.tmp/tasks/<任务码>/check.log`）；诊断时按片段读取。
- 不默认把整份编译日志、规范、源码送进上下文。

### 5）多 agent 协作与失败恢复做成硬检查

- A) 越白名单文件、目标文件混入他人改动 → 停该步。
- B) 提交用独立暂存区（路径限定 commit 或 `GIT_INDEX_FILE`），保护他人暂存，提交后核对索引一致。
- C) 提交成功但推送失败 → 记「已提交、未推送」，重试只执行推送。
- D) 数据库 / 权限 / 门禁失败 → 保留原始错误，不吞错、不自动绕过（**禁** `--no-verify` 绕过）。
- E) 服务启停**不纳入**执行器，仍遵循逐次授权规则。

### 6）第一版控制范围，不造平台

- 只做一个入口脚本、少量验证配置、任务执行记录与必要测试。
- 不做网页、不建新表、不引入后台服务，不自动决定业务方案。

## 4）验收（用本次踩过的坑当验收条件）

- A) 从任何目录调用，都不会跑错 Maven / npm 目录。
- B) Mockito 参数一次配置，后续直接复用。
- C) 他人有暂存改动时，提交仍只包含本任务文件。
- D) 推送被拒绝，不影响已授权的任务回写（`record` 先于 `push`）。
- E) 未改代码时重复检查，不重复执行已通过的静态验证。
- F) 默认只返回摘要，详细日志按需读取。

最小验证（实施时）：手动跑 `inspect` + `check`（无改动 → 命中缓存不重跑）；造一次他人暂存 → `commit` 只含白名单；期望退出码 0 且摘要 ≤12 行。业务方案正确性不靠脚本，需人/agent 复核。
