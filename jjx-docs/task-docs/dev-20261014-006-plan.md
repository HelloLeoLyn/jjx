## 1）现象、根因与证据（都已实跑核对，别重复盘）

**现象**：产品详情「业务流转附件」/产品资料集「客供资料」报

```text
ERROR 1267 (HY000): Illegal mix of collations (utf8mb4_unicode_ci,IMPLICIT) and (utf8mb4_0900_ai_ci,IMPLICIT) for operation '='
```

**唯一炸点**：`jjx-server/.../system/service/ProductCustomerDocumentService.java:33-34`

```sql
LEFT JOIN sys_dict_item dt ON dt.dict_code='attachment_document_type'
     AND dt.item_key=r.document_type AND dt.deleted=0
```

`sys_dict_item.item_key` = `utf8mb4_unicode_ci`，`sys_attachment_ref.document_type` = `utf8mb4_0900_ai_ci` → 相撞。同文件 `:23` 的 `COALESCE(dt.label,r.document_type)` 是同一对列的第二次碰撞（同一病根）。

**根因**：迁移 `271_attachment_references.sql:75 / :103` 建表只写了 `DEFAULT CHARSET=utf8mb4`、**没写 `COLLATE`** → MySQL 8 取"字符集自己的默认排序规则" `utf8mb4_0900_ai_ci`（不是库默认 `utf8mb4_unicode_ci`）。反证：同表 `product_code` 是迁移 `276_attachment_ref_product_code.sql:9` 用**显式** `COLLATE utf8mb4_unicode_ci` 加的 → `r.product_code=p.product_code` 不报错（实跑返回 8 行）。

**触发时机**：这条查询是 HEAD `c6329a3b` 新加的（`+68` 行 + 测试 `+123` 行）→ 新 SQL 第一次踩到老表的老毛病。

**漂移现状**（`bash scripts/check-collation.sh --strict` → **exit 1**）：

```text
-- 3) 漂移汇总：基表列 15 个 / 基表默认 2 张（期望都是 0）
-- 4) 非目标 collation：utf8mb4_0900_ai_ci 14 / ascii_bin 2
✘ --strict：仍有 collation 漂移（列 15 / 表 2 / 库默认 utf8mb4_unicode_ci）
```

**门禁盲区**：`check-collation.sh:75` 的"危险面"只按**同名列**跨 collation 匹配（只报了 `material_code`、`order_no`），而真正炸的 `sys_dict_item.item_key ↔ sys_attachment_ref.document_type` 是**不同名列** → 报了漂移却没点名。

**配套发现**：门禁提示的修复文件 `jjx-docs/sql/migrations/193_collation_unify_utf8mb4_unicode_ci.sql` **已不在仓内**（被 `f96927a4 rm sql` 删除；可取回：`git show 9c5bdd58:jjx-docs/sql/migrations/193_collation_unify_utf8mb4_unicode_ci.sql`，711 行）。所以"全库统一 unicode_ci"这条口径现在只写在脚本注释里 → 本卡顺手把它固化进 `CONVENTIONS.md`（补债，非新增冲突）。

## 3）范围与约束

### 3.1 订正迁移（本卡主体）

**执行前先跑**（拿逐列清单，**不要照抄本卡的 13 列**——门禁报的是 15 列，含 2 个刻意的 `ascii_bin`）：

```bash
bash scripts/check-collation.sh              # 人工读"非目标 collation 的列分布"
bash scripts/check-collation.sh --preflight  # 串列外键 + 唯一索引撞键预检
```

**`sys_attachment_ref` 必须按列 `MODIFY`，禁止用 `ALTER TABLE ... CONVERT TO`**，原因：

1）`source_type varchar(50) CHARACTER SET ascii COLLATE ascii_bin` 是刻意设计，`CONVERT TO` 会把**整表字符串列**都改掉，把它冲成 `utf8mb4_unicode_ci`；
2）`source_type` 还在唯一索引 `uk_attachment_ref_active(attachment_id, source_type, source_id, active_product_id, active_marker)` 里，整表转换会改索引键的排序规则 → 有撞键风险（正是 `--preflight` 要查的）。

待转列（7 个，全部 `utf8mb4_0900_ai_ci`）：`create_by` / `deleted_by` / `display_name` / `document_type` / `remark` / `source_no` / `update_by`；`product_code` 已是 `utf8mb4_unicode_ci`，别动。写法（**列定义必须整段照抄 `SHOW CREATE TABLE` 的原文本**，不得丢 `NULL` / `DEFAULT` / `COMMENT`）：

```sql
ALTER TABLE sys_attachment_ref
  MODIFY create_by     varchar(64)  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…原注释…',
  MODIFY deleted_by    varchar(64)  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…',
  MODIFY display_name  varchar(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…',
  MODIFY document_type varchar(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…',
  MODIFY remark        varchar(500) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…',
  MODIFY source_no     varchar(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…',
  MODIFY update_by     varchar(64)  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL COMMENT '…',
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

`order_shortage_ledger`：6 列 `utf8mb4_0900_ai_ci`（`create_by`/`material_code`/`material_name`/`order_no`/`remark`/`update_by`），无外键、唯一索引在数值列上（`order_id,material_id`）→ 可用 `ALTER TABLE order_shortage_ledger CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;`（仍按 `--preflight` 复核）。

收尾核对：`SHOW CREATE TABLE sys_attachment_ref;` 必须看到 `source_type` 仍是 `ascii_bin`、其余字符串列与表默认都是 `utf8mb4_unicode_ci`。

### 3.2 防复发规则（三层，全部落盘）

1）**写法规范（`CONVENTIONS.md` 新增条款，草案如下，措辞可再压）**
   - 全库字符串列一律 `utf8mb4_unicode_ci`；例外只有刻意列（`sys_attachment.source_type`/`upload_key` 等 `ascii_bin`），必须在迁移注释里写明理由。
   - 建表/加列的 SQL **必须显式** `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`；**禁止只写 `DEFAULT CHARSET=utf8mb4`**（MySQL 8 会取 `utf8mb4_0900_ai_ci`）。
   - 新迁移执行后必须跑 `bash scripts/check-collation.sh --strict`，漂移必须为 0。
2）**门禁·静态**：新增脚本扫 `jjx-docs/sql/migrations/**`，出现 `CHARSET=`/`CHARACTER SET` 却没在同语句带 `COLLATE=` → 报错退出；挂到 `jjx-web/package.json` 的 `validate` 链（与 `check:collation:strict` 并列）。
3）**门禁·动态**：改 `check-collation.sh` 的"危险面"（:75）为**跨表字符串等值连接键**扫描（不只看同名列；至少覆盖 `document_type ↔ item_key`、`product_code ↔ product_code`、`material_code`、`order_no`），并在迁移执行收尾自动/显式提示跑一次 `--strict`。

1）`bash scripts/check-collation.sh --strict` → **exit 0**，漂移 0（列 0 / 表 0 / 库默认 `utf8mb4_unicode_ci`）；

4）静态门禁：故意在临时迁移里写 `DEFAULT CHARSET=utf8mb4`（不带 `COLLATE`）→ 门禁必须报错。

**反例（看似通过其实错）**

1）只给 `ProductCustomerDocumentService` 的 SQL 加 `COLLATE` → 报错消失但漂移还在，其他 join 迟早再炸（本卡明确不做）；

3）迁移执行完没跑 `--strict` → 可能仍有别的表/列漂移（门禁报 15 列，本卡只列举了已知 13 列）。
