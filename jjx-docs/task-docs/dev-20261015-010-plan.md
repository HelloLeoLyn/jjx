## 0）速览

现在系统要回答"某次审批/打印，当时用的是哪份文件"时，靠的是**附件 id 字符串**去反查；id 会被复用或删除，于是出现"指向别人的文件"或"指向不存在的文件"（已实测 19 条）。本方案把"当时那份文件"**连元数据一起存底**，使之后任何删改/解绑都不影响它。

## 1）现状与证据

1）**判定靠启发式**：`AttachmentAccessService.protectedFile()` 用 `review_flow.attachment_ref_ids` 的 `JSON_CONTAINS`，以及 `review_flow/sales_quotation_flow/sales_sample_round/sales_order_review/sales_customer` 里 `attachment_ids / attachments` 的**正则字符串匹配**判定"受控/历史硬引用"；另有四类硬引用表（工艺单明细、质量模板、菲林、产品结构图）。
2）**已实测的坏引用**：`quality_template_registry.file_id` 19 条异常 —— 8 条指向不存在的附件、11 条指向**建档时间晚于模板**的附件（即历史 id 复用被误认）。
3）**没有内容指纹**：这些引用只存 id，不存 `sha256`/文件名快照，事后无法证明"当时那份文件"是什么。
4）**已有部分防护**：`dev-20261012-011` 的 B 修复（硬引用判定加"附件建档时间 ≤ 模板建档时间"防护、`hasFile` 改有效性判定）已编译通过、待随重启复验 —— 属**缓解**，不解决"没有存底"这个根因。

## 2）候选方案

- **A（推荐）独立存底表**：新增 `attachment_evidence`，在"需要留证"的动作发生时写一行快照。
  - 字段（建议）：`evidence_id` / `biz_type` / `biz_id` / `source_ref_id`（可空）/ `attachment_id` / `file_name` / `file_size` / `file_type` / `sha256` / `captured_at` / `captured_by` / `remark`。
  - 读法：按 `biz_type + biz_id` 查证据；打印/复现/追责都读它；`protectedFile()` 的"历史硬引用"判定改为"存在 evidence 行"。
  - 优点：一处模型、一处读法；与"文件 / 引用 / 证据"三层口径一致（见 `reference/attachment-state-vocabulary-dev-20261015-001.md` §7）。
- **B 在现有证据表逐张补列**（`review_flow`、`sales_order_review`、`sales_quotation_flow`、`sales_sample_round`、`sales_customer` 各加 `*_sha256/*_file_name`）：写入点分散、判定仍散落，重复度高，不建议。
- **C 只加防护不做存底**（= 现状 + B 修复）：成本最低，但"编号复用后仍指错"的根因保留。

**推荐 A**，分两步：先并行（新表 + 新写入点，读法仍兼容旧字段），稳定后再把 `protectedFile` 的启发式切到 evidence。

## 3）写入点清单（实施前逐项确认）

1）审批/评审类：`review_flow`（含 `attachment_ref_ids`）、`sales_order_review`、`sales_quotation_flow`、`sales_sample_round`。
2）打印留痕：质量模板打印日志（`quality_template_print_log` 的 `biz_type/biz_id`）。
3）质量类：`quality_template_registry.file_id`、质量档案。
4）工艺/工程硬引用：`product_work_spec_item`（DRAWING/DOCSET_FILE）、`engineering_film`、`product.work_spec_json.structureFileId`。
5）客户侧：`sales_customer.attachments`。
> 每处都要写清"哪一刻算定格"（提交/审核通过/打印），以及定格时快照哪些字段。

## 4）存量订正（19 条）

1）口径：`quality_template_registry` 的 19 条 `file_id` **全部置空 + `remark` 留痕**（写明"历史 id 复用误认，模板文件需重新上传"），**不猜内容、不按 id 反查内容**。
2）模板文件由业务重新上传（用户已知晓）。
3）附件 5~11 的"产品身份漂移"是**另一件事**（是否恢复成"现行受控图纸"），已有独立记录，不在本卡内一并处理。
4）订正属"批量 UPDATE/订正" ⇒ 执行前**用户手工全库备份**（现行规则：三类必做之一）。

## 5）验证与回滚

1）迁移：建表脚本幂等（`CREATE TABLE IF NOT EXISTS` + 列注释）；走 `scripts/db-migrate.sh`，执行前备份存在性由脚本校验。
2）功能验证：挑一条已审核单据，确认 evidence 行存在且字段（文件名/大小/sha256）与附件行一致；解绑后再查 evidence 仍在。
3）反例：不能因为"evidence 表建了"就宣称 19 条已修；两条要分别验。
4）回滚：`file_id` 按执行前备份写回；`DROP TABLE attachment_evidence`（新表无外键依赖）。

## 6）边界与待拍板

1）**不动**现有证据字段语义；新表并行期不改变任何既有读法。
2）待拍板：`protectedFile()` 何时从"启发式"切到"读 evidence"（切换点必须单独定，避免一处漏改导致误判）。
3）待拍板：存底是否只对"已审核/已打印"定格，还是所有提交动作都存（影响数据量）。

## 7）不做（本卡）

1）不实施：本卡只交付方案；实施需另立执行卡并由用户点名。
2）不重跑历史迁移、不改 19 条以外的数据、不动附件文件本体。
