## 0）一屏速览（先读这里）

**一句话**：附件"挂在哪"现在有**两套**——老的 `sys_attachment.biz_type/biz_id`、新的 `sys_attachment_ref`。本卡把老的那套**退役**，只留 refs 一条链；并把**多产品单据**（报价/订单）的附件产品归属定下来。

**已拍板（不要再讨论）**：

| # | 拍板项 | 定论 |
|---|---|---|
| P1 | 老通道 `biz_type/biz_id` | **退役**：不再写、不再查（只留历史） |
| P2 | 非单据来源（付款凭证 `purchase_payment` 等） | **扩 refs 白名单、新增来源**，不保留老通道例外 |
| P3 | 多产品单据附件 `product_id` | **上传时选产品**（下拉=本单明细产品，可留空=整单级）；**回填只回填显式选了的行** |
| P4 | 真删文件能力 | 公共组件**只解除引用**；真删收敛到**一个受控管理入口** |
| P5 | 下载/预览、重复检测的老路径 | **一并退役**，只留 refs 那套 |
| P6 | 与 041 的先后 | **本卡（042）先定口径 → 041 再落地产品侧** |

**数据库**：**本卡不需要改库**——无迁移、无字典改动（`purchase_payment` 来源只是代码里的白名单）。所以**连不上 MySQL 的沙箱（如 Codex）也能做**全部分代码工作。

**不做**：产品文件库 / 工程图集 / 产品文件归档（归 `041`）；脏数据与存量迁移（用户明确不考虑）；权限模型本身。

## 1）目标

**当前行为（已核）**：附件中心新通道上传**不写** `biz_type/biz_id`；所有按老字段查询的地方**看不到新附件**（附件中心"历史附件"段、产品详情"业务流转附件"、质量档案、状态流转弹窗、付款凭证）。下载/预览、重复检测各有两套路径。

**期望行为**：只剩 refs 一条链；老路径无残留调用；付款凭证等非单据来源也走 refs；多产品归属可预期。

## 3）范围：分 5 步，每步可独立交付

### S1 付款凭证纳入 refs（新增来源）
- 后端 `AttachmentSourcePolicy.java`：`SOURCES` 增 `purchase_payment` —— 权限前缀 `purchase:payment`、来源单号 SQL 取 `purchase_payment.payment_no`（按该表实际软删列写条件）。
- 前端 `jjx-web/src/enums/system/AttachmentEnum.ts`：`ATTACHMENT_SOURCE_PERMISSION` 加 `purchase_payment: 'purchase:payment'`；`ATTACHMENT_SOURCE_CODE` 加短码 **`PAY`**。
- 前端 `jjx-web/src/views/purchase/payment/index.vue`：`:594` 列表、`:607` 上传、`:625` 删除 → 全部换 refs（上传走附件中心 TEMP→绑定；删除改**解除引用**）。
- 权限点已存在（`purchase:payment:view` / `:edit`，menu 172/174）——**不需要建菜单权限**。
- 验收：能传、能看、能解除引用；不再出现"传上去看不到"。

### S2 产品详情「业务流转附件」改读 refs
- 后端 `ProductServiceImpl.getBizAttachments` 改按 refs 聚合（可复用现有 `AttachmentRefService.product(productId)` 的语义）。
- 前端 `ProductDetail.vue:342-354` 的取数随之调整（字段名以 refs VO 为准）。
- 验收：询价/报价/订单里新传的附件，在产品详情能看到。

### S3 质量档案 / 状态流转弹窗换组件
- `views/production/quality-archive/index.vue:103`、`components/BizFlowDetail/index.vue:52` 的 `AttachmentPanel`（老通道）→ 改挂 `AttachmentCenter`（只读或编辑按原语义）。
- `AttachmentPanel/index.vue` 在无调用方后可删除（**删前先确认无引用**）。
- 验收：两处显示的附件与单据侧一致。

### S4 老路径退役清理（**放最后做**，等 S1—S3 没有调用点）
- 老下载/预览：`SysAttachmentController` 的按 id 下载/预览 → 统一走 `/refs/{refId}/download|preview`。
- 老重复检测：前端 `attachmentApi.bySha256` → `attachmentRefApi.refsBySha256`。
- 老上传：`/upload`、`/upload-product` 的业务调用点清零（产品侧留 041）。
- 真删：`attachmentApi.remove` / `/permanent/{id}` 不再由业务模块直接调用；收敛到一个受控管理入口（权限位明确）。
- 验收：全仓检索这些老 API/路径**无业务调用残留**（`grep` 证据贴进 remark）。

### S5 多产品选产品（P3 落地）
- `AttachmentCenter.vue` + `useAttachmentRefs.ts`：上传/绑定时可带 `product_id`（单产品单据已有 `productId` prop；多产品需**选产品下拉**，选项=本单明细产品，可留空）。
- 回填：多产品单据**只回填用户显式选了产品的行**，禁止统一回填。
- 验收：同一张报价单的附件可分别挂到不同产品；未选的为整单级。

**建议顺序**：S1 → S2 → S3 → **S5** → S4。

## 4）约束

1）不动 refs 唯一性与绑定语义、不动落库口径。
2）**权限不得弱化**：保留"TEMP/ORPHAN 仅上传人可读且未过期"与"有 ref 且来源可读即放行"；`AttachmentAccessService` 的老字段兜底分支**只有在"无 ref 附件"全部纳入 refs 后**才可删。
3）产品侧（产品文件库/工程图集/归档）**不在本卡**。
4）多产品**留空 = 整单级**是合法状态，不要强制必选。
5）不改权限模型、不加菜单权限（本卡所需权限点都已存在）。

## 5）验收

**行为**
1）单据侧附件只有 refs 一条链；老字段不再写、老查询无业务调用。
2）付款凭证走 refs（`purchase_payment`），上传/查看/解除引用正常，权限按 `purchase:payment:view/edit`。
3）老下载/预览、老重复检测路径退役后**无残留调用**（贴 grep 证据）。
4）多产品：选了的行 `product_id` 正确，未选的为空；保存不会把整单附件统一指向同一产品。
