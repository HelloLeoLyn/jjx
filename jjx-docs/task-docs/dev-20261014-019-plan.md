## 0）一屏速览

**一句话**：工程图纸的**结构化元数据**（图种 / 图纸编号 / 图纸名称 / 版本 / 原稿-打印件）现在只存在 `sys_attachment` 的列上，公共附件链路（temp 上传 → 建 `sys_attachment_ref`）**不写这些列**；本卡让后端支持它，才能把图纸迁入公共组件而不丢字段。

## 1）现状与证据（2026-10-14 只读核对）

- `sys_attachment` 列含：`version` / `drawing_no` / `drawing_name` / `file_role` / `category` / `is_current` / `is_controlled` / `released` 等（图纸元数据在这里）。
- `sys_attachment_ref` 列只有：`product_id` / `product_code` / `document_type` / `display_name` / `remark` / `sort_order`（**无任何图纸列**）。
- 老写：`EngineeringDrawingLibrary.vue:246` → `attachmentApi.uploadProductFile(file, code, category, version, { drawingNo, drawingName, version, fileRole })` → 老接口 `/system/attachment/upload-product`（写上面那些列）。
- 图纸库依赖这些列做：图种分类 tab、图纸/版本分组、原稿 vs 打印件唯一性、`updateDrawingMetadata` 元数据编辑（`PUT /system/attachment/{id}/drawing-metadata`）。
- 公共路径：`AttachmentCenter` → `useAttachmentRefs`（temp 上传 → `sys_attachment`，建 ref）→ **不带也不写图纸列**。

## 2）候选方案

- **A）引用表加图纸列**：`sys_attachment_ref` 增 `drawing_no/drawing_name/version/file_role/...` → 迁移 + 改 `AttachmentRefService`/列表接口。图纸是"附件属性"而非"引用属性"，放引用表语义略歪，且老读取仍看 `sys_attachment`。
- **B）保留 `sys_attachment` 列，扩公共上传/建 ref 让其能写这些列**（推荐）：在公共上传/绑定 DTO 增加可选的图纸元数据，落库仍写 `sys_attachment` 既有列；图纸库读取口径不变。
- **C）独立图纸元数据表**（`product_drawing_meta` 关联 ref）：最灵活最重，除非要版本化受控管理，暂不必。

**推荐 B**（改动最小、保住既有图纸库读列口径、不新增表）。

## 3）验收

图纸经公共组件（`AttachmentCenter`）上传后：图种 / 编号 / 名称 / 版本 / 原稿-打印件 能写、能读，图纸库的分类分组、同图纸同版本唯一性、元数据编辑均不受影响；`sys_attachment_ref` 里也有该产品的引用行（产品维度可见）。

## 4）交付与回写

- 回写：开工 `status=1`+`start_time`+`assignee_name`；完工 `status=2`+`completed_time`+`remark`；聊天六行模板。

## 决策（2026-10-14 逐项讨论定，用户拍板）

- 图纸元数据口径选 **B**：**保留 `sys_attachment` 既有图纸列**（图种/编号/名称/版本/原稿-打印件），扩公共上传与建引用链路让其能写这些列；图纸库现有读列口径不变。
