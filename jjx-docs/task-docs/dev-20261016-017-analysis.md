## 背景与结论

同一内容在不同草稿或单据重复上传时，各建一条 sys_attachment 并保存独立物理文件；同草稿内按幂等键复用。现状符合 reference/attachment-refactor-decisions-dev-20261016-001.md §8，是 P3 存储优化项。

建议暂不直接给 sys_attachment.sha256 增加全局唯一约束。后续确需去重时，保留每次上传的文件记录、草稿引用与业务身份，另设内容存储层共享物理字节；该方向尚未批准实施。

## 现状证据

1）前端 jjx-web/src/composables/useAttachmentRefs.ts:322：buildRequestKey 使用 SHA-256(draftKey|内容哈希)，浏览器不可计算哈希时采用备用算法。同用户、同草稿、同内容的稳定幂等以可计算内容哈希为前提。
2）后端 jjx-server/src/main/java/com/jjx/system/service/AttachmentLifecycleService.java:67：上传键加入用户身份，按 upload_key 查已有行；新键写入 attachment-temp/UUID.bin，再建立文件和草稿引用。服务端自行计算内容哈希，不信任客户端哈希。
3）AttachmentAccessService.java:30：TEMP/ORPHAN 读取受单个 upload_owner 和 expires_at 限制；文件行还包含图号、版本、受控和下发标记。直接合并文件行会牵连不同上传的权限及业务生命周期。
4）AttachmentLifecycleService.java:383：回收判定检查有效引用、历史保护、保留期及共享路径。多行共用路径会命中 SHARED_PATH_REVIEW_REQUIRED，不能仅改 file_path 实现完整去重与回收。
5）备份结构中 upload_key 唯一，sha256 是普通组合索引；现有设计没有内容全局唯一约束。
