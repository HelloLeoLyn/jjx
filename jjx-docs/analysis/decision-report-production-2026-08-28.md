# 生产报工剩余决策项（一页纸，2026-08-28）

> 供生产管理拍板。每项给出：现状 / 选项 / 推荐。已实现代码不涉及，
> 拍板后由 Codex 实施。

## 1. 审批漏斗矩阵（dev-20260827-011，P3）

现状：报工审批人 = 直接父任务执行人；First Task 的 assignee 恒为 NULL
（无代码为其赋值），因此其直接子任务（深度2）的报工只能生产管理
（production:all）审批。一层派工模式（管理者直接派给工人）下，全部报工
压向生产管理岗；多层派工（管理者→组长→工人）由组长批。

选项：
  A. 首次派工强制 First Task 挂 assignee（=生产管理者本人），深度2 报工
     由管理者本人批 → 每层都有明确上级审批人，树完整。代价：派工多一步。
  B. 未分配时审批人放宽为工单负责人/工序创建人 → 审批分散。代价：权限
     语义变复杂。
  C. 保持现状 + 文档化审批矩阵（深度2=生产管理批，深度3+=直接父任务
     执行人批）。代价：管理岗审批量可能大。

推荐：C 短期（零改动）+ A 中期。现场是 3 层树（管理者→组长→工人），
若一层派工场景多、管理岗审批量大，再上 A。

## 2. 全不良"完成任务"语义（dev-20260827-016，P2）

现状：任务完成量 = SUM(APPROVED 报工的合格+不良)，100% 不良也能数学上
"完成任务"→ 工序完成 → FQC FAIL 打回 EXECUTING 返工。"任务已完成"状态
在 FQC 判定前失真（看板显示已完成，实际在返工）。

选项：
  A. 任务完成 gate 要求合格量>0（或合格率下限）→ 全不良不能"完成"，
     语义真实。代价：若返工链路不完整，任务会"永远完不成"的死锁风险。
  B. 保持现状 + 文档化：任务完成 = FQC 前置阶段完成，最终以 FQC 为准。
  C. 看板/列表对"已完成但 FQC 未过/返工中"的任务加标记。

推荐：B + C。现状流程其实闭环（全不良→完成→FQC FAIL→打回复工），
语义靠 FQC 兜底；加标记解决展示失真即可，A 有死锁风险。

## 3. 审批人快照（dev-20260827-017，P3，随 011 一起定）

现状：审批人在审批时点动态查 parent.assignee；报工提交后任务被收回/换人
→ 审批关系漂移（原上级批不了，只剩生产管理能批）；报工表无"提交时点应
审批人"快照。

选项：
  A. production_work_report 加 pending_reviewer_id/name 快照（提交时写），
     审批 gate 优先用快照 → 关系稳定。代价：加字段+提交时多一次父任务查询。
  B. 保持动态计算 + 文档化漂移规则。
  C. 收回/换人时联动处理其 PENDING 报工（提示/转批）。

推荐：A（成本低，提交时本来就要查父任务）。若 011 选 A（强制挂人），
快照价值降低；若 011 保持现状，快照值得做。

## 4. 代报通道（dev-20260827-019，P3）

现状：提交人硬绑定 = 任务执行人（WorkReportActionServiceImpl:85），组长
代报、管理员代报均被拒。安全上干净，但请假/混线/班组协作场景不便。

选项：
  A. 保持禁止 + 文档化。
  B. 加代报权限位 production:work-report:proxy + 双人快照（reporter=事实
     报工人，proxy=代操作人）→ 审计清晰。
  C. 仅管理员可代报。

推荐：B（制造业常态场景，双人快照审计完整）；团队小无需求则选 A。
