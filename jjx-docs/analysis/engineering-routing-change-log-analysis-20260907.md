# 工程管理工艺路线流水缺口核查与改造方案

> 核查日期：2026-09-07  
> 核查范围：工程管理 / 工艺路线列表、详情、编辑、操作流水  
> 本文仅记录分析与实施方案，不包含代码改动。

## 一、问题结论

当前问题由两个相互独立的缺口造成：

1. 工艺路线列表没有流水入口，是前端入口设计遗漏；流水入口目前只放在详情弹窗底部。
2. 编辑流水没有内容变更，是后端编辑日志只记录了“执行编辑”，没有生成并写入字段级 `detail.changes`。

此外，自动升版编辑还存在流水归属问题：更新接口可能生成新的工艺路线 ID，但日志仍按请求中的旧路线 ID 记录。

## 二、现状与根因

### 2.1 列表页没有流水入口

工艺路线详情弹窗 `RouteDetailDialog.vue` 已经接入通用 `TraceTimeline`，查询条件为：

- `bizType = routing`
- `bizId = routingId`

工艺路线列表 `index.vue` 只负责打开详情弹窗，没有直接打开流水的行级操作。因此用户必须依次进入“查看详情 → 流水”，列表中无法直接查看。

后端已经支持按 `bizType + bizId` 查询业务对象流水，此问题不需要新增流水查询接口。

### 2.2 编辑日志没有字段差异

`EngineeringRoutingController.update()` 上的 `@Log` 已配置模块、动作、业务类型和业务 ID，但没有配置 `detail`：

```java
@Log(
    module = "工艺路线管理",
    businessType = BusinessType.UPDATE,
    bizType = "'routing'",
    bizId = "#routingId",
    action = LogActions.ROUTING_EDIT
)
```

`EngineeringRoutingServiceImpl.updateRouting()` 返回普通 `EngineeringRoutingVO`，返回结果中也没有可供日志切面读取的 `detailMessage`。

通用流水组件只会从日志 `detail` 中解析如下结构：

```json
{
  "changes": [],
  "attachments": []
}
```

因此系统能够显示“工艺路线编辑”这一操作，但无法显示修改前后的内容。

### 2.3 当前明细保存方式无法直接产生可靠差异

工艺路线更新采用以下方式：

1. 更新路线主表；
2. 删除该路线原有全部工序明细；
3. 按前端提交内容重新插入全部工序；
4. 重新计算总工时和工序数。

数据库层面看到的是“全部删除、全部新增”，并不能表达用户实际执行的是新增一道工序、调整顺序或修改工时。因此必须在删除原明细之前读取完整旧快照，再与请求中的新内容进行业务级比较。

### 2.4 自动升版的流水归属不正确

当 `bumpVersion=true` 时，`updateRouting()` 会创建一个新的工艺路线版本并返回新的 `routingId`。但是控制器日志的 `bizId` 固定取路径参数 `#routingId`，也就是旧版本 ID。

这会造成：

- 新版本详情中看不到本次升版创建流水；
- 编辑或升版动作被记录到旧版本；
- 流水无法清楚表达旧版本与新版本的继承关系。

## 三、改造方案

### 3.1 在列表增加流水入口

在工艺路线列表操作区增加“流水”按钮，直接打开现有 `TraceTimeline`：

- `bizType` 固定使用 `routing`；
- `bizId` 使用当前行 `routingId`；
- 与详情弹窗复用同一组件和同一查询口径；
- 详情弹窗原有流水入口继续保留。

### 3.2 增加工艺路线编辑结果对象

建议新增专用编辑结果 VO，而不是给通用路线详情 VO 混入日志职责：

```java
public class EngineeringRoutingEditVO {
    private EngineeringRoutingVO routing;
    private String detailMessage;
    private Long oldRoutingId;
    private Long effectiveRoutingId;
}
```

其中：

- 普通编辑：`oldRoutingId` 与 `effectiveRoutingId` 相同；
- 自动升版：`oldRoutingId` 为原版本，`effectiveRoutingId` 为新版本。

控制器日志通过返回结果读取 `detailMessage` 和实际生效的路线 ID。

### 3.3 生成主表字段差异

建议至少记录：

- 路线名称；
- 所属产品；
- 路线版本；
- 描述；
- 备注；
- 是否当前版本；
- 总人工工时、总机器工时和工序数的最终变化。

流水内容使用业务名称和格式化后的值，不展示 Java 属性名或数据库字段名。

### 3.4 生成工序明细差异

建议覆盖：

- 新增工序；
- 删除工序；
- 工序顺序调整；
- 工序名称或类别变化；
- 标准工时、自定义人工工时、机器工时变化；
- 工艺参数变化；
- 设备、车间、描述等变化；
- 组合工序中子作业的新增、删除、修改和排序。

示例：

```text
工序顺序：印刷 2 → 3
新增工序：冲型
丝印人工工时：1.5 → 2.0 小时
丝印工艺参数：网版 300目 → 350目
删除子作业：外观检查
```

### 3.5 工序匹配规则

当前保存会重建工序明细，`itemId` 不稳定，不能作为差异比较的唯一键。

本次建议采用：

1. 父工序优先按稳定业务标识 `processId` 匹配；
2. 同一 `processId` 重复出现时，按出现序号辅助匹配；
3. 子作业按父工序、子作业 `processId` 或名称、出现序号匹配；
4. 顺序变化单独记录，不能误判为删除后新增；
5. 对无法可靠匹配的明细，明确记录为删除和新增，不生成错误的字段修改信息。

长期方案是为路线工序增加编辑时保持稳定的业务 UUID，但不作为本次改造的前置条件。

### 3.6 自动升版流水

推荐自动升版时生成两条关联流水：

- 旧版本记录：`工艺路线升版 V1.0 → V2.0`，包含新版本 ID；
- 新版本记录：`由 V1.0 创建 V2.0`，包含完整内容变更及旧版本 ID。

这样从旧版本可以找到去向，从新版本可以追溯来源。普通编辑仍只记录当前路线一条流水。

如果现有 `@Log` 切面不适合在一次请求中写入两个业务 ID，应在事务成功后使用统一日志记录服务按顺序写入两条日志，避免日志先于业务事务提交。

### 3.7 补齐其他动作的流水内容

建议同批补齐：

- 创建：路线基本信息与初始工序摘要；
- 复制版本：源版本、新版本及复制工序数；
- 设置当前版本：原当前版本 → 新当前版本；
- 提交审批：草稿 → 待审批；
- 审批通过/驳回：状态变化和审批意见；
- 删除：删除前的路线编码、版本和工序摘要。

状态展示和比较必须复用现有审批状态枚举，不新增数字或字符串状态魔法值。

## 四、实施顺序

1. 定义工艺路线变更字段字典和格式化规则；
2. 实现主表及工序树的旧、新快照比较器；
3. 调整编辑服务返回编辑结果及 `detailMessage`；
4. 修正普通编辑和自动升版的流水业务 ID；
5. 在列表增加复用型流水入口；
6. 补齐创建、复制、当前版本和审批动作的流水内容；
7. 增加后端差异单元测试和前端入口验证；
8. 运行状态枚举检查、前端类型检查及后端相关测试。

## 五、验收与测试范围

至少覆盖以下场景：

1. 单独修改路线主表字段；
2. 新增、删除、修改和排序父工序；
3. 新增、删除、修改和排序组合工序子作业；
4. 同一标准工序重复出现时差异匹配正确；
5. 修改工时、工艺参数、设备和描述；
6. 无实际变化时不展示空的“内容变更”；
7. 普通编辑流水归属当前路线 ID；
8. 自动升版的旧、新版本均能相互追溯；
9. 列表和详情打开的是同一份流水；
10. 历史日志没有 `detail` 时仍能兼容展示；
11. 编辑事务回滚时不留下成功流水；
12. `npm run check:status-enums` 和前端类型检查通过。

## 六、历史数据说明

历史编辑日志没有保存修改前后的快照，无法可靠反推出字段差异。因此本方案只保证改造上线后的编辑操作产生完整内容变更；历史流水继续展示动作、操作人和时间，不伪造历史差异。

## 七、待业务确认

自动升版流水有两种选择：

1. **推荐方案：旧版本和新版本各写一条关联流水。** 双向可追溯，符合版本管理语义。
2. 简化方案：只在新版本记录升版流水。实现成本略低，但从旧版本无法直接看到升版去向。

除该项外，列表增加流水入口、记录路线主表及工序明细差异，当前没有业务歧义，可按本方案实施。
