# 质量模块统一口径与历史追溯分析建议报告

> 日期：2026-09-28  
> 类型：只读分析与治理建议  
> 状态：未实施，不改业务逻辑、不改数据、不新增数据库表  
> 核查范围：质量检验批、检验项目、不良台账、处置、返工复检、件级追溯、报废凭据、库存关联及对应前端页面

## 1. 执行摘要

当前质量模块并非单一的“检验页面问题”，而是已经形成了多个并行口径：

~~~text
检验批 quality_lot
    ├─ 检验项目 quality_lot_item
    ├─ 不良台账 quality_ncr
    │    ├─ 处置动作 quality_ncr_action
    │    ├─ 不良件 quality_ncr_piece
    │    └─ CAPA quality_capa
    ├─ 报废凭据 quality_scrap_order / 来料侧独立报废单
    └─ 库存流水 inventory_transaction
~~~

主要问题不是表数量本身，而是：

1. 同一数量在检验批、不良台账、处置动作、库存流水中重复表达。
2. 当前状态、历史事实、单次事件经常被页面并列展示。
3. 复检批的“整批替代”和“局部追加”语义依赖服务代码推导，数据结构不够直观。
4. IQC、IPQC、FQC 共享部分模型，但入口、数量计算、来源关联和页面展示仍然分散。
5. 检验判定和检验项目存在覆盖/重写路径，历史不能完整恢复。
6. 前端存在多套 DTO 映射和本地计算，页面之间容易出现不同口径。

建议的总方向是：

> 第一阶段不新增表。以现有表为事实来源，建立统一的质量追溯读模型和数量口径层；前端统一消费该读模型。只有确认现有表无法恢复判定变更、重开、复检和撤销历史后，才评估追加 append-only 质量事件表。

## 2. 核查方法与边界

本次为代码和结构只读核查，未执行数据库写入、迁移、服务重启或业务数据修复。

重点查看：

- jjx-server/src/main/java/com/jjx/quality/domain/entity/
- jjx-server/src/main/java/com/jjx/quality/service/
- jjx-server/src/main/java/com/jjx/quality/controller/
- jjx-web/src/views/quality/
- jjx-web/src/views/inventory/iqc/
- jjx-web/src/api/quality/

## 3. 当前模型盘点

### 3.1 检验批：当前的统一主模型

quality_lot 的注释已经定义了质量数量恒等式：

~~~text
lot_quantity = inspected_quantity + 待检余量
inspected_quantity = pass_quantity + fail_quantity
fail_quantity = disposed_quantity + 待处置
stored_quantity <= lot_quantity
~~~

证据：QualityLot.java 第 15-19 行及第 56-67 行。

字段职责意图是：

| 字段 | 当前意图 | 风险 |
|---|---|---|
| lotQuantity | 本批应检总量 | 有时页面称“批量/收货数量”，需要区分来源批与复检批 |
| inspectedQuantity | 已检数量 | 可被重新判定覆盖 |
| passQuantity | 合格数量 | 既有检验结果，也可能参与库存/有效 FQC 汇总 |
| failQuantity | 不良数量 | 又被 NCR 复制一份 |
| storedQuantity | 已入库/已放行 | 与库存流水存在派生关系，但不是库存真源 |
| disposedQuantity | 已处置不良数量 | 与 NCR 的同名字段重复 |
| parentLotId | 复检来源批 | 只能表达父子关系，不能单独表达替代/追加语义 |

### 3.2 检验项目：当前结果可被覆盖

quality_lot_item 保存检验项目、实测值、CR/MA/MI 和项目结论。当前保存逻辑是先删除该批原有项目，再插入本次项目。

这意味着：

- 当前结果可查询；
- 历史录入过程无法从表中完整恢复；
- 判定之前修改检验项目，不会自然形成一条版本历史；
- 页面显示“当前检验项目”，不能称为“历史检验记录”。

### 3.3 不良台账：第二套数量汇总

quality_ncr 保存：

- defectQuantity
- CR/MA/MI 数量
- disposedQuantity
- status
- 结构化主缺陷与补充原因

其 pendingQuantity() 是：

~~~text
defectQuantity - disposedQuantity
~~~

这本身是合理的派生关系，但 disposedQuantity 又在 NCR 表中持久化，因此它不是单纯查询计算值。

### 3.4 处置动作：最接近事件，但仍可变

quality_ncr_action 保存：

- 处置类型：返工、让步接收、报废；
- 本次数量；
- 状态；
- 返工执行单；
- 复检批；
- 审批与客户确认信息；
- 操作人、时间、备注。

它是当前质量模块中最接近“事件流水”的表，但仍存在：

- 状态被更新为 PROCESSING、DONE、VOID；
- 撤销通过更新原动作实现；
- 返工完成、复检生成和动作闭环之间跨多个服务更新；
- 处置动作与 NCR/检验批汇总需要同步维护。

因此它可以作为处置历史的主来源，但不能单独代表完整质量历史。

### 3.5 不良件：身份追溯，不参与库存

quality_ncr_piece 已明确规定：

- 一物一号；
- 一件一个处置决定；
- 一件可有多条缺陷记录；
- 不参与库存数量计算。

这条边界是正确的，应该保留。它适合回答“哪几件、每件为何不良、每件怎么处置”，不适合被页面当作库存结存来源。

### 3.6 报废凭据：存在业务分叉

质量模块有 quality_scrap_order，来料侧还有独立的来料报废凭据链。成品报废单的注释明确写了“库存不受影响”，来料侧则有自己的 IQC 处置和库存边界。

这不一定需要合并成一张表，但必须统一上层语义：

~~~text
报废单 = 实物/审批凭据
处置动作 = 质量处置事件
库存流水 = 库存变化事实
~~~

三者不能互相冒充。

## 4. 关键问题与证据

### 4.1 P1：检验批与 NCR 各自持有“已处置数量”

处置登记时，服务先更新 NCR 的 disposedQuantity，再调用检验批服务更新检验批的 disposedQuantity。

证据：QualityNcrServiceImpl 的处置路径同时执行：

~~~text
ncr.setDisposedQuantity(...)
ncrMapper.updateById(ncr)
qualityLotService.addDisposedQuantity(ncr.getLotId(), quantity)
~~~

风险：

- 任一异常路径漏同步，两个余额立即分叉；
- 撤销处置时还要反向回写两个汇总；
- 页面若分别读取两个字段，会得到不同的“已处置/待处置”；
- 汇总字段不是流水重算结果，而是写路径维护结果。

### 4.2 P1：判定数量是覆盖式快照，不是历史事件

applyJudgement() 直接覆盖：

~~~text
inspectedQuantity
passQuantity
failQuantity
result
status
~~~

证据：QualityLotServiceImpl 第 506-513 行。

虽然复检会创建子批，但“重开后重新判定”仍然会在当前批上覆盖结果。历史只能依赖备注、更新时间或外部操作日志，无法保证恢复完整的数量版本。

### 4.3 P1：检验项目历史被删除重建

保存检验项目时使用删除后插入策略。结果是：

- 无法比较第 1 次和第 2 次检验项目结果；
- 无法知道 CR/MA/MI 是何时变化的；
- NCR 形成前后的项目结果不一定能还原；
- 页面显示的“检验项目”实际是当前版本快照。

### 4.4 P1：复检存在“替代”和“追加”两种不同语义

当前系统同时支持：

1. 整批复检：新版本替代旧版本，不再按旧版本计账；
2. 返工局部复检：子批只针对返工数量，合格结果追加回有效产出。

这两种模式不能只靠 parentLotId 表达。必须额外明确：

~~~text
relationshipMode = REPLACE | INCREMENT
scopeQuantity = 本次复检覆盖量
effectiveQuantity = 对父批有效数量的影响
~~~

如果不在统一读模型中输出这些语义，页面只能依赖各处服务代码推断。

### 4.5 P1：质量页面各自拼装数据

当前至少存在：

- IQC 独立明细页；
- 通用质量检验批工作台；
- 产品不良台账；
- 来料不合格处置；
- 报废单；
- 检验打印页；
- CAPA 页面。

这些页面使用不同的 API DTO 和本地字段映射。例如同一质量批在前端存在 QualityLot、QualityVO、IQC WorkRow 等转换模型。

直接后果：

- 同一字段在不同页面叫法不同；
- 某页面显示当前余额，另一个页面显示原始结果；
- 复检关系只在部分页面可见；
- “已处置”“待处置”“已入库”计算规则可能分叉。

### 4.6 P2：状态值和结果值存在跨层分散

质量域同时存在：

- pending/pass/fail/concession 结果；
- PENDING/INSPECTING/JUDGED/CLOSED 批状态；
- DRAFT/PENDING/APPROVED/REJECTED IQC 复核状态；
- PENDING/PROCESSING/DONE/VOID 处置状态。

部分字段由枚举管理，部分代码和页面仍直接比较字符串。历史上已经出现大小写不一致导致判定、报表或提交校验错误的记录。

建议把“结果”“生命周期状态”“允许动作”“处置状态”严格拆开，页面只消费后端下发的允许动作和统一标签。

### 4.7 P2：来源关系丰富但没有统一展示契约

检验批可以来自：

- INBOUND_ITEM
- WORK_REPORT
- EXECUTION
- 返工执行
- 销售/出货等来源

实体中已有 sourceType、sourceId、sourceItemId、orderId、executionId、sourceNo、orderNo、salesOrderNo 等字段，但页面仍有“来源 #内部ID”“批 #内部ID”或来源缺省的问题。

用户真正需要的是：

~~~text
来源业务单号 + 来源类型 + 材料/产品 + 工序/报工 + 批号
~~~

内部 ID 只能作为详情辅助定位，不能作为主展示。

## 5. 统一数量口径建议

### 5.1 数量分类

所有质量页面的数量应先归入以下五类之一：

| 类别 | 定义 | 来源建议 |
|---|---|---|
| 原始事实 | 某次检验/收货/判定当时产生的数量 | 检验批或检验事件 |
| 单次事件 | 某一次处置、复检、放行、撤销的数量 | 处置动作/复检关系/库存流水 |
| 当前派生 | 截至当前时点的余额 | 由事实聚合，不由前端猜 |
| 有效汇总 | 跨批次谱系折算后的有效产出 | 统一谱系策略 |
| 库存数量 | 实际进入库存引擎的数量 | inventory_transaction |

### 5.2 页面固定展示层次

不要把所有数字放在同一行。统一为：

~~~text
原始检验
  本批应检 / 已检 / 合格 / 不良

处置履历
  时间 / 处置类型 / 本次数量 / 状态 / 来源不良单 / 关联执行或复检批

复检谱系
  原批 → 子批 / 替代还是追加 / 本次覆盖或追加数量

当前余额
  当前待处置 / 当前已入库 / 当前有效合格 / 截至时间

库存影响
  收入 / 发出 / 调整 / 结存，全部来自库存流水
~~~

### 5.3 禁止前端推导的数量

前端禁止自行计算或猜测：

- 已处置 = 不良 - 剩余；
- 复检数量 = 父批不良；
- 有效合格 = 所有子批合格简单相加；
- 已入库 = 合格数量；
- 库存结存 = 业务单据数量。

这些计算必须由后端统一服务或数据库查询层完成，并同时返回口径说明和截至时间。

## 6. 建议的目标结构

### 6.1 第一阶段：不新增表，建立统一读模型

建议增加质量域只读聚合服务，例如 QualityTraceQueryService，输出统一 QualityTraceVO。它不是新的业务真源，只是现有表的规范化读取层。

建议结构：

~~~text
QualityTraceVO
├── source                 来源单据、材料/产品、工序、批号
├── lot                    当前检验批及原始检验结果
├── lotLineage             父批、子批、替代/追加关系
├── inspectionVersions     可恢复的现有版本/当前快照
├── ncrs                   关联不良台账
├── actions                处置动作流水
├── pieces                 件级追溯摘要
├── stockEffects           库存流水摘要
├── currentBalances        当前派生余额
└── consistency            发现的跨表不一致
~~~

该服务首先只读，不改变既有写入逻辑。目标是让 IQC、FQC、IPQC、NCR、报废、打印页面先拥有同一个展示口径。

### 6.2 第二阶段：统一写路径和数量投影

把所有写入收敛到少数几个领域动作：

~~~text
recordInspectionResult()
createNcrFromInspection()
createDispositionAction()
completeDispositionAction()
revokeDispositionAction()
createReinspectionLot()
applyInventoryEffect()
~~~

每个动作必须明确：

- 输入数量的口径；
- 影响哪些事实；
- 是否产生库存流水；
- 是否允许撤销；
- 如何回算当前余额；
- 如何与父批/子批关联。

### 6.3 第三阶段：只在确有缺口时增加事件表

若通过第一、二阶段核查发现以下历史无法恢复，再考虑新增 append-only 事件表：

- 同一检验批多次判定的完整版本；
- 检验项目变更前后值；
- 重开原因与重开前状态；
- 复检替代/追加决策；
- 非处置类质量状态变更。

新表若确实需要，应只记录事件，不再复制当前余额。建议事件形态：

~~~text
event_id
aggregate_type
aggregate_id
event_type
quantity_snapshot
before_snapshot
after_snapshot
source_document
operator
occurred_at
reason
~~~

但这不是第一步，也不应在没有完成现有数据盘点前直接创建。

## 7. 分阶段实施建议

### 阶段 0：冻结口径和范围

产出：

- 质量模块数量字典；
- IQC/IPQC/FQC 生命周期矩阵；
- 复检替代/追加规则；
- 处置类型与库存影响矩阵；
- 页面和 API 责任边界。

不改代码、不改数据。

### 阶段 1：建立只读一致性核查

检查：

- quality_lot.fail_quantity 与 NCR 不良总量；
- quality_lot.disposed_quantity 与有效处置动作总量；
- NCR 已处置量与有效处置动作总量；
- 复检子批数量与返工动作数量；
- 有效 FQC 汇总与库存入库流水；
- 库存批次结存与库存流水派生结存。

输出只读问题清单，不自动修数据。

### 阶段 2：统一 QualityTrace 读模型

范围：

- 后端聚合查询；
- IQC 详情；
- 通用质量批详情；
- NCR 详情/处置详情；
- 报废详情；
- 打印详情。

先统一读，不改变写路径。

### 阶段 3：统一写路径和反向动作

重点：

- 处置动作只能通过领域服务落账；
- 撤销必须有反向动作或明确限制；
- 检验项目保存不再无审计地覆盖；
- 复检生成明确记录替代/追加语义；
- 所有库存影响必须进入库存流水。

### 阶段 4：历史补强

仅针对阶段 1、2 证明无法恢复的历史缺口，选择：

- 补充事件表；
- 增加版本表；
- 或对旧数据标记“历史不可完全恢复”，避免伪造历史。

## 8. 修改范围估算

| 方案 | 预计范围 | 说明 |
|---|---:|---|
| 页面止血 | 3-8 个前端文件 | 只改文案和展示，不能解决历史问题 |
| 统一读模型 | 10-25 个前后端文件 | 复用现有表，不新增业务表，建议优先做 |
| 写路径收敛 | 20-40 个前后端文件 | 涉及 IQC/FQC/NCR/库存/返工联动 |
| 完整历史治理 | 另行评估 | 可能涉及迁移、历史标记、专项回归和数据修复 |

不建议一次性“大爆炸式重构”。建议以统一读模型为中间层，逐页迁移，旧接口保留一段过渡期并增加对账。

## 9. 验收标准

### 9.1 数量验收

- 任一页面能区分原始检验数量、单次处置数量、当前余额和库存数量。
- 页面不再由前端自行推导已处置、有效合格或库存结存。
- 所有余额能通过既定事实重算。
- 同一批在 IQC、质量批、NCR、报废、打印页面显示一致。

### 9.2 历史验收

- 能查看处置动作时间、数量、操作人、状态和撤销关系。
- 能区分原批、复检批、整批替代和局部追加。
- 判定重开、复检、处置撤销不会伪装成原始历史数据。
- 无法恢复的旧数据明确标记，不用当前快照冒充历史。

### 9.3 追溯验收

~~~text
采购订单
 → 入库单/入库行
 → IQC 检验批
 → NCR
 → 处置动作
 → 返工执行/报废凭据/让步接收
 → 复检批
 → 库存流水/成品批次
~~~

每个箭头都必须有明确 ID、业务单号和数量口径。

### 9.4 工程验收

- 前端 vue-tsc --noEmit 通过；
- 后端编译和质量域定向测试通过；
- npm run check:status-enums 通过；
- npm run check:iqc-lineage:strict 和库存严格巡检通过；
- 新增读模型必须有跨表一致性测试；
- 不启动、不重启服务作为自动化验收步骤，运行态验证由用户授权后单独执行。

## 10. 当前不建议做的事情

1. 不要再为“剩余数量”“复检数量”“历史数量”各新增一张汇总表。
2. 不要在前端通过减法推导处置余额。
3. 不要把 quality_lot 的当前字段直接称为历史记录。
4. 不要把 quality_ncr_action、报废单、库存流水混成同一种单据。
5. 不要一次性重写 IQC、FQC、IPQC、NCR 全部写路径。
6. 不要先迁移数据再讨论替代/追加语义。

## 11. 待业务确认的决策点

1. 整批复检是否永远替代父批？局部返工复检是否永远追加？是否允许同一父批混用？
2. 让步接收是否计入“合格”、还是独立计入“特采”并单独展示？
3. 返工中的数量在质量模块中属于“待处置”“处理中”还是“已处置但未回收”？
4. 报废、退货、返工、让步接收的库存影响是否固定，还是按来源类型区分？
5. 重开后重新判定，是修改原批版本，还是一定生成新版本？
6. 历史数据缺少事件时，是否接受标记“历史不可完全恢复”，而不是补造事件？

## 12. 最终建议

推荐路径：

~~~text
先冻结口径
  → 做只读一致性巡检
  → 建统一 QualityTrace 读模型
  → 逐页面迁移展示
  → 收敛写路径
  → 最后评估是否需要事件表
~~~

这条路径可以控制修改范围，避免继续堆补丁；同时不会把现有数据直接推倒重建。当前 IQC 页面文案改动可以作为临时止血，但不应作为质量模块最终架构。
