## 0. 复核结论

描述里的**代码事实与推理链逐条成立**（行号已核）。复核补充三点**比原文更严重**的性质：

1. **不是"静默丢第 101 张"，而是「该工单此后持续建不出单」**——每次重算都会撞回同一个 `-FI100`（见 §2 仿真）。
2. **失败对上层完全不可见**：调用方 `QualityFinishServiceImpl:77` 忽略返回值；控制器 `InventoryInboundController:256` 也只 `Result.success(null)`（HTTP 200 + data=null）。没有异常、没有提示，只有一行 `log.warn`。
3. **现有两道门禁都覆盖不到**：八查（`check-inbound-lot-integrity.sh`）没有「有效批是否已有入库单」这一项；`check-doc-no.sh` 只管 `sys_number_sequence` 体系与时间戳式编号，不管**派生号**（`-FI<NN>` 不占号段），而且设计稿里**本该拦住它**的那一项（§131 的「长度/前缀偏离登记表」）**根本没实现**。

> 结论：**成立，P2 合理**（触发门槛 ~100 张/工单，但演示与高频复检场景推进很快——今天一天已经把某工单堆到 8 张）。

## 2. 触发链（等价仿真，完全镜像 Java 逻辑）

用 Python 按 `:2185-2193` 的逻辑逐步模拟（正则 `re.fullmatch` ≈ Java `matches()`；`%02d` ≈ f-string `:02d`）：

```
第   1 次调用: 出单            生成=WO-PL260923001-01-FI01
第   2 次调用: 出单            生成=WO-PL260923001-01-FI02
...
第  99 次调用: 出单            生成=WO-PL260923001-01-FI99
第 100 次调用: 出单            生成=WO-PL260923001-01-FI100     ← 3 位，能出单
第 101 次调用: 重复 → return null  生成=WO-PL260923001-01-FI100   ← 又算成 100，撞车
```

**为什么是"持续"而不是"一次"**：`-FI100` 匹配不上 `-FI\d{2}` → 每次 max 都只看到 99 → 目标恒为 100 → 恒撞 → **该工单之后每一张新批单都建不出来**，除非人工改号/删单。

**现实数据**（2026-09-23 19:5x）：`WO-PL260923001-01` 已有 **12 张**（FI01…FI08 + 5 张 `-R`），**全库最大 FI 序号 = 8** → 距离 100 尚远，但：一张批单 ⇒ +1、每次复检换代 ⇒ 新批 ⇒ +1，**演示/高频场景消耗很快**。
