# 人事管理模块方案

- 日期：2026-09-10
- 状态：**待拍板**（本文只给方案，未动库、未动代码）
- 输入：现有 `sys_user`（42 账号）、`sys_dept`（17 部门）、员工花名册 Excel（52 人 / 11 列）

---

## 1. 现状与问题

| 项 | 现状 |
|---|---|
| 用户表 `sys_user` | 42 行，**基本是岗位占位账号**（印刷一组工人/冲型二组组长/来料检验员…），仅 `admin`（系统管理员）与 `gudy`（林仪增）是真人名 |
| 组织 `sys_dept` | 17 个节点：JJX公司 / 研发部 / 市场部 / 办公室 / 生产中心 / 印刷车间(1-2组) / 冲型车间(1-2组) / 组装车间(1-2组) / 采购部 / 深圳市精捷信科技 / 部门1 |
| 人事数据 | **完全没有**：无员工档案表、无岗位表、无在职状态/工龄/异动 |
| 花名册 Excel | 52 人 × 11 列：姓名/部门/职称/电话/邮箱/进厂日期/身份证号/身份证地址/现在住址/学历/专业/个人履历 |

**结论**：`sys_user` 不是员工名册（它是账号与权限主体）；人事信息无处安放。→ **需要独立的人事模块**。

---

## 2. 设计原则（三条）

1. **员工 ≠ 账号**：员工档案是"人"的主数据；账号是可选的、可共用/可无的登录凭证。关系＝**可选一对一**（`hr_employee.user_id` 可空）。
2. **敏感信息隔离**：身份证号、住址属敏感个人信息。不能塞进被全站高频 join 的 `sys_user`；独立表 + 独立权限 + 展示脱敏。
3. **组织复用**：部门沿用 `sys_dept`，不另建组织树；岗位/学历等枚举走现有 `sys_dict`。

### 3.2 `hr_position` 岗位/职称（新增，替代 Excel 自由文本）
`position_id / position_code / position_name / dept_id(可空) / level / status / 审计列`
> Excel 里"职称"只填了 QC/IPQC 几个；规范化后由字典维护（如 QC / IPQC / IQC / 组长 / 车间主任 / 业务员 / 设计师 / 操作工…）。

### 3.3 `hr_employee_change` 人事异动流水（新增，P1）
`change_id / emp_id / change_type(入职|调岗|转正|离职|复职) / from_dept_id / to_dept_id / from_position_id / to_position_id / effective_date / reason / operator / create_time`
> 与现有 `review_flow` 思路一致：**每次异动一条，历史不覆盖**。

### 3.4 复用（不新建）
- 部门：`sys_dept`
- 枚举：`sys_dict`（学历、婚姻状况、离职原因…）
- 附件：`sys_attachment`（身份证扫描件、劳动合同、照片）
- 审计/追溯：`sys_oper_log` + `@Log` + TraceTimeline
- 编号规则：`biz_no_rule`（工号前缀/位数）

## 4. 功能范围（分三期）

### P0 —— 员工档案（本期建议做）
- 员工档案：分页列表（部门树筛选 / 姓名·工号·手机搜索 / 在职状态过滤）、新增、编辑、离职、详情
- **Excel 导入**：模板下载 → 上传 → **预校验**（部门映射、身份证校验位、手机/身份证查重、日期解析）→ **导入结果报告**（成功 N 条 / 失败 M 条 + 每行原因）
- 导出（Excel）
- 与账号关联：员工详情可"关联/解除系统账号"；开账号时从档案带出姓名/手机/部门
- 敏感字段：默认脱敏（`4415**********0137`），有 `hr:employee:sensitive` 权限才可查看/编辑
- 附件：身份证/合同/照片上传（复用 AttachmentUploader）

### P1 —— 组织与人事运作
- 组织视图：按部门/车间/班组看人员编制与在岗（树 + 人头数）
- 人事异动：入职/调岗/转正/离职登记 + 异动流水时间线
- 工龄/司龄统计（按 hire_date 计算）、在职/离职花名册报表
- 试用期到期提醒（→ 通知/任务，复用事件体系）
- 派工选人联动：候选人员显示"真实姓名 + 岗位 + 班组"（现在候选只有账号昵称）

### P2 —— 考勤与薪酬（**单独立项**，本模块不承诺）
考勤机对接/排班/请假加班 → 工资核算。数据量大、规则复杂，需独立需求与评审。

## 7. 待你拍板的 6 点

1. **目的**：只是存档花名册（→ 不建表，归档即可），还是要在系统里用（派工选人/工龄/通知/后续考勤）？**决定要不要做这个模块。**
2. **部门映射**：§6 的映射表是否认可？「品质部」「仓库」「加工/刀模」要不要新建部门？
3. **工号规则**：如 `JJX` + 4 位流水？还是沿用现有 `biz_no_rule` 配置一套？
4. **敏感字段**：身份证号是否**加密存储**（AES，密钥进配置）？谁能看？
5. **员工与账号**：允许"一个账号对应多个员工"（工位共用）还是严格一对一？
6. **范围**：只做 P0，还是 P0+P1 一起？

## 8. 风险与注意

- **合规**：身份证号、住址属《个人信息保护法》敏感个人信息 → 最小必要采集 + 权限 + 脱敏 + 加密；导出要留痕（`@Log`）。
- **删除策略**：离职员工**不物理删除**（要保留历史与工龄），用 `employment_status=9` + `del_flag`。
- **账号命名冲突**：现 `sys_user` 的岗位占位账号（印刷一组工人…）将来与真实员工并存 → 需要一次清理/映射决策，否则"派工选人"会同时看到占位与真人。
- **导入原子性**：建议逐行独立事务 + 结果报告（不要整批回滚），导入前做表级 guard 备份。
- **工作量**：P0 约「1 张主表 + 1 张岗位表 + 8 接口 + 2 页面 + 导入导出」，属中等规模；P1 再加异动/组织视图/提醒。
