### 2.2 扫码C（设备码防错校验）可行性

- **现状**：`production_operation_execution` 已有 equipment_id / equipment_code / equipment_name；`production_work_report` 带 equipment 快照。设备管理页（EquipmentController）已有 CRUD。
- **实现路径**：
  1. 设备贴牌二维码（内容=设备编号 `EQ-{code}`，复用现有标签打印技术）
  2. 开始工序前扫设备码 → 与 execution.equipment_code 比对
  3. 一致 → 放行开始；不一致 → 拦截（或记录实际设备放行，策略待定）
- **技术风险**：低。无新依赖，前后端各一个页面/接口的事。
- **决策点**：不一致时**硬拦截**还是**记录实际设备放行**？（需 Leo 拍板）

### 2.4 手机摄像头扫码的限制（已知，非阻塞）

- `getUserMedia` 仅 HTTPS/localhost 可用 → 局域网 HTTP 手机开不了摄像头
- **现状兜底**：扫码枪（零配置最稳）+ 手动输入工单号，已跑通
- **进阶**：内网 HTTPS（nginx + mkcert 自签）一次部署解锁手机摄像头实时扫码 + PWA
- **判定**：不阻塞业务，属于"锦上添花"部署项，可后置

### 阶段 2：扫码C 设备码防错校验（核心遗留功能）
- **前置决策**（Leo 拍板）：设备码不一致时 ①硬拦截 ②记录实际设备放行

- 前端：设备贴牌二维码生成（复用标签打印）+ 开始工序扫码步骤（PC 扫码枪 / 手机 H5 两入口）
- 验收：在非指定设备上开始 → 按策略拦截/记录；指定设备 → 正常放行
