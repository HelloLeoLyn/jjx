# JJX ERP 产品作业规范版本与历史追溯设计方案

> 版本：V1.0（业务设计评审稿）  
> 日期：2026-10-11  
> 状态：待确认，非实施指令

## 1. 背景与目标

JJX ERP 已有客供资料、样品单、BOM、工艺路线、刀模、冲型条件参数、冲型备注、印刷工艺、工程图、油墨调和记录、作业规范检测等业务资料。相同产品编码在不同时期可能发生技术变更；历史订单及生产工单必须能还原当时**被批准采用**的完整制造要求，而不能误读当前资料。

本方案目标：

1. 现有业务模块继续维护各自资料，不另建第二套编辑入口。
2. 统一发布产品作业规范版本，固化完整制造依据。
3. 生产订单/工单锁定明确的版本，历史可追溯。
4. 技术变更有原因、有版本差异、有生效范围；已发布版本不可覆盖。
5. 区分“规定使用的规范”和“实际执行记录”，支持未来批次级追溯。

**术语**：本方案在业务界面沿用“产品作业规范”；底层的“规范发布版本”相当于一份不可变的制造资料基线，不代表必须引入独立 PLM 系统。

## 2. 范围与资料职责

| 资料 | 权威维护位置 | 发布时固化内容 | 特别说明 |
|---|---|---|---|
| 客供资料 | 客供资料模块 | 已确认文件版本、文件内容不可变引用、校验值 | 草稿/未确认资料不默认纳入 |
| 样品单 | 样品单模块 | 关联的确认单及关键要求 | 需识别样品状态 |
| BOM | BOM 模块 | BOM 明细或不可变 BOM 版本引用 | 不得只存可变 BOM ID |
| 工艺路线 | 工艺路线模块 | 工序顺序、工序属性、版本 | 以现有路线实体为准 |
| 刀模 | 刀模模块 | 刀模编号、适用要求、必要参数/版本 | 实物刀模使用记录属于执行层 |
| 冲型条件参数 | 参数模块 | 完整参数值、单位、适用条件 | 参数修改后历史值不变 |
| 冲型备注 | 参数/工艺模块 | 发布时备注正文 | 不以当前备注替代历史备注 |
| 印刷工艺 | 印刷工艺模块 | 工艺步骤、参数及要求 | 可按工序归类 |
| 工程图 | 工程图模块 | 文件版本、不可变文件引用及哈希 | 不允许历史 URL 指向新文件 |
| 油墨调和记录 | 现有模块 | **仅标准配方/调和要求**（若有） | 每次实际调和记录属于生产执行，不能伪装为标准 |
| 作业规范检测 | 现有模块 | **检测标准/方法**（若有） | 实测结果属于质检/执行，需确认现有模块语义 |

发布版本不直接复制各模块的编辑功能。对已具备不可变版本能力的资料，可记录版本引用；对可能覆盖更新的结构化资料，保存完整快照。对于附件，必须保存不可变文件版本或独立归档副本及 SHA-256 校验值。

## 3. 核心业务原则

1. **产品身份与版本分离**：同一 `productId` 可有多个规范发布版本，产品编码不因普通技术变更而必须变化。
2. **草稿可编辑、发布不可改**：发布后的正文、资料清单和附件引用不可原地修改；修订必须产生新版本。
3. **当前资料不等于生产依据**：生产只能使用已发布且被允许使用的版本，不能直接读取产品最新编辑数据。
4. **工单显式绑定**：正式下达时记录实际批准采用的规范版本 ID；不得按生产日期倒推“当时最新”。
5. **旧版保留**：新版本发布不删除旧版本；旧版本是否允许用于新工单由生效策略和授权决定。
6. **来源可查、历史可读**：每条快照保留原始来源 ID，但历史展示以不可变版本/快照为准。
7. **版本切换留痕**：投产后变更不能静默覆盖绑定；应记录影响批次、数量、时间、责任人及批准依据。
8. **历史数据不伪造**：无法证明的旧订单规范标记“待确认/无法还原”，不能自动套用当前版本。

## 4. 建议业务结构

```text
产品 Product
 ├─ 当前资料（由现有模块维护）
 └─ 作业规范发布版本 ProductWorkSpecVersion
      ├─ V1.0 ─ 资料条目 ProductWorkSpecItem × N
      ├─ V1.1 ─ 资料条目 ProductWorkSpecItem × N
      └─ V2.0 ─ 资料条目 ProductWorkSpecItem × N

生产订单/生产工单（复用现有实体）
 └─ workSpecVersionId → ProductWorkSpecVersion

生产中途切换（按需）
 └─ WorkSpecUsage/ChangeLog → 旧版、新版、生效范围、批准信息
```

**V1 建议两张新核心表**：版本表 + 版本资料明细表。没有多套独立规范主档需求时，不新增 `ProductWorkSpec` 主表。订单绑定优先在现有实体上增加字段；若已有多对多或复杂执行记录，需以代码核查结果决定是否新增关联表。

## 5. 实体设计（逻辑模型）

### 5.1 `product_work_spec_version`：发布版本

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `product_id` | 产品 ID，外键到现有产品实体 |
| `version_no` | 产品范围内唯一版本号，如 V1.0 |
| `status` | DRAFT / PUBLISHED / RETIRED；草稿是否入本表需结合现有流程确认 |
| `change_summary` | 本次修订说明 |
| `effective_from` | 计划生效时间（可空，不代替工单绑定） |
| `published_at`, `published_by` | 发布时间与发布人 |
| `approved_at`, `approved_by` | 审批信息（如启用审批） |
| `based_on_version_id` | 基于哪个版本修订（可空） |
| `manifest_hash` | 发布清单校验值（规范化序列化后计算） |
| `created_at`, `created_by` | 创建审计 |

约束：`UNIQUE(product_id, version_no)`；已发布版本不允许更新其发布清单、内容、哈希及关键关联。当前推荐版本可通过查询策略或现有产品字段表达，不建议同时维护多处互相矛盾的“当前版本”状态。

### 5.2 `product_work_spec_item`：发布资料条目

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `spec_version_id` | 所属发布版本 ID |
| `resource_type` | BOM / ROUTING / DIE / FORMING_PARAM / FORMING_NOTE / PRINTING / DRAWING 等 |
| `source_id` | 原始资料记录 ID（追踪来源） |
| `source_version_id` | 原始资料不可变版本 ID（若支持） |
| `operation_ref` | 对应工序标识（若适用） |
| `snapshot_json` | 对可变结构化资料保存发布时完整快照（可空） |
| `file_revision_ref` | 不可变文件版本/归档对象标识（可空） |
| `content_hash` | 条目内容或文件 SHA-256 校验值 |
| `sort_order` | 展示顺序 |

一个版本可有多个同类型条目（例如多张工程图、多个刀模或多条工序参数），**不能**简单对 `(spec_version_id, resource_type)` 做唯一约束。应按来源/工序/用途制定去重规则。

**快照与引用策略**：
- 结构化数据可能被原模块覆盖：发布时复制完整必要字段及明细到 `snapshot_json`。
- 原模块已有真正不可变版本：保存 `source_version_id`，并确保历史记录不被物理删除；可同时固化摘要/哈希。
- 附件：保存不可变对象版本 ID 或归档副本，记录哈希与元数据；原始可变 URL 不可作为唯一历史凭据。
- 需定义快照 Schema 版本，以支持未来字段演进和历史读取。

### 5.3 生产单据绑定（修改现有实体）

在**实际代表生产执行单元**的现有生产订单/工单实体上新增 `work_spec_version_id`（非空时外键引用发布版本）。如果销售订单/生产订单存在技术版本指定，可在上游保留 `requested_spec_version_id` / `planned_spec_version_id`，但它不替代执行工单的实际绑定。

规则：
- 创建工单时可推荐当前允许使用版本；正式下达前必须人工确认或按明确业务规则自动确认。
- 下达后禁止静默更换 `work_spec_version_id`。
- 工单与规范必须属于同一产品；后端校验，不仅靠前端。
- 历史页面始终按绑定的版本 ID 读取。

### 5.4 投产中变更（条件扩展）

如果一张工单可能前 3,000 件用 V1.0、后 7,000 件用 V1.1，单个 `work_spec_version_id` **不足以证明全部实际执行情况**。需要增加 `work_spec_usage`（或复用现有批次/派工执行记录），记录 `work_order_id`、`spec_version_id`、生效批次/数量区间、开始结束时间、批准人、变更单及操作审计。不能用覆盖工单字段代替执行履历。

## 6. 发布与维护流程

```text
原有模块修改资料
   ↓
产品作业规范页面汇总当前资料（工作态）
   ↓
预检查：必需项、资料状态、关联产品、附件完整性
   ↓
生成与上个发布版本的差异预览
   ↓
填写变更原因，必要时审核
   ↓
原子发布：生成版本 + 条目快照/不可变引用 + 哈希
   ↓
标记可用版本；历史版本保持不变
   ↓
新工单选择/确认使用版本
```

**一致性要求**：发布过程应避免一边读取 BOM、一边被其他人修改参数而形成混合快照。可采用事务隔离、乐观锁版本校验或先生成候选清单后复核；附件归档失败时不得将版本标为发布成功。发布失败需可重试且不产生半成品正式版本。

## 7. 变更与生效规则

| 场景 | 处理原则 |
|---|---|
| 修改当前冲型参数 80→85 | 当前工作数据可变；V1.0 保持 80；确认后发布 V1.1 为 85 |
| 发布 V1.1 时已有未投产工单 | 不自动替换；按批准规则决定是否变更绑定 |
| 老客户要求沿用 V1.0 | 允许在受控条件下选择旧版，并保留原因 |
| 工单已经投产，后续数量改用新版 | 记录切换事件及适用批次/数量；不得覆盖原执行事实 |
| 修改仅涉及不影响生产的备注 | 由业务规则决定是否需要重新发布；若已发布内容变化，必须产生新版本 |
| 历史图纸被替换/删除 | 历史归档版本仍可打开并校验 |

版本状态与使用权限分离：`PUBLISHED` 表示已发布；是否默认推荐、是否禁止新工单使用、是否允许特批沿用，建议作为明确的生效/授权规则，而不是把所有含义压入一个“当前/历史”字段。

## 8. 页面与操作建议

**产品作业规范页**：产品基本信息、当前资料汇总、缺失检查、未发布变更提示、发布新版本、版本列表、版本差异。

**版本详情页**：版本号、发布人/时间、变更原因、11 类资料的完整发布内容；支持查看工程图和文件的历史版本；发布后只读。

**生产订单/工单页**：显示“指定/计划版本”和“实际绑定版本”（按现有单据层级裁剪）；点击可查看对应历史资料；如果发生切换，展示每段执行记录。

**历史追溯入口**：可由产品、订单、工单、生产批次（若有）进入，最终都定位到同一个不可变发布版本；若证据不足，明确显示“无法确定历史版本”。

## 9. 样例

| 产品 | 规范版本 | BOM | 刀模 | 冲型压力 | 工程图 |
|---|---|---|---|---|---|
| A001 | V1.0 | BOM-A | DM001 | 80 | DRAW-A |
| A001 | V1.1 | BOM-A | DM001 | 85 | DRAW-A |
| A001 | V2.0 | BOM-B | DM002 | 85 | DRAW-B |

| 工单 | 实际绑定版本 | 历史查询结果 |
|---|---|---|
| MO-001 | V1.0 | 压力 80、DM001、DRAW-A |
| MO-002 | V1.1 | 压力 85、DM001、DRAW-A |
| MO-003 | V2.0 | 压力 85、DM002、DRAW-B |

即使现在 A001 的参数改成 90，MO-001 的历史查询仍是 80。

## 10. 历史数据迁移

1. 清查现有订单/工单是否已有版本号、附件、审批、生产日期等证据。
2. 对可证明的历史配置，补建历史发布版本并绑定相应工单，记录证据来源与补录人。
3. 对不可证明的订单，标记“历史规范未知/待确认”，不把当前技术资料反填为历史事实。
4. 先对新下达工单启用强制绑定；老单逐步补录，避免一次性假数据迁移。

## 11. 分阶段实施

**P0：可靠追溯闭环**
- 只读盘点现有 11 类资料及生产实体。
- 实现两张核心表（如核查后确有必要）及不可变附件策略。
- 实现发布、历史版本查看、工单版本绑定、历史查询。
- 发布后不可变；后端校验同产品及发布状态。

**P1：维护效率**
- 版本差异、缺失资料检查、发布前审批、历史补录。

**P2：复杂变更**
- 工程变更单、生效策略、工单中途切换、批次/数量级实际执行追溯。

若业务确认存在“投产中途切换规范”，应将对应最小执行记录提前到 P0，而不能留到 P2。

## 12. 验收场景

1. 发布 V1.0（冲型压力 80），之后原始参数改成 85；历史 V1.0 仍显示 80。
2. 发布 V1.1 并绑定新工单；老工单继续显示 V1.0。
3. 替换当前工程图后，历史工单仍能打开旧图纸。
4. 仅知道产品 ID 而无版本绑定时，系统不能伪称历史工单使用最新规范。
5. 下达工单时，不能绑定其他产品的规范或未发布版本。
6. 并发修改资料时，不允许发布混合、不一致的版本。
7. 发布失败时不出现可被工单使用的半成品版本。
8. 若存在工单中途切换，可还原不同批次/数量所用的版本。

验证策略：优先复用现有测试和最小针对性检查，进行真实业务 E2E 验收；**禁止默认新增测试类，禁止每次改动执行全量测试**。阶段收口时再按风险安排完整验证。

## 13. 待业务确认的关键问题

1. 同一产品是否可能同时存在多套适用规范（设备/产线/客户要求），还是始终只有一套规范的多个版本？
2. 一张生产工单是否可能中途切换规范，是否已有批次/数量分段记录？
3. “油墨调和记录”包含标准配方还是纯实际调和记录？
4. “作业规范检测”指检测标准、检测作业指导还是实际检测结果？
5. 哪些资料已有真正不可变版本，哪些是直接覆盖修改？
6. 规范版本在销售订单、生产订单、派工、工序执行哪个层级最终锁定？
7. 历史老订单可用什么证据恢复当时的资料？
