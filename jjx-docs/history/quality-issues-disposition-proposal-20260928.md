## 1. 结论先行

本轮问题的共同根因不是几个页面文案错误，而是质量处置被按类型拆成多张表，并且每条路径各自维护状态、数量和关联关系：

```text
让步接收 / 退货 / 返工 / 报废
        ↓
多张类型表 + 多套状态机 + 多个数量写入点
        ↓
页面按表拆 Tab、账目重复持久化、历史难以还原
```

建议目标不是继续给四张表打补丁，而是：

1. 保留隔离台账作为“被处置对象及剩余量”记录；
2. 将让步接收、退货、返工、报废统一为一张 IQC 处置动作表；
3. 统一动作类型、状态机、审批、权限、幂等和数量口径；
4. 质量动作、库存流水、页面读模型各自守住边界；
5. 旧表迁移后停止写入，经过对账周期再归档/删除。

`a6191c71` 已完成部分主链路修复，但不应视为质量模块整体治理完成。当前仍需优先处理普通采购入库回写、让步接收数量语义、统一处置表迁移和全域读模型。

## 3. 目标数据模型

### 3.1 隔离台账和处置动作分工

`inventory_iqc_quarantine` 不是处置类型，而是隔离对象台账，应保留，职责是：

- 记录哪一批物料被隔离；
- 记录隔离总量和当前剩余量；
- 关联来料、检验批、IQC 批次；
- 展示当前是否还有可处置数量。

让步接收、退货、返工、报废属于同一种业务对象的四类动作，统一进入：

```text
inventory_iqc_disposition
```

可以直接升级现有 `inventory_iqc_disposition_order`，避免再增加一张过渡主表。

### 3.2 统一处置表核心字段

```text
disposition_id
disposition_no
action_type              RELEASE / RETURN / REWORK / SCRAP
status
approval_status
quarantine_id
inbound_id
inbound_item_id
inspection_id
lot_id
iqc_batch_id
quantity
operator_id / operator_name
approver_id / approver_name
reason
remark
child_lot_id
child_inbound_id
effective_time
legacy_source_type
legacy_source_id
create_time
update_time
```

类型专属字段只有在需要查询、关联或约束时才加列；不能为了页面方便再次建 `_scrap`、`_rework`、`_return` 表。非核心扩展信息可以使用 JSON，但数量、状态、批次和单据关联不能藏在 JSON 中。

### 3.3 统一状态机

公共状态：

```text
PENDING
PENDING_APPROVAL
PENDING_INBOUND
PROCESSING
COMPLETED
REJECTED
CANCELLED
```

类型只定义允许的流转，不再各自复制状态字段：

```text
SCRAP:  PENDING → PENDING_APPROVAL → COMPLETED / REJECTED
RELEASE: PENDING → PENDING_INBOUND → COMPLETED
RETURN: PENDING → PROCESSING → COMPLETED
REWORK: PENDING → PROCESSING → COMPLETED
```

同一处置单必须有状态流转校验、版本/行锁或幂等键，禁止通过重复请求重复扣减剩余量。

## 4. 真源和数量口径

### 4.1 三个域的唯一事实

```text
inventory_iqc_disposition
    = IQC 处置申请、审批和动作流程事实

quality_ncr_action
    = 质量域有效处置动作投影/事实

inventory_transaction
    = 库存实际变动唯一事实
```

三者不能互相冒充：

- 报废申请不算有效处置；审批通过后才进入有效质量处置；
- 退货、返工、报废不产生可用库存流水；
- 让步接收只有仓库确认入库后才产生库存流水；
- 返工复检合格品通过 `IQC_REWORK` 待确认入库进入库存。

### 4.2 数量字段规则

```text
检验批总量 = 合格量 + 不良量
不良量 = 有效处置量 + 剩余可处置量
已确认入库量 <= 本批合格量
库存结存 = 入库流水 - 出库流水 ± 调整流水
```

建议将以下字段降为可重算缓存，而不是独立真源：

- `quality_lot.disposed_quantity`；
- `quality_ncr.disposed_quantity`；
- `inventory_iqc_quarantine.remaining_quantity`；
- `inventory_iqc_batch.disposed_quantity`。

短期可以保留字段以兼容页面和查询，但每次写入后必须能用统一动作表重算，并由巡检发现差异。

## 5. 迁移实施方案

### 阶段一：冻结口径和建立迁移基线

迁移前只读盘点：

1. 四张旧表的记录量、状态分布、关联完整性；
2. 同一处置是否重复存在；
3. 旧表合计与 NCR 动作、隔离剩余、检验批汇总的差异；
4. 可重算、部分缺失、不可完全恢复三类历史清单。

旧数据不根据当前汇总字段伪造历史动作。

### 阶段二：扩展统一处置表

优先升级 `inventory_iqc_disposition_order`：

- 增加 `action_type` 和统一状态字段；
- 增加审批、子批、子入库关联字段；
- 增加 `legacy_source_type/source_id`；
- 增加唯一约束，确保来源动作幂等；
- 增加必要索引：隔离单、检验批、批次、状态、动作类型。

这一阶段不删除旧表，不改历史含义。

### 阶段三：迁移旧数据

```text
旧 disposition_order → 保留原 action_type
scrap_order           → SCRAP
rework_order          → REWORK
return_order          → RETURN
```

迁移后逐条对账：单号、数量、状态、操作人、时间、批次和来源不能丢失。无法可靠映射的记录标记为历史不完整，不用当前汇总量补造。

### 阶段四：切换写路径

所有新动作只能写统一表：

- `handleQuarantine`；
- 报废审批；
- 返工完成；
- 退货完成；
- 让步接收入库确认。

旧表停止写入。兼容查询可以暂时保留，但不能双写，否则会重新形成多套账。

### 阶段五：切换查询和前端

提供统一接口：

```text
GET /inventory/iqc-dispositions
```

通过 `actionType`、`status`、`inboundId`、`lotId`、`batchId` 筛选，不再通过四张表拆页面 Tab。

页面统一展示：

- 待处理；
- 待审批；
- 待确认入库；
- 已完成。

这些是状态视图，不是四套业务页面。

### 阶段六：旧表只读观察后归档

满足以下条件后，才允许归档或删除旧表：

- 一个完整业务周期无旧表新增；
- 统一表与旧表对账为 0；
- 所有页面、报表、打印和接口不再读旧表；
- 备份和回滚方案已确认；
- 用户审核通过。

## 6. 当前代码遗留的直接修复项

统一处置表迁移前，必须先处理以下两个缺口，否则迁移数据会继续扩大错误：

### 6.1 普通采购入库回写检验批

采购来源 `confirm()` 必须统一回写关联质量批的 `stored_quantity`，并触发关闭判断。回写失败不能只记录 warn 后让库存确认成功。

验收：

```text
合格 492 → 确认入库 → quality_lot.stored_quantity = 492
库存流水入库累计 = 492
检验批可满足 CLOSED 条件
```

### 6.2 拆开 accepted 和 stored

明确：

```text
accepted_quantity = IQC 质量接受结果
stored_quantity   = 已确认进入库存的数量
```

让步申请不能因为创建申请就重复增加库存相关数量；仓库确认只产生库存事实和入库结存。

## 7. 统一读模型

即使最终合并底层表，前端也不应直接依赖表结构。建议提供：

```text
QualityTraceView
```

至少包含：

- 来料批次；
- 采购单号；
- 检验批号；
- 原批/复检批关系；
- 整批收货；
- 整批合格；
- 整批不良；
- 本批复检；
- 已处置；
- 剩余可处置；
- 已确认入库；
- 当前处置状态；
- 来源单据和业务单号。

IQC、NCR、报废、打印、检验批工作台均使用该模型，禁止各页面本地拼接数量。

## 8. 历史和审计

统一记录以下事件：

```text
ITEMS_SAVED

REVIEWED
DISPOSED
REINSPECTION_CREATED
REINSPECTION_JUDGED
INBOUND_CONFIRMED

```

历史快照至少保留：操作人、时间、事件、批次关系、数量快照、检验项快照和来源单据。

旧数据只做事实盘点，不补造不存在的操作历史。

```text
旧表状态 = 新表状态
旧表来源关联 = 新表来源关联
历史操作人/时间不丢失
```

### 10.3 主链路 E2E

使用：收货 500、合格 492、不良 8。

```text
报废 1 → 待审批 → 通过
退货 1 → 完成
返工 1 → 复检子批 → 复检合格
复检合格 1 → IQC_REWORK 待确认入库
仓库确认 → 库存流水 +1
剩余可处置 = 5
```

检查：

- 原批 492 不重复入库；
- 报废审批通过只生效一次；
- 驳回恢复剩余量；
- 复检结果不覆盖原批结论；
- 检验批最终可以满足关闭条件。

### 10.4 幂等和并发

- 连续双击审批；
- 两个用户同时审批；
- 重复确认入库；
- 重复生成复检批；
- 接口超时后重试；
- 同一隔离记录重复处置。

预期：动作只生效一次、库存流水只产生一次、统一表只保留一条有效动作。

### 10.5 展示验收

复检行至少显示：

```text
原批：QL260928003
复检批：RW-IQW260928001
关系：INCREMENT
本批复检：1
该批只针对：1 件
整批不良：8
已处置：3
剩余可处置：5
```

不得把“整批不良 8”展示成“复检 8”。

## 11. 防止以后继续拆表

新增质量业务类型必须先通过以下检查：

1. 它是否只是现有动作的类型变体？
2. 是否可以复用统一处置表？
3. 是否可以复用统一状态机和审批？
4. 是否有独立生命周期？
5. 是否需要独立权限和管理页面？
6. 是否能证明现有统一表无法承载？

默认规则：

```text
同一业务动作的类型变体 → action_type
派生汇总 → 查询/缓存，不新建汇总表
页面展示 → 统一读模型，不按表拆页面
独立业务对象 → 只有通过提案和用户审核后才允许建表
```

## 13. 建议任务拆分

虽然目标是统一合并，但实施建议按可回滚边界拆任务：

| 阶段 | 内容 | 结果 |
|---|---|---|
| M1 | A4/A5 数量和采购入库闭环 | 账务不再继续扩大 |
| M2 | 统一表结构、旧数据迁移、对账 | 四类动作进入一张表 |
| M3 | 全部写路径切换、旧表停写 | 消除双写 |
| M4 | 统一查询接口和页面工作台 | 页面不再按表拆分 |
| M5 | 历史、权限、打印、报表和清理旧表 | 完成全模块收口 |

阶段之间必须有自动对账和可回滚点，不能在同一批次里直接删除旧表。
