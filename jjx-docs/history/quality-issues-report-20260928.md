## 一、链路与现状（背景）

```
采购单 PO → 采购收货（自动生成入库单 IN260928xxx，此时货未入库）
  → IQC 检验录入（按材料行建检验批 QL260928xxx）
  → 单项 IQC 审核（品质主管）
  → 确认入库（仓库，才加库存；采购入库单不走单据级审批）
  → 不合格 → 隔离台账 → 处置（让步接收 / 退货 / 返工 / 报废）
  → 返工 → 复检子批 RW-xxxx → 复检
```

关键事实：
- 采购入库单**不能走单据级审批**（`approve()` 会抛「采购入库请使用单项 IQC 审核」）；`approve_status` 是并行冗余字段，永远停 1。
- 让步接收（RELEASE）原先**直接过账加库存**（已由 dev-20260928-009 改为「生成待确认入库单」）。
- 报废（SCRAP）→ 处置单 `PENDING_APPROVAL`，审批通过才生效。

## 四、附：规范提案（草稿）—— CONVENTIONS §15「模型收口与表数增长控制」

**背景**：2026-09-28 联调暴露「一种业务动作的多种类型各建一张表 + 各一套状态机」，导致页面被迫按表拆 Tab；全库已 124 张表。§14 只覆盖「新表 vs 配置/字典/属性」，不覆盖本类问题。

1. **一业务一表，变体用类型字段**：同一业务动作的不同类型（让步/退货/返工/报废）→ 一张表 + `type` 字段；类型专属字段可空或走 JSON 属性。**禁止**每类型一张表 + 每类型一套状态机。
   *例外（须提案说明）*：结构完全不同 + 独立生命周期 + 独立权限点。
2. **审批一套化**：统一「审批单 + 审批状态 + 审批权限」，类型驱动；**禁止**按类型各建审批表/状态机。
3. **单一真源 + 汇总不落库**：一个事实只有一个写入入口（如库存只能走 `applyDelta`）；汇总字段（`disposed_quantity` / `accepted_quantity` 等）**默认不落库**，需重算得到；确需落库必须登记「可由什么重算 + 对账脚本」并进巡检。
4. **域边界**：质量/库存/采购各管自己的事实；跨域**只保留 ID 关联 + 只读聚合**，不复制对方汇总字段。
5. **展示不得按表拆**：一个业务对象 = 一个页面/工作台；后端提供只读聚合模型，前端不得按底层表拆 Tab、不得自行拼数量。
6. **门禁 + 基线**：① `表数基线`（当前 124，**只许缩小**；新增须提案）；② 新增表/字段先过 §14 判据 + 本提案 7；③ 巡检脚本覆盖：状态魔法值 / 大小写 / 恒等式 / 跨表对账 / 表数基线；④ 定期**熵减**（合并同类表、清死表/死字段/死代码）。
7. **提案模板**：新增表或改模型必须写一页：① 为什么不能复用现有表；② 与现有表关系（主/附）；③ 迁移与兼容（旧数据）；④ 回滚；⑤ 风险。**用户拍板后**才走 `db-migrate.sh`。

**首个应用对象**：IQC 4 张处置相关表 + `quality_ncr*` → 先**只读聚合**（页面单表），模型合并另立提案。
