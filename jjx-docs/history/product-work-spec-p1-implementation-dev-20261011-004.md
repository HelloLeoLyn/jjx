## 一、本轮已拍板口径（用户 2026-10-11）

1. **不设规范主档**：私印、一个产品只有一个客户，不会并存多套规范 → 一条规范多版本，版本直接挂 `product`。
2. **工单可能中途换版**（少但可能）→ 最小「执行区间记录」提前到 P0/P1，不留 P2。
3. **油墨调和记录**：无固定配方，只是给生产现场一张纸随手记录 → 属执行记录，**不持久化、不进发布版本**（页签保持纸面）。
4. **分色检查表**：工程交生产前对产品工程资料（菲林排版/图纸/刀模等）的检查 → 属**放行前证据**，不进规范正文，也不当生产检测标准。
5. **BOM / 工艺路线**：审批后要改是升版本号、产品引用同步设置 → 属**真版本**，发布时可直接「引用已批准版本」。
6. **版本锁定层级**：销售订单记「采用版本」+ 生产工单锁「实际执行版本」；派工/工序执行不逐条锁。

## 二、§15 新表提案（3 张，需用户拍板）

### 2.1 `product_work_spec_version`｜发布版本

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `product_id` | 产品 ID（引用现有产品） |
| `version_no` | 产品范围内版本号，如 V1.0 |
| `status` | PUBLISHED / RETIRED（草稿不入本表，仍是工作态） |
| `change_summary` | 本次修订说明 |
| `based_on_version_id` | 基于哪个版本（可空） |
| `manifest_hash` | 发布清单校验值（规范化序列化后计算） |
| `effective_from` | 计划生效时间（可空，不代替工单绑定） |
| `published_at` / `published_by` | 发布时间 / 发布人 |
| `create_by/create_time/update_by/update_time/deleted` | 审计 |

约束：`UNIQUE(product_id, version_no)`；发布后发布清单、内容、哈希、关键关联不可改。

不复用原因：现有 `product.work_spec_json` 是工作态、直接覆盖写，`revision` 只是并发校验摘要，无法重建旧版内容（P0 已核）。

### 2.2 `product_work_spec_item`｜发布条目

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `spec_version_id` | 所属发布版本 |
| `resource_type` | SPEC_JSON / BOM / ROUTING / DRAWING |
| `source_id` | 原始资料记录 ID（追踪来源） |
| `source_version_id` | 原始资料不可变版本 ID（若支持） |
| `operation_ref` | 对应工序标识（若适用） |
| `snapshot_json` | 发布时完整快照（对可能被覆盖的结构化资料） |
| `content_hash` | 条目内容或文件 SHA-256 |
| `sort_order` | 展示顺序 |

约束：**不**对 `(spec_version_id, resource_type)` 唯一（一版可含多张图纸/多条目），按来源/工序/用途去重。

### 2.3 `work_spec_usage`｜执行区间记录

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `work_order_id` | 生产工单（复用现有实体） |
| `spec_version_id` | 该区间实际使用的规范版本 |
| `qty_from` / `qty_to` | 生效数量区间（可空） |
| `start_time` / `end_time` | 生效起止时间 |
| `change_reason` | 换版原因 |
| `approved_by` / `approved_at` | 批准人 / 时间 |
| `create_by/create_time/deleted` | 审计 |

用途：一张工单分段执行两个版本时，逐段记录实际执行依据（不能用覆盖工单字段代替）。

回滚：删除两张/三张新表；`work_spec_usage` 可独立回滚（不改现有表）。

## 三、现有表加字段（§15.4 字段级闸，非新表）

- `sales_order_product` + `work_spec_version_id`（该订单产品「采用版本」）
- `production_order` + `work_spec_version_id`（工单正式下达锁定的「实际执行版本」）
- `sys_attachment` + `sha256`(char64) + `controlled`(受控标记 0/1)

## 四、P1 发布范围

发布时固化：

- **SPEC_JSON**：`work_spec_json` 全文快照（含印刷整组备注、变更、分色检查结果等）。
- **BOM**：引用「已批准」版本（记 `bom_id` + 版本 + hash）。
- **ROUTING**：引用「已批准」版本。
- **DRAWING**：选用的结构图/工程图文件版本 + `sha256`。

**未纳入（发布页显式标注「未纳入本次发布」）**：客供资料受控库（尚未建）、样品/样品需求单、领料单、油墨（纸面执行）、实际检测记录。

## 五、页面改动

- **作业规范页**：加「发布新版本」+ 版本列表 + 「工作态 vs 已发布」差异提示。
- **版本详情页**：只读展示已发布内容 + 发布人/时间/原因；发布后只读。
- **生产订单/工单页**：显示「指定/计划版本」与「实际绑定版本」；有换版则展示执行区间。
- **历史追溯入口**：产品/订单/工单 → 定位到不可变发布版本；证据不足显示「历史未知」。
- **发布时后端校验**：同产品、已发布、BOM/路线一致、必需项齐。

## 六、地基（与 P1 一起做）

- `sys_attachment` 加 `sha256` + 受控标记；受控件**禁删/禁覆盖**，回收站只放未受控件。
- 附件**去重**（同文件只存一份）+ 存储路径**可配置**（盘不足加盘/NAS，不改业务）。
- 理由：发布版本要「引用不可变文件」，现无哈希列且允许物理删除 → 不补则引用模式不成立。

## 七、顺序与验收

顺序：§15 提案拍板 → 建 3 表 + 3 字段 + 附件哈希 → 发布 / 订单采用 / 工单绑定 / 历史查询 → 逐页签接入。

验收（B §12 + C 的 E2E）：

1. 发布 V1 后改当前资料，历史 V1 仍读原值（冲型压力等）。
2. 发布 V1.1 并绑定新工单；老工单仍显示 V1。
3. 替换当前工程图后，历史工单仍能打开旧图。
4. 仅知产品 ID 无绑定时，系统不伪称历史工单用最新规范。
5. 下达工单不能绑其他产品或未发布版本。
6. 并发修改资料不产生混合、不一致的版本；发布失败不出现可用的半成品版本。
7. 若工单中途换版，可还原不同批次/数量所用的版本。

## 八、实施时确认（不阻塞提案）

1. 附件是否真有删除保护 → 决定发布时「引用」还是「快照」（引用要求源文件不可变）。
2. 版本号格式（V1.0 风格 / 是否随产品编码）、谁能发布（权限点）。
3. 工单绑定是「下达强制」还是「可推荐」（B 建议：正式下达前人工确认）。

## 九、回滚方案

- 建表迁移反向：`DROP TABLE`（3 张新表）。
- 加字段迁移反向：`DROP COLUMN`（`work_spec_version_id` × 2、`sha256`/`controlled`）。
- 页面：隐藏发布/版本/绑定入口即回到当前行为（现有功能不受影响）。

## 十、不做

- 不自建 DMS/PLM，复用现有附件服务。
- 不为省存储删受控资料（去重 + 分层 + 加盘，不是删）。
- 不把 `work_spec_json` 当历史；不一次接入全部 8 个子页签。
