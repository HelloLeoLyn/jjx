# 产品作业规范版本追溯 P0：现状核查与最小闭环评估

- 日期：2026-10-11
- 任务：dev-20261011-003（隶属 dev-20261011-002）
- 范围：只读核查现有源码与本地数据库表结构；不实施版本发布、订单绑定或数据补录。

## 一、结论与边界

现有页面以产品为入口，打印时读取产品当前资料并动态组合 BOM、工艺路线和附件；系统尚无“产品作业规范发布版本”，销售订单产品明细和生产工单也尚无规范版本绑定。现有 `product.work_spec_json` 的确认动作只写回同一产品行，不能作为不可变历史版本。`revision` 是并发校验摘要，不是可重开的旧版内容。

P1 应以产品发布不可变规范版本为主线，销售订单记录该产品采用版本，生产工单正式下达时锁定实际使用版本。页面可维持“产品 → 订单（默认最新）”的浏览方式；历史展示只能读取已固定的采用记录和发布内容，不能实时读取产品当前值来冒充历史。

用户提供的 V1.0 设计稿是业务评审稿，不是已实施事实。以下“建议”均需在 P1 实施任务中进一步确认，尤其是各来源的发布资格与审批规则。

## 三、核心实体与复用边界

| 实体 | 已有字段/行为 | 对版本追溯的影响 |
|---|---|---|
| `product` | `product_id`、`work_spec_json`、当前 BOM/路线指针 | 可保留为工作态；不能把当前 JSON 或当前指针直接作为历史工单依据。 |
| `engineering_bom`、明细 | `bom_id`、`bom_version`、`approve_status`、`is_current`；已审批 BOM 禁止常规编辑，支持复制新版本。 | 已批准版本有复用价值；发布时仍须检查明细完整性、删除路径及不可变保证，必要时快照。 |
| `engineering_routing`、明细 | `routing_id`、`routing_version`、`approve_status`、`is_current`；可编辑状态下明细会原地替换，也支持升版。 | 仅引用路线 ID 不足以证明完整工序历史；发布需限定已批准版本并固定工序内容/防删除。 |
| `sys_attachment` | `biz_type/biz_id/category/version/drawing_no/file_path`，无文件 SHA-256 列；支持逻辑删除与过期物理删除。 | 发布引用需要不可变文件、哈希及留存策略。现有附件 ID 不构成充分的历史文件保证。 |
| `sales_order_product` | `id`、`order_id`、`product_id`（可空）、产品编码快照；无规范版本字段。 | 销售订单“采用哪版”应以订单产品关系记录；历史 `product_id` 缺失时不能仅凭编码自动认定。 |
| `production_order` | `order_id`、`sales_order_id`（可空）、`product_id`、`bom_id`、`routing_id`；无规范版本字段。 | 工单最终执行版本需显式绑定；绑定时须校验产品和 BOM/路线与发布内容一致。无销售订单来源的工单仍需明确版本。 |

## 四、关键覆盖/混合风险

1. `ProductWorkSpecMapper.write()` 直接更新 `product.work_spec_json`；`confirm()` 也写回该字段。确认状态会在来源变化后失效，但旧确认内容没有独立历史版本。`sourceRevision` 只检验当时来源摘要，不能重建当时资料。
2. `docset.ts` 在每次预览时按 `productId` 拉当前规范、当前 BOM/路线、客供和产品附件。当前打印是“此刻资料组合”，不是订单或工单的历史发布版本。
3. BOM/路线虽有版本与审批，未批准草稿可原地改；文件即使已有编号和版本，也可能在撤回、回收站清理后消失。发布必须核验资格并固定内容或不可变引用。
4. `sales_order_product` 和 `production_order` 均没有规范版本绑定。仅按日期倒推最新版本无法证明生产实际采用版本。
5. 客供资料 V2.0 受控模型尚未建成，不能把现有附件聚合列表直接称作已批准、不可变的客供资料库。

## 五、P1 最小变更建议与验收边界

1. **发布层**：在核查新表准入与清理归属后，优先评估 `product_work_spec_version`（产品发布版本）和 `product_work_spec_item`（发布条目）。发布时原子固定规范 JSON、必要的 BOM/路线明细和结构图文件版本/副本、来源及哈希；发布后内容不可改。产品 `work_spec_json` 继续作为工作态编辑源。
2. **采用与执行层**：在 `sales_order_product` 记录采用版本；在 `production_order` 记录实际锁定的 `work_spec_version_id`，并校验同产品、已发布、BOM/路线一致。若销售订单关联不适合增列，再评估关系表；不要先建通用文档关联表来替代版本绑定。
3. **发布范围**：P1 明确覆盖规范正文、BOM、路线、选用结构图；其他子 tab 未接入前应显式提示“未纳入本发布版本”。样品确认、客供文件、印刷规范等逐项接入，领料和实际调墨作为执行记录，不冒充发布要求。
4. **工单生命周期**：在正式下达前固定版本，之后禁止静默换版。若存在同工单投产中途换版，必须先补最小执行区间记录（批次/数量/时间和批准依据），不能仅覆盖工单字段。
5. **历史数据**：仅证据足够的旧单可补录发布版本和绑定；证据不足显示“历史规范未知”。本次未对既有业务数据做任何回填。

P1 端到端验收：P1 产品发布 V1 → S1 采用 V1 → S2 明确沿用 V1 → 新规范发布 V2、S3 采用 V2 → 各工单锁定本次实际版本 → 当前资料继续修改后，S1/S2 与旧工单仍打开原文和原图，且能核对文件哈希。发布失败或并发来源变化不得产生可用的半成品版本。
