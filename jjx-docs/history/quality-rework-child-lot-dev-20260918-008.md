# 质量管理：供应商返工复检子批次与批次谱系方案（dev-20260918-008）

## 1. 登记目的

当前不合格品处置、供应商返工和待复检流程容易继续沿用原收货批次，造成“原批次收货事实”和“返工后质量结论”混在一起。该任务先登记完整方案，待评审后再决定是否立即实施。

## 2. 推荐业务模型

- 原供应商收货批次作为父批次，保留原始收货数量、供应商、收货时间和原始质量结论。
- 供应商返工完成后生成内部子批次（例如 `PO202609180002-1/RW01`），子批次作为待复检和后续入库的操作对象。
- 子批次必须显式保存父批次、来源返工单、返工数量、当前状态和创建事件；不能只依靠批次号字符串约定。
- 允许同一父批次多次返工、拆分多个子批次，并为后续合并或报废保留谱系扩展能力。

## 3. 计划变更范围

1. 批次主数据与父子谱系关系：增加可查询的批次身份、父批次、来源返工单、数量和状态关系。
2. 供应商返工单：返工下发/完工时创建子批次，禁止把父批次直接伪装成返工批次。
3. 复检入口：待复检列表、详情和提交接口以子批次为对象；原批次仅用于追溯展示。
4. 数量规则：整批判定合格时接收数量必须等于收货数量；部分合格、返工、报废分别按子批次或处置明细记录。
5. 状态、权限和审计：父子批次状态独立但受谱系约束，关键流转记录操作人、时间、数量和来源单据。
6. 查询与前端：支持从原收货批次追到返工单、子批次、复检记录和库存批次，也支持从子批次反查父批次。

## 4. 实施策略

- 优先采用轻量批次主表/谱系表，而不是在现有 `batch_no` 字段中拼接和猜测关系。
- 不做历史数据迁移；当前处于开发阶段，新增结构只服务新流程，旧数据按兼容只读展示。
- 实施前先完成表结构、唯一约束、状态转换矩阵和接口兼容评审，再拆分后端、前端和测试提交。
- 本登记不包含立即改代码、改表或发布；后续以本任务为入口单独执行。

## 5. 验收标准

- 父批次与一个或多个返工子批次可双向追溯，来源返工单和数量准确。
- 返工待复检入口只能操作对应子批次，原批次不能直接作为返工复检对象。
- 整批合格时，接收数量不等于收货数量会被阻断；部分合格和处置数量有明确记录。
- 状态、权限、库存入库和查询链路无越权、重复入库或批次混淆。
- 既有正常收货、合格入库和非返工复检流程回归通过。

## 6. 验证计划

- 后端：父子批次创建、重复提交、数量边界、状态转换和权限接口测试。
- 前端：待复检入口、批次谱系展示、错误提示、筛选和详情跳转测试。
- 联调：收货 → 不合格处置 → 供应商返工 → 子批次待复检 → 复检判定 → 入库/报废全链路验证。
- 规则：执行 `RM001599` 及相关质量规则回归，确认整批合格接收数量等于收货数量。

## 7. 参考依据

- GS1 Global Traceability Standard：批次/批号、关键追踪事件及转换关系。
- SAP Batch Split：批次拆分后形成可独立管理的部分批次。
- Oracle Rework Batch Genealogy：返工批次与来源批次的谱系追踪。

## 8. 本次实施结果（2026-09-18）

- 返工完成时生成 `RW-{返工单号}` 子批次；直接发起复检也生成独立子批次；复检检验记录和入库明细改用子批次号。
