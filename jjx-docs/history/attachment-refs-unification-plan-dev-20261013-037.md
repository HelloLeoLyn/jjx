## 1. 目标（一句话）

把附件的「两套存储 + 两套分类」收敛成 **一套存储（`sys_attachment` + `sys_attachment_ref`）+ 一套分类（资料类型字典）+ 两个视图（产品维度 / 单据维度）**；产品资料库**保留**为「产品维度的资料视图」，**只退役它的上传端**。

## 3. 现状盘点（只读核查结论）

| 维度 | 产品资料库（老） | 公共附件中心（新） |

## 4. 目标架构

- **存储**：`sys_attachment`（物理文件 + 受控图档字段）+ `sys_attachment_ref`（关联，带 `product_id`）。
- **分类**：`attachment_category`(一级 5) + `attachment_document_type`(二级 24 → 32)。
- **上传**：唯一入口 = 公共上传组件（TEMP → 绑定；权限、重复检测、待绑定队列都在这一条链上）。
- **视图**：
  - 单据维度 = 附件中心列表（标题行 + 勾选 + 批量）。
  - 产品维度 = 产品资料库（按**一级**分组、组内列二级与文件），上传嵌公共组件 `mode='upload-only'`。
- **受控图档**（版本 / 设为现行 / 下发撤回）**独立保留**在工程图集页，不进 refs 语义。

## 6. 明确不做 / 不动

1）受控图档（版本 / 现行 / 下发）不搬进公共组件。
2）真删文件的能力保留在原位（公共组件只有「解除引用」）。
3）19 类别里其余 9 项**不扩字典**（本轮只补 8 个二级）。
4）不动权限模型（`product:view` / `product:edit` 已存在且有 7 个角色授权）。

## 7. 建议实施顺序

M0 → M1 → M2 → M3 → M5 → M4

理由：先清数据可省掉存量映射；先把分类补齐（M1）才谈得上"分类统一"；上传端（M2）先修，产品视图改造（M4）才有新数据可看；老通道收口（M5）放在视图改造前，避免两次改列表。

## 8. 前置与风险
