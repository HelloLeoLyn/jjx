# JJX 客供资料管理模块完整设计方案 V2.0

> 文档类型：业务与技术设计方案  
> 日期：2026-10-10  
> 状态：设计评审稿（已纳入本轮确认的业务规则；接口、数据库及现有组件复用情况待代码核查）  
> 范围：产品作业规范中的客供资料页签、产品详情复用入口、来源单据关联及受控文档管理  
> 前端技术：Vue 3 + TypeScript + Element Plus  
> 原则：不修改现有业务代码；本文件仅定义方案

## 1. 项目背景与目标

现有客供资料不应只是产品抽屉里的附件列表，而应成为以产品为归属的受控资料库。需要覆盖询价、报价、销售订单、样品单和人工上传的资料，并保证当前有效版本明确、历史可追溯、来源可查询、文件不可被静默覆盖。

**目标**：以 `productId` 关联产品；提供统一的客供资料列表、入库/关联、重复检测、版本确认、历史、预览及审计能力；通过公共业务组件在产品作业规范和产品详情中复用。

**非目标**：本阶段不建设独立 DMS 平台；不引入额外 `itemId`、`customerId`；不重构所有业务单据上传功能；不默认引入 AI 图纸识别、复杂审批引擎、断点续传或全局文件去重服务。

## 2. 已确认业务决策

| 编号 | 决策 | 规则 |
|---|---|---|
| D-01 | 产品归属 | 每份客供资料仅归属一个 `productId`；一个产品可有多份资料 |
| D-02 | 客户维度 | 当前业务中一个产品不存在多客户，不新增 `customerId` |
| D-03 | 上传入口 | 询价、报价、销售订单、样品单等沿用原有附件上传，不打断业务流程 |
| D-04 | 受控入库 | 资料进入产品客供资料库时进行重复检测和版本确认 |
| D-05 | 重复判断 | SHA-256 + 产品 + 文档编号 + 文档类型 + 客户版本号联合辅助判断 |
| D-06 | 冲突处理 | 用户选择“关联已有 / 创建新版本 / 新建资料 / 取消”；系统只推荐，不自动覆盖 |
| D-07 | 版本生效 | 新版本先 `received`，确认后才 `active`；旧有效版本在此之前继续有效 |
| D-08 | 文件不可变 | 历史版本文件不得原位覆盖；物理存储可去重，业务记录必须保留 |
| D-09 | 多来源 | 同一受控修订版可关联多个来源单据，新增来源不自动产生新修订版 |
| D-10 | 复用 | 产品作业规范与产品详情共享业务组件和后端规则 |

## 3. 术语与业务边界

- **产品（Product）**：JJX 现有产品实体，以 `productId` 作为客供资料归属键。产品编码用于展示与搜索，不代替主键。
- **受控资料（CustomerDoc）**：一份逻辑文档的长期身份，例如“OX-001 客户图纸”。
- **修订版（DocRevision）**：该资料某一时点的完整、不可变文件集合及业务修订信息。
- **文件明细（DocRevisionFile）**：修订版中每个 PDF、DWG、STEP、Excel 等文件。
- **来源关系（DocSourceRelation）**：修订版与询价、报价、订单、样品等单据的关联记录。
- **来源附件**：业务单据原有附件，尚不等于经过工程确认的有效受控资料。
- **入库**：从来源附件或手工上传形成受控文档/修订版，并完成必要的分类、重复检查与确认。

### 3.1 基本关系

```text
Product(productId)
  └── CustomerDoc (一产品多文档)
        ├── DocRevision (一文档多修订版)
        │     ├── DocRevisionFile (一版本多文件)
        │     └── DocSourceRelation (一版本多来源)
        └── activeRevisionId (当前有效版本，可为空)
```

暂不设计跨产品共用一份逻辑文档的复杂关系；未来确有需求时再引入适用对象关系表。

## 4. 典型业务场景

### 4.1 询价 → 报价 → 销售订单重复使用同一图纸

1. 询价单 `INQ-001` 上传 `OX-001图纸.pdf`，业务上传照常成功。
2. 工程人员在产品 `OX-001` 的客供资料库执行“从询价单关联”。
3. 系统识别无已有文档，建立 CustomerDoc + 第 1 个修订版，状态 `received`。
4. 工程确认后修订版 `active`。
5. 报价单 `QT-001`、销售订单 `SO-001` 继续使用同一文件；入库时发现相同内容，推荐“关联已有”。
6. 确认后仅增加来源关系，不复制逻辑文档、不创建无意义版本。

### 4.2 客户提交新版本

- 已有图纸 `DWG-1001 / A/0` 为 `active`。
- 新文件声明 `DWG-1001 / A/1`，内容不同。
- 系统提示疑似同一文档的新修订版；用户确认后生成 `received` 修订版。
- **A/0 仍为 active**，生产端继续使用旧有效版。
- 工程人员核对并确认 A/1 后，在同一事务内把 A/1 改为 active、A/0 改为 superseded、更新 activeRevisionId。

### 4.3 内容相同但客户版本号不同

SHA-256 相同只说明二进制内容相同，不意味着业务修订声明相同。允许用户确认创建新修订记录，复用相同物理文件对象，同时保留客户声明和操作原因。

### 4.4 文件名相同但内容不同

文件名只能作为候选匹配依据。系统提示“可能为新版本”，用户选择创建新版本或独立新资料，不自动覆盖。

### 4.5 在制生产订单与图纸切换

产品详情默认显示当前 `active` 版本；已经下达的生产订单应记录其实际使用的 `revisionId`（作为后续生产集成要求）。新版本生效不应自动改变在制订单的执行依据；如需切换，应通过明确的变更/确认流程。

## 5. 文档类型与来源

### 5.1 文档类型字典

| code | 名称 |
|---|---|
| customer_drawing | 客户图纸 |
| specification | 技术规格书 |
| approval_sheet | 承认书 |
| inspection_standard | 检验标准 |
| change_notice | 变更通知 |
| golden_sample | 标准样品资料 |
| packaging_spec | 包装规范 |
| compliance_report | 认证报告 |
| other | 其他资料 |

“标准样品”实体样件本身不等于附件，第一版只管理其电子资料。字典优先复用现有配置能力，是否使用 `sys_attachment.category` 待核查；受控文档的业务类型不应仅依赖附件分类字段。

### 5.2 来源类型

`inquiry`、`quotation`、`sales_order`、`sample`、`upload`。来源单据 ID 与来源行 ID 由业务适配器校验，不能仅信任前端传值。

### 5.3 存储策略

| 策略 | 含义 | 前提 |
|---|---|---|
| reference | 复用原附件对象 | 原附件不可变、可长期保留、权限可控 |
| snapshot | 创建独立归档副本 | 原附件可变、可删除或不满足受控保存要求 |

来源类型只决定**默认建议**，不能硬编码为绝对策略。归档/引用选择由服务端策略控制；前端一般不允许随意覆盖安全规则。必须验证源文件在引用模式下不会被原业务删除或覆盖，否则强制快照。

## 6. 核心数据模型

以下是**逻辑模型**，实际表名、主键类型、附件字段及索引需与 JJX 现有数据库规范对齐。

```ts
interface CustomerDoc {
  id: string
  productId: string
  docType: CustomerDocType
  docNo?: string             // 客户图纸/资料编号，可空
  title: string
  activeRevisionId?: string  // 当前有效修订版，可空
  createdBy: string
  createdAt: string
  updatedAt: string
}

type RevisionState = 'received' | 'active' | 'superseded' | 'obsolete'

interface DocRevision {
  id: string
  docId: string
  versionNo: number          // 系统顺序号 1,2,3...
  revisionNo?: string        // 客户原始版本号，如 A/0、Rev.02
  state: RevisionState
  changeReason?: string
  ecnRef?: string
  receivedBy?: string
  receivedAt?: string
  provider?: string
  confirmedBy?: string
  confirmedAt?: string
  effectiveAt?: string
  createdBy: string
  createdAt: string
}

interface DocRevisionFile {
  id: string
  revisionId: string
  attachmentId: string
  fileName: string
  sha256: string
  fileRole: 'primary' | 'supporting'
  sortOrder: number
  storageMode: 'reference' | 'snapshot'
}

interface DocSourceRelation {
  id: string
  revisionId: string
  sourceType: CustomerDocSourceType
  sourceRefId: string
  sourceRefLineId?: string
  sourceAttachmentId?: string
  linkedBy: string
  linkedAt: string
}
```

### 6.1 数据库约束

1. `CustomerDoc.productId` 必填并引用现有产品主键。
2. `DocRevision(docId, versionNo)` 唯一，版本号由服务端并发安全分配。
3. 同一 `docId` 最多一个 `active` 修订版；数据库可用条件唯一索引或等价事务锁机制实现。
4. `activeRevisionId` 必须指向所属 CustomerDoc 且状态为 `active` 的修订版；无生效版本时允许为空。
5. 修订版确认入库后，其文件集合和关键业务版本字段不可原位修改；变更应生成新修订版。
6. 来源关系应对 `(revisionId, sourceType, sourceRefId, sourceRefLineId, sourceAttachmentId)` 做业务去重；空值唯一性需按数据库实现单独处理。
7. 文件的 `sha256` 计算必须基于实际文件字节，不能只信任前端传入值。
8. 文件引用、快照、来源关系的创建与版本入库应保持一致性；失败需回滚元数据并清理孤儿文件。
9. 文件物理删除必须检查全部业务引用，历史受控文件不得因源单据删除而丢失。

### 6.2 状态说明

| 状态 | 含义 | 生产默认可见 |
|---|---|---|
| received | 已接收，等待确认 | 否 |
| active | 已确认生效 | 是 |
| superseded | 已被后续版本替代 | 否 |
| obsolete | 已作废，不再适用 | 否 |

允许同一文档存在多个 received 候选修订版，但应明确审核顺序和并发冲突处理；同一时刻最多一个 active。首次入库可无 active。作废是独立动作，不能假定一定存在替代版本。

### 6.3 状态转换

```text
新版本入库 → received
received ──确认生效──> active
active ──新版本确认生效──> superseded
received / active ──作废（权限+原因）──> obsolete
```

不允许普通用户将 superseded 版本直接“改回 active”；需要恢复时，应基于历史内容创建**新的修订版**，重新确认，保留完整历史。若当前 active 作废，需同步清空 activeRevisionId，并提示生产端当前无有效版本。

## 7. 重复检测与入库决策

### 7.1 检测时机

业务单据上传时不弹出受控文档重复提示；只有执行“加入客供资料库 / 从单据关联 / 上传受控资料”时触发检测。

### 7.2 检测顺序

1. 校验 `productId`、来源权限和附件可访问性。
2. 计算/读取服务端可信 SHA-256，按产品范围查找内容完全一致的已有修订文件。
3. 用 `docNo + docType` 查找可能属于同一逻辑文档的版本。
4. 辅助比较 `revisionNo`、文件名和来源关系。
5. 返回**候选记录与原因**，不直接做业务合并。

| 检测结果 | 系统建议 | 允许操作 |
|---|---|---|
| 同产品、同业务文档、文件哈希相同 | 关联已有修订版 | 关联 / 新修订版（说明原因）/ 新资料 / 取消 |
| 同文档编号与类型、哈希不同 | 疑似新版本 | 新修订版 / 新资料 / 取消 |
| 哈希相同但类型或编号不同 | 内容重复、身份未必相同 | 由用户确认，禁止自动合并 |
| 文件名相同、其他信息不足 | 疑似相关 | 用户确认新资料或版本 |
| 无候选 | 新建资料 | 新建 / 取消 |

**关键区分**：SHA-256 判定的是文件字节相同；“是否同一受控文档”属于业务身份判断；“是否新版本”需要业务确认。多文件修订版应按文件集合及文档身份进行比较，不能只比较主文件。

### 7.3 冲突确认弹窗

显示本次文件、候选资料编号、类型、当前有效版、来源、匹配原因、差异摘要，提供四种动作：

- **关联已有**：选择已有 `revisionId`，只建立新的来源关系；不产生新版本。
- **创建新版本**：选择目标 `docId`，填写客户版本号及变更原因；新版本为 received。
- **新建资料**：创建新 `CustomerDoc` 及 received 修订版。
- **取消**：不修改受控资料库，原业务附件仍然保留。

后端必须重复验证候选和权限；处理提交需要幂等键，避免双击或网络重试产生重复版本。

## 8. 前端页面设计（Vue 3 + TypeScript + Element Plus）

### 8.1 页面 A：客供资料列表 `CustomerDocPanel`

入口：产品作业规范抽屉“客供资料”页签，以及产品详情中的相同公共组件。

**顶部**：产品信息、资料总数、当前有效数、待确认数、已作废数；按钮“新增资料”“从单据关联”。

**筛选**：资料类型、来源、状态、文档编号/名称；默认显示当前有效和待确认，可切换全部历史。

**表格列**：资料编号、名称、类型、当前有效版本、待确认版本数、来源摘要、更新时间、状态、操作。

**操作**：查看详情、预览、下载、版本历史、创建新版本、确认生效（按权限显示）。批量导出与审厂导出作为后续增强。

建议组件：`ElTable`、`ElTag`、`ElSelect`、`ElInput`、`ElButton`、`ElPagination`、`ElEmpty`。

### 8.2 页面 B：新增/关联资料 `CustomerDocEditor`

以 `ElDrawer` 或 `ElDialog` 实现统一编辑入口，支持：

- 来源：手工上传 / 询价单 / 报价单 / 销售订单 / 样品单。
- 来源单据与行选择（按产品和权限过滤）。
- 选择已有附件或拖拽上传新文件。
- 填写资料类型、资料编号、标题、客户版本号、接收信息。
- 新修订版必须填写变更原因；有 ECN 时可关联编号。
- 点击“检查并继续”进入重复检测结果，再确认入库。

文件选择使用现有 Element Plus `ElUpload` 或已有公共附件组件；最终文件提交和文档入库应区分阶段，避免未确认即创建有效文档。

### 8.3 页面 C：重复检测 `CustomerDocDuplicateDialog`

以 `ElDialog + ElRadioGroup + ElTable` 展示候选。突出“内容完全相同”和“疑似同一文档”两种不同结论。默认推荐关联已有，但不自动执行。新版本分支要求明确目标文档及变更原因。

### 8.4 页面 D：版本历史 `CustomerDocHistory`

顶部显示当前有效版；列表显示系统版本号、客户版本号、状态、接收时间、确认人、生效时间、文件数、变更原因。支持查看历史、预览/下载（权限控制）、对比元数据、确认待生效版本。高级文件内容对比后续实施。

### 8.5 页面 E：详情/预览 `CustomerDocDetail`

展示基本信息、版本信息、主文件及附加文件、来源单据、变更记录和审计日志入口。预览复用现有能力；对 DWG/STEP 等不支持浏览器直接预览的格式，提供下载或受控转换预览，不承诺所有格式都可在线显示。

### 8.6 页面交互约束

- 未授权操作在前端隐藏/禁用，同时后端强制校验。
- `received` 状态不能被生产端当作有效图纸。
- 确认生效前显示影响提示，特别是在制订单的版本关联（完成生产联动后启用）。
- 操作成功后只刷新相关列表、详情和版本数据，不强制刷新整个产品页面。
- 统一 loading、错误提示、取消、重复提交防护和空状态引导。

以上是逻辑组织建议，实际应遵循 JJX 当前组件目录和 API 分层习惯。上传/预览/下载优先复用现有公共组件，不为客供资料单独复制文件基础设施。

建议统一入口接口：

```ts
interface CustomerDocPanelProps {
  productId: string
  readonly?: boolean
  defaultState?: 'active' | 'all'
}
```

`CustomerDocEditor` 应由父组件传入产品上下文与操作模式；来源选项和权限由服务端返回或统一业务配置提供，不允许前端独立决定受控规则。页签注册表是否需要抽象，应根据现有产品作业规范页面规模决定，避免为了一个页签引入过度配置化。

## 10. 后端服务与 API 草案

实际 URL 命名需与 JJX 既有规范统一，以下只定义业务契约。

| 方法 | 路径示例 | 用途 |
|---|---|---|
| GET | `/api/customer-docs?productId=...` | 列表、筛选、分页 |
| GET | `/api/customer-docs/{id}` | 资料详情及有效版 |
| GET | `/api/customer-docs/{id}/revisions` | 版本历史 |
| POST | `/api/customer-docs/intake/check` | 入库前重复检测及候选返回 |
| POST | `/api/customer-docs/intake/confirm` | 用户确认关联/新建/新版本 |
| POST | `/api/customer-docs/{id}/revisions/{revisionId}/activate` | 确认生效 |
| POST | `/api/customer-docs/{id}/revisions/{revisionId}/obsolete` | 作废 |
| GET | `/api/customer-docs/{id}/audit-logs` | 审计记录 |
| GET | `/api/customer-docs/files/{fileId}/download` | 受控下载 |

### 10.1 入库检查响应示例

```ts
type IntakeSuggestion = 'link_existing' | 'new_revision' | 'new_document'
interface IntakeCheckResult {
  checkToken: string              // 短期有效的检查上下文，确认时服务端重新验证
  candidates: Array<{
    docId: string
    revisionId?: string
    matchKind: 'exact_bytes' | 'same_doc_identity' | 'possible_match'
    reasons: string[]
  }>
  suggestedAction: IntakeSuggestion
}
```

### 10.2 生效事务

后端必须在事务中锁定目标文档，校验候选状态、权限和当前有效版本，更新旧版本、新版本与 `activeRevisionId`，写入状态审计，并使用乐观锁/版本号防止并发确认冲突。事件通知等外部副作用在事务提交后可靠触发。

## 11. 权限与审计

### 11.1 第一阶段最小权限

- 查看当前有效资料。
- 查看全部版本（工程/质量等授权岗位）。
- 上传/关联/创建修订版。
- 确认生效/作废。
- 下载/打印（可独立授权）。

生产岗位默认只能获取当前有效版本；工程岗位负责确认。岗位映射以 JJX 现有权限体系为准，不额外搭建一套 RBAC。

### 11.2 审计事件

记录：入库、来源关联、新建版本、确认生效、作废、预览、下载、打印（系统可感知时）。每条至少包含操作人、时间、动作、文档 ID、修订版 ID、来源/目标、结果及必要的请求上下文。审计记录应限制普通业务用户修改/删除；“不可篡改”如需严格保证，应另行设计存储与留存机制，不仅依赖界面不可编辑。

### 11.3 文件安全

- 下载/预览由后端鉴权，避免可猜测的永久公开 URL。
- 历史文件不得被普通业务操作覆盖或物理删除。
- 引用模式需保证源文件可用性和不可变性。
- 打印水印可作为增强；DWG、STEP 原始工程文件不得为加水印而直接改写原文件。

## 12. 生产与质量集成边界

第一阶段只保证产品层面的当前有效版本和历史追溯。后续生产订单、工序执行、检验记录需要能够保存当时实际采用的 `revisionId`，不能只通过 `productId` 动态查询最新版本替代历史依据。ECN 联动应明确影响评估、受影响在制单据和人工确认规则，避免新版本生效时静默改变生产依据。

## 13. 分阶段落地计划

| 阶段 | 交付范围 | 验收重点 |
|---|---|---|
| P0：现状核查 | 产品表、附件表、来源单据、公共上传/预览组件、权限、当前客供资料页签 | 明确可复用能力与真实约束；只读核查 |
| P1：受控资料基础 | CustomerDoc/Revision/File、手工入库、列表、详情、当前有效版、最小权限 | 能入库、查看、确认生效、保留历史；不可覆盖 |
| P2：来源关联与重复检测 | 询价/报价/订单/样品来源适配、SHA-256 检测、四种确认动作 | 原业务上传不受影响；同文件多来源不重复建档 |
| P3：版本与审计完善 | 历史、作废、版本变更原因、审计查询、下载鉴权 | 待确认不替代生效版；操作可追溯 |
| P4：生产质量联动 | 生产/检验锁定修订版、ECN 影响提示 | 在制单据不被静默切换依据 |
| P5：文控增强 | 审厂导出、水印、复杂版本对比、临时授权 | 按实际业务需要逐项评审 |

**实施纪律**：日常采用最小定向验证；不默认新增测试类，不执行全量测试；较完整 E2E 验收安排在阶段收口。Git commit/push 由用户人工执行。未经确认不得自动修改现有业务文件。

## 14. 验收场景清单

1. 产品 A 新建图纸，产生 received，未确认前生产端不可见。
2. 工程确认 A/0，列表仅有一个 active，生产端能查看。
3. 相同文件从报价单再次入库，系统推荐关联已有；确认后来源增加但文档和版本数量不增加。
4. 同名不同内容文件入库，系统提示疑似新版本；旧 active 不变。
5. A/1 被确认后，A/0 superseded、A/1 active，切换一致且可追溯。
6. 相同内容但客户修订号不同，允许有原因地创建新修订版。
7. 无权限人员不能通过 API 或文件直链读取历史/未生效资料。
8. 新增修订版多文件时，所有文件共同构成不可变版本快照。
9. 并发确认两个 received 版本时，最终不可能存在两个 active。
10. 作废当前有效版本后，系统显示无有效版本，不回退到历史版本。
11. 来源单据删除或附件生命周期变化，不得导致已归档受控版本丢失。
12. 后续生产联动后，历史订单仍能追溯其实际使用的修订版。

## 15. 待核查事项与未决问题

### 15.1 必须从现有代码核查

- 产品主键与产品编码字段，是否已有产品文档关系表。
- `sys_attachment` 是否真实存在、字段与附件服务行为、存储后端、是否可覆盖/删除、是否已有 SHA-256。
- 询价、报价、销售订单、样品单附件的关联粒度（单头/明细）、权限和可用性。
- 现有文件上传、预览、下载组件及服务接口。
- 产品作业规范抽屉实际组件结构、产品详情复用方式。
- 现有岗位/权限编码、审计日志机制、数据库类型与唯一索引能力。

### 15.2 尚待业务确认

| 事项 | 当前建议 | 备注 |
|---|---|---|
| 客户资料编号是否必填 | 可空 | 允许没有编号的文件入库，但应给出标题 |
| 接收人/接收时间是否必填 | 手工上传建议必填；单据来源可自动带入 | 需结合真实流程 |

## 16. 评审结论与下一步

本 V2 方案将“产品归属、文档身份、修订版本、文件集合、来源关系”明确分层，并将重复检测从原业务附件上传流程移到受控入库环节。第一版优先实现**可入库、可关联、可确认、可追溯、不覆盖**的业务闭环；复杂文控和生产联动分阶段推进。

**建议下一步**：先对 JJX 现有附件与产品作业规范代码做只读核查，输出“现状差异 + 数据库最终表结构 + 接口清单 + 页面交互清单”，经人工确认后再拆分开发任务。核查时不改代码、不新增测试、不执行全量测试、不 commit/push。
