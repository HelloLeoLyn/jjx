## 1）这张表管什么

附件的"状态"在界面上有若干叫法，一部分直接来自数据库字段，一部分只是前端的过程提示（库里没有对应值）。本表把两者对齐，并写明哪些词**不能**当作库状态使用。

## 2）界面上叫什么 ↔ 库里存什么

| 界面上叫什么 | 库里存什么 | 出现在哪 |
|---|---|---|
| 上传中 | 库里还没有这一行 | 上传队列（文件还没传完） |
| 待绑定 | `TEMP` | 附件中心「待绑定」区 |
| 绑定失败 | 仍是 `TEMP`（只有前端标了失败） | 附件中心「待绑定」区 |
| 已绑定 | `BOUND`（存在有效引用） | 各单据附件区、附件中心 |
| 已释放（留记录） | `PURGED` | 文件管理 → 回收站 / 待清理区 |
| 待人工复核 | `LEGACY` | 文件管理（管理员） |
| （孤儿件，无界面词） | `ORPHAN` | 现基本不用，出现即为无归属闲置件 |

**库里有、界面上通常看不到的行**（只在管理员的文件管理里可见）：被解绑之后的附件、从未绑定过的临时件、`LEGACY` 老附件。它们不在单据界面显示，但记录与磁盘文件都保留。

## 3）三条组件口径

1）**解绑 ≠ 删文件**：业务页面上只提供"移除 / 解绑"，点了只影响"这张单还看不看得到"；**删文件只在管理端**（文件管理 → 回收站 / 待清理）。解绑后记录与磁盘文件都保留，需要省磁盘时走"已释放（PURGED）"。
2）**上传只管上传**：上传只产生"待绑定"的临时件；**正式挂载发生在业务提交时，且与业务同一个事务**（采购收货、采购发票等已按此实现）。上传了但业务没提交，不产生正式引用。
3）**绑定失败由用户重试**：在待绑定区手动点"重试"；系统不自动重试、不自动放弃。已知缺口：过期只能靠提示 + 用户移除（见 dev-20261013-047 与 dev-20261014-034）。

> 第 2 条的"各单据具体在什么时机挂附件"属业务口径，不在本表范围：见 dev-20261015-002。

## 4）两个未入库的过程态（明确不进库）

- **上传中**：文件尚未传完，库里没有这一行；
- **绑定失败**：文件已入库（仍是 `TEMP`），失败信息只存在于前端待绑定队列。

不给数据库增加这两个值：无需迁移，也无需改动上传/绑定/解绑的写入路径。

## 5）规矩

1）**库里值是唯一真源**，界面词只是显示名；同一库里值在不同页面可以叫不同名字，但必须能在本表查到对应关系。
2）**新增状态**：先加库枚举与本节对照表，再写页面文案；页面不得自造第四种说法。
3）写"可能已过期 / 绑定失败"这类**推测性提示**时，必须写清"这只是过程提示，不代表库里状态已变"（例：绑定失败时库里仍是 `TEMP`）。

## 7）只读的四类来源与界面表现（2026-10-15 定）

一个附件区域"能不能改"，来源有四种，**不许合并成一个条件**：

| 类别 | 谁决定 | 判定来源 | 界面表现（2026-10-15 用户拍板 A） |
|---|---|---|---|
| ① 模式=只读 | 页面 | 调用方传 `mode="readonly"` | 整块只读：只有预览/下载 |
| ② 只读属性 | 页面（业务条件） | 调用方传入 `:readonly` 变量 | 按传入值为准（同一页面可切：未审核可改、审核后只读） |
| ③ 无编辑权限 | 权限 | 编辑权限码（`edit-perm` / `editPerm`）未命中 | **按钮不出现** |
| ④ 业务锁定 | 业务状态 | 单据状态（已审核 / 已核销 / 已完成…） | **按钮灰着并写明原因**（如"已审核，不可再改"） |

**③ 与 ④ 必须显示得不一样**：没权限 = 看不到按钮；有权限但业务不允许 = 看得到、灰着、有原因。两者都退化成"看不到"是缺陷。

### 7.1 当前 27 个调用方的归类（2026-10-15 实测）

- ① 模式=只读（1 处）：`views/sales/order/components/OrderDetailDrawer.vue`（销售订单详情）。
- ② 只读属性（3 处）：`views/sales/sample-order/components/SampleInfoCard.vue`、`views/purchase/order/components/OrderDetailDialog.vue`（付款凭证段）、`views/purchase/payment/index.vue`（付款单详情段）。
- ③ 权限判定（23 处）：询价 / 报价 / 订单 / 样品 / 采购订单 / 采购发票 / 采购收货 / 送货回签 / 质量档案 / 质量模板 / 产品资料 / 客供资料 / 菲林图纸 / 操作证据弹窗。多数显式传 `view-perm` + `edit-perm`；少数不传（菲林图纸、付款单段、样品工程台账），此时按"来源权限前缀 + `:view` / `:edit`"兜底判定（`useAttachmentRefs.ts` 的 `canView` / `canEdit`）。
- ④ 业务锁定：可复用的 `:locked` 目前**只被用作"提交中防连点"**（3 处：采购收货弹窗、采购发票新建/核销，`:locked="submitting"`）；**"单据已审核 / 已核销"这类状态锁定没有统一表达** —— 调用方各自用 `v-if` 藏块，或借 `upload-blocked` 文案表达前置未满足（实测 3 处：询价表单"请先点保存生成单据"、菲林图纸"请先选择关联产品"、采购发票"发票文件在核销时上传"）。

### 7.2 结论（写给实施）

1）① ② 由调用方声明，组件照做即可；③ 必须由权限码判定，前端只负责隐藏。
2）④ 要新增统一表达：**能看见、灰着、带原因**。落地时按主分析 §4 的"入口清单"逐调用方核一遍（先只覆盖已证明等价的入口）。

## 8）组件两条规范（2026-10-15 定）

1）**展示范围由调用方传参**：组件不写死"要不要看关联文档 / 是否只按本产品归属"。例——产品详情只传"本产品归属"，所以只看自己的；报价详情传"同链路"，所以能看上游询价单的；将来某个业务想开放，在它的页面多传一个参数即可，组件不用改。
2）**组件治理不以文件数 / 模式数（行数）减少作为验收**。验收看行为：
   - 查看/只读件**不产生**上传、绑定等写副作用；
   - 无权限的人拿不到附件；
   - 不同单据的草稿队列互不串；
   - 切换单据不显示上一个单据的结果；
   - 编辑与查看的列口径一致。
