## 1）为什么写这篇

公共附件组件里混进了业务概念：表格操作列**按「待绑定 / 已绑定」给不同按钮**、确认框**写死「解除引用 / 待绑定队列」**等业务词。
第 0 步**不改代码**，先把**业务模型**和**组件边界**写清楚，作为后续小步改造的基准。

## 2）业务模型：两层对象

1）**文件** `sys_attachment` —— 字节资源，全局一份（sha256 唯一）。状态：
   - `TEMP`：上传了、还没被任何单据引用
   - `BOUND`：至少被一个单据引用
   - `PURGED`：已清理（留记录）
   - `LEGACY`：老附件
   - `ORPHAN`：无归属闲置件
2）**引用** `sys_attachment_ref` —— **「某单据用了某个文件」**这件事；带 展示名 / 资料类型（一级+二级）/ 产品归属 / 排序。
   - **一个文件可被多个单据引用**；**引用 ≠ 文件**。

## 3）业务动作与时机

| 动作 | 落到哪 | 时机 / 约束 |
|---|---|---|
| 上传 | 新增 `TEMP` 文件 | 还没有引用 |
| 绑定（建引用） | 新增 `sys_attachment_ref` 行 | 单据**保存时同事务**（dev-20261015-034）；**缺二级资料类型 → 拒绝保存**（dev-20261015-032） |
| 改（改名 / 改类型） | 改**引用** | 不动文件 |
| 移除（解绑） | 删**引用** | 文件保留 |
| 删文件 | — | **只在管理端回收站**，业务页做不到 |

## 4）三个最容易混的点

1）「待绑定」**不是一个对象**，是「上传完成但还没引用」的**中间态**（只有 `TEMP` 文件、没有引用行）。
2）同一个「移除」：**未建引用**的行 = 丢弃中间态（没有引用可删）；**已建引用**的行 = 删引用 → **底层注定是两个动作**，但这属**业务层**，不该由公共组件自己判断。
3）一个单据解绑**不影响**别的单据对同一文件的引用。

## 5）组件边界（组件只做 CRUD，业务概念不进组件）

1）公共组件只提供**通用 CRUD 能力**（增 / 删 / 改 / 查），**不带任何业务概念**；
2）**显示哪些动作、哪些可用**，一律由**调用方传参**（动作清单 + 行级能力位）决定；组件**不按业务态（待绑定/已绑定）分支**；
3）**业务词不进组件**（「待绑定」「解除引用」「队列」等）；确认框的标题/正文/按钮由调用方传；
4）「保存」这类**业务动作** = **调用方注入的按钮**，组件只负责「渲染 + 回调」，不解释其业务含义。

## 6）分步改造（未开始，每步独立可回滚、默认行为不变）

1）第 1 步：给表格操作列搭「动作清单」参数通道（**不传 = 现状**，行为零变化）；
2）第 2 步：待绑定行的按钮改从参数取（默认仍是 `重试/移除`，外界无感）；
3）第 3 步：确认框文案参数化（组件不再写死业务词）；
4）第 4 步：所有行用**同一套按钮**（差异靠行能力位/参数）+ 调用方注入「保存」。
