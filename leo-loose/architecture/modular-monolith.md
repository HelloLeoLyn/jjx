# 模块与分层设计

性质：实践提炼＋建议基线。适用于单团队或少量团队维护的前后端分离应用。

## 已有实践与采用边界

按模块分包、模块内设置 Controller / Service / Mapper，以及 DTO / VO / Converter，是来源系统已有的组织方式。新项目可延续单体部署，同时加强代码依赖边界。是否拆分独立服务，应由独立发布、故障隔离、团队归属或负载需求决定。

下文的依赖约束是建议基线；来源系统仍存在跨域 Mapper 引用和公共层依赖具体模块的情况。

## 推荐结构

```text
server/
  platform/                 认证适配、日志、存储、数据库、时钟等基础能力
  shared/                   少量稳定类型与纯函数
  modules/<module>/
    api/                    对其他模块公开的接口与契约
    web/                    HTTP Controller、Request DTO、Response VO
    application/            用例编排、事务边界、调用模块接口
    domain/                 有实际复杂度时设置：规则、值对象、策略
    infrastructure/         Mapper、外部适配器、持久化实现
web/
  api/                      接口客户端与传输类型
  components/               基础展示与通用交互组件
  composables/              可复用交互状态
  modules/<module>/         模块页面、组件、用例级交互
  stores/                   真正需要跨页面共享的状态
```

简单 CRUD 可以合并 domain 与 application 的物理目录；不要为没有职责的层创建空接口和转发类。目录名称允许调整，职责和依赖方向应保持清晰。

## 职责与依赖

| 部分 | 负责 | 边界 |
|---|---|---|
| Controller | 协议转换、参数校验、认证授权接入 | 不直接写数据库，不承担长事务编排 |
| Application Service | 一个明确用例、事务组织、调用必要策略 | 不处理 HTTP 响应和 UI 展示细节 |
| Domain | 与协议和存储无关的规则 | 不依赖 Controller、请求会话或页面类型 |
| Infrastructure | SQL、文件、缓存、外部服务适配 | 对上暴露明确接口，返回结果和故障语义可解释 |
| shared | 稳定契约、纯函数、通用值类型 | 不引用具体模块的 Mapper、实体和页面 |
| platform | 公共技术能力 | 特殊场景通过上下文或扩展接口接入，不堆积模块分支 |

跨模块访问优先使用对方的公开接口。只有数据拥有模块可以直接修改其数据。报表联查可以作为明确登记的只读投影存在，应记录涉及表与兼容责任，不能借此开放跨模块写入口。

调用方向由模块依赖图表达；出现双向调用时，先识别共同编排者、稳定契约或只读投影，再决定拆分。消息事件应有明确用途，不能仅为隐藏循环依赖而引入。

## 公共能力的提取规则

满足以下条件再提取公共实现：存在多个真实使用方；相同语义而非仅代码外观相似；依赖较小；公共参数能清楚表达差异；有维护归属与验证。

日志服务接收已经确定的操作者、对象标识和关联标识；若需要模块专属解析，由模块实现解析接口。公共层不应自行查询每个模块的内部表。

避免为了复用建立覆盖所有场景的 BaseService。可组合的小能力更容易保持边界；只用于一个模块的工具可以留在该模块。

## 如何验证

- 新模块使用[模块设计模板](../templates/module-design.md)列出公开接口、数据所有权和依赖。
- 为禁止依赖建立自动检查，例如 shared 不依赖 modules、模块外代码不导入内部 Mapper。
- 集成测试通过模块公开入口验证写入与回滚；复杂纯规则使用快速单元测试。
- 评审时检查职责数量和变更原因。文件行数只作为提示，不直接代替设计判断。

例外应记录理由、范围和退出条件，参照[决策模板](../templates/architecture-decision.md)。
