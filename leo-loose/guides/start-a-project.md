# 用本资料启动新项目

性质：建议基线。此指南组织设计与验证顺序，不是可运行脚手架的安装说明。

## 第一步：确定约束

复制并填写[项目约定模板](../templates/project-profile.md)，确认应用类型、团队规模、数据敏感度、预期负载、可接受停机、部署方式和运维能力。不确定的内容保留为待决定项，不虚构规模数字。

按来源经验可以考虑前后端分离与模块化单体。是否采用 Java / Spring Boot / MyBatis、Vue / TypeScript / Pinia、关系数据库和 Redis，在新项目中决定。Redis、队列、对象存储只在明确需求出现时纳入。

技术版本在开项时核验兼容矩阵并固定工具链与锁文件，本资料不提供声称长期有效的版本清单。

阶段验收：项目约定已填写，标准采用清单有结论，必需的未决项有负责人。

## 第二步：建立最小骨架

按[模块与分层](../architecture/modular-monolith.md)创建职责清晰的目录。建立统一配置加载、请求客户端、响应类型、异常映射、认证授权入口和测试数据库配置。

先选一个普通资源实现创建、查询、修改、分页与拒绝访问。使用明确 DTO / VO，保留持久化模型边界。此时不追求生成所有模块代码。

阶段验收：真实 HTTP 响应与客户端声明一致，正常、非法请求与权限拒绝都有测试，开发环境凭据没有入库。

## 第三步：沉淀第一组公共能力

从实际页面提取搜索、分页、表单、操作反馈和操作列。固定枚举遵循[枚举标准](../standards/enums-and-config.md)，选择唯一组件入口。

为请求建立关联标识和基本日志。至少验证一次异常链路能够从页面提示定位到服务端诊断。初期不为不存在的场景搭建复杂扩展系统。

阶段验收：第二个页面能复用第一组公共能力，组件职责清楚，没有重复类型或隐含全局依赖。

## 第四步：建立写入与故障边界

为关键写用例说明事务、并发、重复请求和超时语义。若引入文件、事件或远程服务，按[副作用标准](../standards/transactions-and-effects.md)设计中间状态、补偿和恢复。

阶段验收：正常和故障注入均能得到可解释结果；重复执行不会重复产生关键副作用；非关键通知与必须完成工作明确区分。

## 第五步：把约定变成持续检查

CI 执行类型、测试、构建和必要的数据库检查。加入模块依赖、接口契约、枚举及文档链接检查。检查脚本与新项目匹配后再使用，不能直接复制来源系统依赖具体表名的脚本。

阶段验收：新检出环境能重建验证；故意制造一个违规时门禁能失败；必需依赖缺失时不会报告通过。

## 第六步：扩展与复核

每个新增模块填写[模块设计](../templates/module-design.md)。重大取舍记录[架构决策](../templates/architecture-decision.md)，说明选择、替代方案、代价与重新评估条件。

在真实需求出现后再决定多实例、独立服务、复杂缓存或事件平台。扩展设计必须覆盖对应的配置传播、定时任务互斥、文件共享和故障恢复。

## 首次发布前的完成条件

- 代码边界、公开 API、权限与数据归属有明确说明。
- 数据迁移、部署配置和恢复方式经过目标环境验证。
- 核心操作的失败、重复和并发场景通过适当测试。
- CI 与实际发布产物对应，未执行项明确可见。
- 必要日志、健康检查和故障定位路径可用。
- 用户确认发布操作；没有把代码完成等同于运行服务已更新。
