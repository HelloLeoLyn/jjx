# 用本资料启动不同类型的项目

性质：建议基线。不预设语言、Web 框架或数据库。

## 1. 确定项目约定

按[项目类型矩阵](../reference/project-shapes.md)识别适用能力，再填写[项目约定](../../templates/project-profile.md)。明确目标、输入输出、运行环境、质量目标和授权范围。必要未知项澄清，其余可独立工作继续。

## 2. 设立 AI 入口

用[项目 AGENTS 模板](../../templates/project-agents.md)建立根入口，说明规则真源、目录地图、命令和完成条件。已有入口保留规则，合并导航；工具专属适配只引用统一入口，避免多份规则分叉。

## 3. 建立最小贯穿功能

| 项目 | 第一个功能示例 |
|---|---|
| Web / API | 真实请求 → 校验 → 响应，有持久化需求再接数据库 |
| CLI / 自动化 | 参数或文件 → 核心处理 → 输出、错误与退出码 |
| 库 / SDK | 公开函数 → 测试 → 打包与调用示例 |
| 桌面 / 移动端 | 界面动作 → 核心逻辑 → 平台适配与反馈 |
| 数据处理 | 脱敏小样本 → 转换 → 输出核对和重复运行 |

目录遵循语言生态，不为空职责建层。复杂应用可参考[分层示例](../architecture/modular-monolith.md)。技术版本与依赖兼容性在建项时核验。

## 4. 按需采用标准

所有项目都明确职责、输入输出、错误处理、配置与验证。HTTP、UI、数据库事务和用户权限只在存在相应能力时采用。

小项目架构说明可以是一页；存在多个运行单元再补结构、运行与部署视图。重大取舍用[ADR 模板](../../templates/architecture-decision.md)，局部实现不强制写 ADR。

## 5. 验证并继续开发

每条检查记录执行目录、依赖、副作用与实际结果。CI 使用本项目的测试和构建命令；必需环境缺失不能声称通过。本资料包的[文档检查](../../checks/README.md)不替代应用测试。

起步完成条件：最小功能可验证；项目约定已填写；AI 能找到真实命令；所需标准已实现或有明确待办；限制可见。

继续开发使用[实施流程](../../workflows/implement.md)，跨会话使用[交接流程](../../workflows/handoff.md)。小任务可在对话或已有任务系统记录，避免重复文档。
