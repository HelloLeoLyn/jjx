# 验证、变更与文档治理

性质：任务关联、定向提交、文档索引、增量门禁为实践提炼；可重复 CI 与架构检查为建议基线。

## 标准的完整形态

每项标准包含规则、适用范围、示例、推荐实现、验证方式、例外和维护归属。文档规则对应检查器，结构规则对应架构检查，外部行为对应测试；不能只写口号。

自动生成的文件、数据库迁移和测试夹具的例外需明确列出。例外有理由、责任人和复核条件，不通过扩大存量基线隐藏新违规。

## 测试分工

| 层次 | 主要验证内容 |
|---|---|
| 单元测试 | 纯规则、边界计算、策略选择 |
| 组件测试 | UI 交互、输入输出、请求状态竞争 |
| 集成测试 | SQL、约束、事务、锁、认证授权 |
| 契约测试 | 实际 HTTP 响应与声明的一致性 |
| 端到端测试 | 少量关键功能的完整连接 |
| 架构检查 | 禁止依赖、重复协议定义、公共入口使用 |

选择能发现真实回归的最低成本测试。Mock 可以隔离依赖，但不能证明真实提交、锁竞争和数据库兼容性。对仅调整文案或格式的低风险变更，不必编写镜像实现的测试。

各层级与专门类型（冒烟、回归、验收、探索性、性能、安全、数据一致性）的完整说明、区别与选用原则见[测试层级与类型](testing-levels.md)。

## CI 推荐顺序

1. 固定工具链和依赖锁文件，安装可重复的构建环境。
2. 执行静态检查、类型检查、单元和组件测试。
3. 启动隔离测试依赖，执行迁移、集成与契约测试。
4. 构建产物，按需要执行关键端到端检查。
5. 保存检查结果和必要诊断，按项目政策审查发布。

这是新项目 CI 环境的设计；操作现有运行服务必须遵守该项目明确授权，测试请求不自动授权重启运行实例。

检查触发路径覆盖前端、后端、脚本、契约与迁移。通过、失败、未执行分别报告；必需检查缺环境不能以成功结束。开发者本地可选择只读诊断模式，但不能冒充严格验证。

Git hooks 提供早期反馈，CI 才是团队共同的执行点。规则变更需要验证检查器自身不会漏报关键情形。

## 数据变更与发布

迁移应可识别版本与应用记录；已应用迁移不原地改写。重建测试环境从迁移或受控结构快照开始，不依赖开发人员本地库。

新增持久化对象先说明数据所有权、生命周期、约束与查询需求；可由现有属性或配置表达时避免增加不必要的真源。表数量可以用于观察变化，不能单独决定设计质量。

发布前明确兼容窗口、回退或前向修复路径、验证条件。备份方式、保存位置、保留期和恢复演练由新项目用户确认；不复制来源项目的特定备份政策。生产数据、凭据和个人信息不得作为默认测试种子。

## 协作与提交

- 开始前明确是讨论、诊断还是执行；讨论不改文件或运行状态，执行只覆盖授权范围。
- 查看已有改动，不覆盖其他会话内容；并行实现使用明确文件归属或隔离工作区。
- 一次提交对应一个可解释的目标，只暂存本任务文件。
- 提交信息可以采用 type(scope): 描述；任务码格式、完成状态及是否自动推送由新项目自行确认。
- 数据写入与工具失败必须可见；写后回查，不能以空 catch 或丢弃错误输出掩盖失败。
- 服务生命周期操作单独确认授权；构建、文档整理和一般测试不隐含部署或重启。

## 文档分类

现行规范、设计决策、使用指南、事实参考和历史记录分别管理。一个主题有明确的现行入口，历史记录注明已过期或被替代。模板与填写后的记录分开存放。

新项目应统一索引、链接检查、编码和变更记录。来源项目的目录名、任务数据库和文件命名日期规则属于具体治理选择，可在项目约定中重新确定。
