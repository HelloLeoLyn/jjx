# 测试层级与类型

性质：层级划分、冒烟与回归的定义和区别、选用原则为实践提炼；CI 集成、度量阈值与自动化为建议基线。

## 目的

不同测试回答不同问题，成本与运行时机不同。混淆类型会同时造成两种浪费：用端到端去覆盖每个边界（慢），或用单元测试假装能证明事务、锁与真实依赖（假安全）。选用原则是：**用能真正拦住该类回归的最低成本测试。**

## 层级（范围从小到大）

| 层级 | 主要验证 | 依赖 | 速度 | 何时写 |
|---|---|---|---|---|
| 单元 | 纯规则、边界计算、算法、状态判断 | 无或 mock | 毫秒 | 有分支或计算就写 |
| 组件 | 单个界面单元的交互、输入输出、请求状态竞争 | 前端框架或运行时 | 秒 | 有交互状态就写 |
| 集成 | 持久化、约束、事务、锁、认证授权 | 真实依赖（隔离实例） | 秒至分 | 跨边界且可靠性敏感 |
| 契约 | 实际接口响应与声明一致 | 真实服务 | 分 | 有对外接口 |
| 端到端 | 少量关键路径全链贯通 | 全栈 | 分至时 | 只覆盖必须走通的主流程 |
| 架构检查 | 禁止依赖、重复定义、公共入口使用 | 静态 | 秒 | 有分层与边界约束 |

## 专门类型

| 类型 | 回答的问题 | 触发时机 | 覆盖范围 |
|---|---|---|---|
| 冒烟 | 系统还基本可用吗 | 部署、重启后，上线前第一关 | 少量主路径，分钟级 |
| 回归 | 这次改动有没有弄坏既有功能 | 每次代码改动后 | 受影响的既有功能，尽量自动化 |
| 验收（UAT） | 是否符合业务预期 | 交付或上线前 | 由用户按真实业务执行 |
| 探索性 | 还有哪些没想到的问题 | 每轮迭代、上手新功能时 | 无固定脚本，靠判断 |
| 性能 / 负载 | 目标规模下还扛得住吗 | 上线前、扩容前、热点改造后 | 关键接口与全链 |
| 安全 | 越权、注入、上传、敏感数据暴露 | 有对外入口或权限面时 | 攻击面 |
| 数据一致性 | 账、流水、余额、关联是否对得上 | 每次改动写入路径后 | 以对账脚本覆盖相关表 |

## 与开发阶段的对应（从设计到完成）

测试活动分布在整个生命周期，不是一个"开发完再测"的独立阶段。每个阶段都有应做的验证与"能进下一阶段的出口判据"：

| 阶段 | 主要活动 | 对应测试 / 验证 | 出口判据（满足才进下一阶段） |
|---|---|---|---|
| 设计 | 明确范围、约束、验收标准与风险 | 需求 / 设计评审；架构检查；可测性设计 | 范围与验收标准明确、接口契约已定义 |
| 实施 | 写代码、小步提交 | 单元、组件；静态 / 类型 / 规范门禁；低层回归 | 本地检查通过、单元与组件测试通过 |
| 集成 | 跨模块、跨边界串联 | 集成、契约、数据一致性对账 | 集成与契约通过、对账无差异 |
| 验证 | 系统级验证与探索 | 关键路径端到端、探索性、回归；里程碑做性能与安全 | 关键路径贯通、回归绿、风险已处置 |
| 发布 | 上线准备与演练 | 空环境演练、**上线前冒烟**、验收（UAT）、回滚验证 | 冒烟全过、回滚可执行、用户验收通过 |
| 运行 | 运维、热修与迭代 | **重启后冒烟**、周期数据对账、热修后的回归 | 监控正常、对账一致、回归绿 |

倾向：**把验证尽量前移到能拦住错误的阶段**（设计就定验收标准与契约、实施就跑单元与门禁），越晚发现的缺陷修复成本越高。

对应资料包流程：[启动](../../workflows/bootstrap.md)（设计）→[实施](../../workflows/implement.md)（实施与集成）→[审查](../../workflows/review.md)（验证）→[交接](../../workflows/handoff.md)（发布与运行）；成因排查见[诊断](../../workflows/diagnose.md)。

## 冒烟与回归的区别

- **冒烟**：最小必过集，只判定“还能不能用”。失败即**停止后续测试**，先修；不深挖边界。
- **回归**：把“以前验过、这次可能被影响”的功能再跑一遍，判定“有没有弄坏旧的”。失败后定位被破坏点。
- **关系**：冒烟通常是回归里最先执行的一小撮；两者都适合放进流水线自动执行。改动越靠底层，回归面越大。

## 选用原则

1. 先问“这类错误会被哪一层拦住”，把测试放在能拦住它的**最低**层。
2. 高风险改动（写入路径、金额、权限、事务、并发）配集成与数据一致性测试；纯文案或样式变更不必写镜像实现的测试。
3. Mock 能隔离依赖，但**不能证明**真实提交、锁竞争与数据库兼容性；关键路径需要真实依赖的测试。
4. 通过、失败、未执行分别报告；缺环境不能以“成功”结束。
5. 测试请求不自动授权重启运行实例、改生产数据或部署。

## 与其他验证的关系

测试是验证的一种；静态检查、类型检查、架构检查与数据对账和测试并列，各自回答不同问题。CI 顺序、门禁纪律与例外治理见[验证、变更与文档治理](engineering-quality.md)。

## 维护归属

一个主题维护一个权威位置；新增测试或检查能力时，同步其命令、依赖、失败行为与覆盖范围。
