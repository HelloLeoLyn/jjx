# 从开发任务提炼工程教训

性质：AI 工程知识库方法；来源任务的事实仍以项目任务系统为准。

## 为什么从任务提炼

开发任务记录了真实现象、根因、修复和验收，比脱离上下文编写的“最佳实践”更适合指导 AI。任务标题通常只描述结果，不能直接当成通用规则；需要保留证据并剥离项目业务细节。

## 一条教训的固定结构

每条教训使用[教训模板](../../templates/lesson.md)，至少包含：

- 来源任务码、状态和证据范围；
- 现象与影响；
- 根因，以及原有设计为什么没有挡住；
- 实际处理或当前建议；
- 可迁移的工程原则；
- 自动检查、测试或评审方式；
- 适用边界、尚未验证内容和不应照搬的业务细节。

## 提炼步骤

1. 从 `sys_task` 读取标题、description、remark、状态、任务码和提交信息；任务描述为空时只作为线索，不直接生成教训。
2. 优先筛选缺陷、回归、架构、权限、数据、测试和协作类任务；纯业务规则保留在项目，不进入通用资料。
3. 将多个任务按失败机制聚类，例如事件契约、权限边界、事务回滚或并发状态，而不是按页面名称聚类。
4. 用任务原文核对现象和修复，不把推测写成事实。status=10 可标“已完成”，status=2 标“已交付待复核”，未完成任务只能标“线索”。
5. 把教训映射到一个现行标准和一个验证方式。没有对应检查时，明确写“需补检查”，不声称门禁已经存在。
6. 在索引中登记来源任务码、类别、证据状态和目标标准。新项目复制资料时保留原则，不复制客户、单据、账号和环境信息。

## 什么算可迁移

可以迁移的是失败机制和防护方法，例如“事件 payload 必须有契约测试”；不能直接迁移的是业务单号、角色名称、状态数字和某张表的字段规则。

一条教训如果只能指导 JJX 的一个业务流程，就留在 JJX 任务或业务文档；如果能指导另一种项目的 API、CLI、库或数据工具，才进入本目录。

## 教训的可信度

教训不是永久真理。来源任务可能只修了一个触发点，未覆盖所有入口；新项目采用前要重新验证。索引中的证据状态必须随着任务复核更新，不能因为文档已经存在就升级状态。
