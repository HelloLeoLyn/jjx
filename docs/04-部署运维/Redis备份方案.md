# Redis 备份技术方案

## 1. 文档概述

### 1.1 目的

本文档旨在为 JJX-ERP 系统设计一套完整的 Redis 数据备份与恢复方案，确保在 Redis 服务宕机、数据丢失等异常情况下，系统核心业务数据能够快速恢复，保障业务连续性。

### 1.2 适用范围

本文档适用于 JJX-ERP 系统中所有使用 Redis 存储的业务数据，包括但不限于：

- 业务序列号（订单编号、客户编码等）
- 短信验证码
- 用户会话（Sa-Token）
- 业务缓存数据

### 1.3 阅读对象

- 后端开发工程师
- 系统运维工程师
- 架构师

## 2. 项目 Redis 使用现状

### 2.1 Redis 使用场景总览

| 序号 | 使用场景      | 存储内容             | Key 格式                  | 数据重要性      | 丢失影响                      |
| ---- | ------------- | -------------------- | ------------------------- | --------------- | ----------------------------- |
| 1    | 业务序列号    | 订单编号、客户编码等 | `seq:{bizCode}:{yyMMdd}`  | ⭐⭐⭐⭐⭐ 关键 | 序列号重复/错乱，业务数据混乱 |
| 2    | 短信验证码    | 手机验证码           | `sms:code:{phone}`        | ⭐⭐⭐ 重要     | 用户无法登录，可重新发送      |
| 3    | Sa-Token 会话 | 用户登录 Token       | `satoken:login:session:*` | ⭐⭐⭐ 重要     | 用户需重新登录                |
| 4    | 业务缓存      | 字典、配置等         | 各业务自定义              | ⭐⭐ 一般       | 重新加载即可                  |

### 2.2 数据特性分析

| 数据类型 | 生命周期           | 数据量            | 一致性要求       | 恢复优先级 |
| -------- | ------------------ | ----------------- | ---------------- | ---------- |
| 序列号   | 当天有效，次日重置 | 极小（<100条/天） | 严格（不能重复） | P0 - 最高  |
| 验证码   | 5分钟过期          | 中等              | 一般             | P2 - 低    |
| 会话     | 用户登录期间       | 中等              | 一般             | P1 - 中    |
| 缓存     | 自定义 TTL         | 较大              | 弱               | P2 - 低    |

## 3. 备份目标

### 3.1 核心目标

1. **序列号零丢失**：确保业务序列号不重复、不跳号、不丢失
2. **RTO ≤ 5分钟**：Redis 宕机后，5分钟内恢复关键业务
3. **RPO ≤ 5分钟**：最多丢失最近5分钟的数据

### 3.2 分级目标

| 数据级别         | 备份策略                | RTO      | RPO     | 实施阶段 |
| ---------------- | ----------------------- | -------- | ------- | -------- |
| P0 - 序列号      | MySQL 持久化 + 定时备份 | ≤ 1分钟  | ≤ 5分钟 | 第一阶段 |
| P1 - 会话        | Redis 主从 + AOF 持久化 | ≤ 5分钟  | ≤ 1分钟 | 第二阶段 |
| P2 - 验证码/缓存 | Redis AOF 持久化        | ≤ 10分钟 | ≤ 1分钟 | 第二阶段 |

## 4. 技术方案对比

### 4.1 方案一：MySQL 持久化兜底（推荐用于序列号）

**原理**：每次生成序列号时，同时写入 Redis 和 MySQL。Redis 宕机时从 MySQL 读取最新值恢复。

**优点**：

- 数据零丢失
- 实现简单，不依赖 Redis 特性
- 恢复速度快

**缺点**：

- 每次操作多一次 DB 写入
- 序列号场景数据量小，性能影响可忽略

**适用场景**：P0 级关键数据（序列号）

### 4.2 方案二：定时全量备份（推荐用于缓存数据）

**原理**：定时任务定期扫描 Redis 中的关键 Key，将数据快照写入 MySQL。

**优点**：

- 对 Redis 无侵入
- 实现简单
- 可批量处理

**缺点**：

- 可能丢失备份间隔内的数据
- 全量扫描对 Redis 有一定性能影响

**适用场景**：P1/P2 级数据，可容忍少量丢失

### 4.3 方案三：Redis 主从 + 持久化（推荐用于会话数据）

**原理**：配置 Redis 主从复制 + AOF/RDB 持久化，实现 Redis 自身的高可用。

**优点**：

- Redis 原生方案，成熟稳定
- 自动故障转移
- 数据安全性高

**缺点**：

- 需要额外部署资源
- 配置和维护成本较高
- 需要运维支持

**适用场景**：所有 Redis 数据的底层保障

### 4.4 方案对比总结

| 对比维度   | 方案一：MySQL 兜底 | 方案二：定时备份 | 方案三：主从+持久化 |
| ---------- | ------------------ | ---------------- | ------------------- |
| 数据安全性 | ⭐⭐⭐⭐⭐         | ⭐⭐⭐           | ⭐⭐⭐⭐            |
| 实现复杂度 | ⭐⭐⭐             | ⭐⭐⭐⭐         | ⭐⭐                |
| 运维成本   | 低                 | 低               | 高                  |
| 恢复速度   | 快                 | 中               | 快                  |
| 资源消耗   | 低                 | 中               | 高                  |
| 适用数据   | P0 序列号          | P1/P2 缓存       | 全量数据            |

## 5. 推荐方案：分层备份架构

### 5.1 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                    应用层 (Application)                       │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              RedisSequenceService                     │   │
│  │  生成序列号 → Redis INCR + 定时备份到 MySQL            │   │
│  └──────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              SequenceBackupTask                       │   │
│  │  每5分钟扫描 Redis → 写入 sys_sequence 表             │   │
│  └──────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              SequenceStartupRunner                    │   │
│  │  启动时从 MySQL 恢复 → 写入 Redis                     │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    Redis 层 (缓存 + 序列号)                   │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │  序列号数据   │  │  会话数据    │  │  缓存数据    │      │
│  │  seq:*       │  │  satoken:*   │  │  cache:*     │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
│  ┌──────────────────────────────────────────────────────┐   │
│  │           Redis 持久化 (AOF + RDB)                    │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                    MySQL 层 (持久化兜底)                      │
│  ┌──────────────────────────────────────────────────────┐   │
│  │              sys_sequence 表                          │   │
│  │  存储序列号快照，用于 Redis 宕机后恢复                  │   │
│  └──────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 备份策略

#### 第一层：Redis 持久化（基础保障）

- 开启 Redis AOF 持久化（appendfsync everysec）
- 开启 Redis RDB 快照（save 900 1, save 300 10, save 60 10000）
- 配置 Redis 主从复制（可选）

#### 第二层：MySQL 定时备份（序列号专用）

- 每5分钟将 Redis 中的序列号同步到 MySQL
- 每天凌晨清理30天前的历史数据
- 应用启动时自动从 MySQL 恢复

#### 第三层：应用层兜底（序列号专用）

- 序列号生成使用 Redis INCR 原子操作
- Redis 不可用时，降级到数据库序列（兜底方案）
- 序列号生成失败时，抛出明确异常，避免生成重复编号

### 5.3 恢复流程

```
Redis 宕机
    │
    ▼
检测 Redis 不可用
    │
    ├── 序列号服务 → 降级到 MySQL 读取最新值
    │               └─ 写入 Redis（恢复后）
    │
    ├── 会话服务 → 用户重新登录
    │
    └── 缓存服务 → 从数据库重新加载
                └─ 写入 Redis（恢复后）

Redis 恢复
    │
    ▼
应用重启 / 检测到 Redis 恢复
    │
    ├── SequenceStartupRunner
    │   └─ 从 MySQL 恢复序列号到 Redis
    │
    ├── 缓存预热
    │   └─ 重新加载热点数据
    │
    └── 恢复正常服务
```

## 6. 数据库设计

### 6.1 序列号备份表

```sql
CREATE TABLE sys_sequence (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '主键ID',
    biz_code VARCHAR(20) NOT NULL COMMENT '业务代码 (SO, PCO, PO, WPO, CUST)',
    biz_date VARCHAR(6) NOT NULL COMMENT '日期 (yyMMdd)',
    current_seq BIGINT NOT NULL DEFAULT 0 COMMENT '当前序列号值',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    UNIQUE KEY uk_biz_code_date (biz_code, biz_date)
) COMMENT '序列号备份表';
```

### 6.2 索引说明

- `uk_biz_code_date`：唯一索引，确保每个业务每天只有一条记录
- 查询场景：按 `biz_code + biz_date` 精确查询，无需额外索引

### 6.3 数据量预估

- 每天最多 5 条记录（5 个业务代码）
- 保留 30 天：最多 150 条记录
- 数据量极小，无需分表

## 7. 代码设计

### 7.1 核心类设计

```
com.jjx.framework.common
├── RedisSequenceService.java          # Redis 序列号服务（已实现）
│   ├── BizCode 枚举                   # 业务代码枚举
│   ├── generateBizNumber()            # 生成业务编号
│   ├── getCurrentSequence()           # 获取当前序列号
│   ├── resetSequence()                # 重置序列号
│   └── getSequenceStats()             # 获取序列号统计

com.jjx.system.domain.entity
├── SysSequence.java                   # 序列号备份实体

com.jjx.system.mapper
├── SysSequenceMapper.java             # 序列号备份 Mapper

com.jjx.system.service
├── SequenceBackupTask.java            # 序列号备份定时任务
│   ├── backupSequences()              # 每5分钟备份（@Scheduled）
│   ├── cleanHistoryData()             # 每天凌晨清理历史数据（@Scheduled）
│   └── restoreSequencesFromDb()       # 从数据库恢复序列号
│
├── SequenceStartupRunner.java         # 启动时恢复序列号
│   └── run()                          # CommandLineRunner 实现
```

### 7.2 备份流程（SequenceBackupTask）

```
@Scheduled(fixedRate = 300000)  // 每5分钟
backupSequences()
    │
    ├── 遍历所有 BizCode 枚举值
    │   │
    │   ├── 从 Redis 获取当前序列号 (getCurrentSequence)
    │   │   └── 如果为 null 或 0，跳过（当天未使用）
    │   │
    │   ├── 查询 MySQL 是否已有记录
    │   │   ├── 无记录 → INSERT 新增
    │   │   └── 有记录 → 比较值大小，只更新更大的值
    │   │
    │   └── 记录日志
    │
    └── 完成
```

### 7.3 恢复流程（SequenceStartupRunner）

```
CommandLineRunner.run()
    │
    ├── 遍历所有 BizCode 枚举值
    │   │
    │   ├── 从 MySQL 查询当天序列号
    │   │   └── 如果存在且 > 0
    │   │       └── 调用 resetSequence() 恢复到 Redis
    │   │
    │   └── 记录日志
    │
    └── 完成
```

### 7.4 异常处理

| 异常场景                | 处理方式                            | 日志级别 |
| ----------------------- | ----------------------------------- | -------- |
| Redis 连接失败          | 抛出异常，业务层捕获后降级          | ERROR    |
| MySQL 写入失败          | 记录错误日志，不影响 Redis 正常使用 | ERROR    |
| 序列号达到最大值 (9999) | 抛出 BusinessException，人工介入    | ERROR    |
| 启动恢复失败            | 记录警告日志，序列号从1开始         | WARN     |

## 9. 风险与应对

| 风险                    | 影响               | 概率 | 应对措施                        |
| ----------------------- | ------------------ | ---- | ------------------------------- |
| Redis 和 MySQL 同时宕机 | 序列号无法生成     | 极低 | 手动设置起始序列号              |
| 序列号达到 9999 上限    | 当天无法生成新编号 | 低   | 监控告警 + 人工介入             |
| 备份数据被旧值覆盖      | 序列号回退         | 低   | 只更新更大的值                  |
| 时钟回拨导致日期错误    | 序列号重复         | 低   | 使用 Redis 时间，不依赖系统时间 |
| 并发写入导致数据不一致  | 序列号错乱         | 低   | Redis INCR 原子操作保证         |

appendonly yes

auto-aof-rewrite-percentage 100

save 60 10000
